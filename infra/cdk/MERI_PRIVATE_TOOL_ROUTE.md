# Meri delegated-tool private route — controlled topology gate

This is a local CDK candidate, **not a deployment instruction to run `cdk deploy`**. On 2026-09-24, the single live environment's `Capiro-dev-Compute` stack reports `UPDATE_ROLLBACK_COMPLETE`, but its logical ALB still refers to an absent physical ALB. The live `capiro-dev-api` and `capiro-dev-meriv2-orchestrator` ECS services have no service registry or Service Connect. Broad stack reconciliation is outside this change.

## Two independent switches

- Default: `meriPrivateToolNetworkEnabled` is absent/false and `meriPrivateToolApiBaseUrl` is absent. No Meri-specific security groups, ingress, or target override are synthesized.
- Network preparation: set `meriPrivateToolNetworkEnabled=true` **without** a URL. This synthesizes a caller SG attached only to the orchestrator, an API-private-target SG attached only to the API, and target ingress from caller on TCP/4000. Both services retain their existing shared SG. Delegated calls still use `MERIV2_API_BASE_URL` and the public route. This is only a source expression of the intended topology; do not deploy the drifted Compute stack to apply it.
- Traffic switch: only after the live topology is registered, reachable and identity-checked, set `meriPrivateToolApiBaseUrl=http://api.capiro.dev.local:4000` with the network flag still true. A URL without the network flag fails synth. The URL is passed only to the orchestrator's `MERIV2_TOOL_API_BASE_URL`. The API and orchestrator must retain the same existing `INTERNAL_SERVICE_SECRET` reference; no secret value belongs in source or release evidence.

The shared service SG is attached to ten live ECS services. An ingress rule on that SG would expose port 4000 on every task using it, so the Meri ingress must target only the dedicated API SG. The shared SG already allows outbound; an extra caller SG cannot by itself restrict egress. The private route uses HTTP within the VPC and still requires a valid user Bearer, tenant/membership and role checks, plus `ToolServiceSecretGuard`. Do not replace these gates with network reachability alone.

## Staged acceptance and rollback record

The opt-in source candidate does **not** safely describe the live Cloud Map attachment: `ComputeStack` declares the cluster namespace `capiro-dev.local` and `cloudMapOptions: { name: 'api' }`, while the recorded live namespace is `capiro.dev.local` and the API ECS service has no registry. A stack synth can therefore propose a registry in the wrong namespace; changing the namespace or importing/replacing discovery resources through `Capiro-dev-Compute` is not approved by this package. Keep `meriPrivateToolApiBaseUrl` unset and do not deploy this stack. Register the existing live Cloud Map API service against the API ECS service only through a separately approved, pinned ECS service update, with rollback rehearsed first.

The private target deliberately bypasses the public ALB/WAF path for the orchestrator's delegated tool POSTs. It is not evidence of WAF enforcement and must not become a general API base URL. The unchanged `/api/clio/tools/:name` handler must continue to enforce the user Bearer, authenticated tenant/membership and route/tool role policy, and the matching internal service secret (`MERI_TOOLS_REQUIRE_SERVICE_SECRET=true` in API). Source evidence is in `ApiToolExecutorRepo`, `MeriController`/`TenantGuard`, `MeriController`/`RolesGuard`, and `ToolServiceSecretGuard`; the CDK synth test pins the API service-secret enforcement environment and secret references on both services. Network reachability is an additional boundary, not an authorization substitute.

Before any authorized topology change, record (with secret values omitted):

- exact API and orchestrator service descriptions, current task-definition ARNs, desired/running/pending counts, deployment state, subnets and SGs;
- canonical task-definition JSON SHA-256, container image digest for every running task, and the exact prior task-definition revision to restore for each service;
- the existing Cloud Map namespace/service IDs, DNS record/TTL and instances; ALB target-group health; and current API `/health` plus orchestrator `/health` responses.

Stop if live services, Cloud Map, SGs, task image digests or service status differ from the approved snapshot. Do not hand-register task IPs. The topology-only stage adds the dedicated caller/target SGs and attaches the existing Cloud Map `api` registry to the API service, leaving both task definitions and `MERIV2_TOOL_API_BASE_URL` unchanged. ECS service-registry changes roll tasks: require API desired/running `2/2`, orchestrator `1/1`, zero pending tasks, completed deployments, healthy ALB targets, and Cloud Map A records matching the current API task ENI addresses. From the orchestrator network, verify `api.capiro.dev.local` resolves only to those private task addresses and a read-only `GET /health` on port 4000 succeeds. Recheck both service health endpoints and save the exact post-stage service configurations and task-definition ARNs/digests.

Only after a separately approved traffic-switch stage may a pinned orchestrator task revision differ by exactly `MERIV2_TOOL_API_BASE_URL=http://api.capiro.dev.local:4000`; preserve image digest, roles, secret references (including `INTERNAL_SERVICE_SECRET`), all other environment/configuration and service network settings. Keep the API task definition unchanged. Require stable healthy service counts and repeat the direct private health check before reads. At the final live-QA gate, run exactly four authorized, read-only delegated QA requests in the approved `capiro-internal` tenant using uniquely marked synthetic records where needed; no other tenant is in scope. Capture each `x-meri-delegated-request-id`; for all four, correlate bridge dispatch/completion with API handler entry/completion and record status only (no prompt, credentials or response bodies). Confirm public app/API health remains healthy. Run approved negative authorization controls for missing/invalid Bearer and missing/wrong service secret; each must be denied by the normal API path. Wrong-tenant and role-denied live controls require an appropriate separately approved actor and remain unverified with the current admin-only account; do not impersonate another tenant or create users/grants. These checks establish application authorization behavior, not WAF coverage: the delegated requests do not traverse the public WAF.

Rollback gates are asymmetric and explicit. If only the traffic switch fails, restore the exact pre-switch orchestrator task-definition ARN (with no `MERIV2_TOOL_API_BASE_URL`), force/wait for stable `1/1`, verify its image digest and health, then confirm delegated calls returned to the prior public route. If topology preparation harms service health or authorization, first restore the captured pre-stage API/orchestrator service configurations and remove the API registry via an empty `serviceRegistries` update; retain the exact prior task definitions/digests, wait for API `2/2` and orchestrator `1/1`, and verify all ALB targets and public health. Do not delete the dedicated SGs until recovery is confirmed and cleanup is separately reviewed. ECS service-registry updates trigger a rolling deployment and require the ECS service-linked role; operator authorization and rollback capacity are prerequisites. This staged package grants no live change approval. See the [Amazon ECS `UpdateService` API](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_UpdateService.html) for the documented rolling-deployment behavior when service registries are changed.
