THE TWO REMAINING LOSS PATHS (root-confirmed, both closed here)

1) DURABLE ACCEPTANCE WAS BEING READ AS A COMPLETED HANDOFF.
   Meri's receiver stores ACCEPTED and then QUEUED for the ACTIVE /
   open-occurrence / backpressure cases (source-event-receiver.mjs:227-267), and
   source-event-store keeps RETRYABLE=['ACCEPTED','QUEUED']. Nothing in production
   drains `unresolved` (only focused tests call it) — the producer's future replay IS
   the retry mechanism. The prior Core lane listed ACCEPTED and QUEUED in
   DEFINITE_SOURCE_EVENT_STATES, so an accepted-but-unsettled event advanced the
   durable recovery cursor and was never re-offered: the same permanent stranding the
   cursor exists to prevent, one state later.

   FIX: DEFINITE_SOURCE_EVENT_STATES is GONE. The single rule is now
   advancesDeliveryCursor({state, recorded}) in bizdev-watch.types.ts:
     - ACCEPTED / QUEUED                 -> HOLD (in flight, retryable)
     - UNKNOWN / unintelligible state    -> HOLD
     - DEDUPED                           -> HOLD unless it names a terminal recorded outcome
     - DISPATCHED / SKIPPED / REFUSED / CONFLICT -> ADVANCE
     - DEDUPED + recorded in {DISPATCHED, SKIPPED, REFUSED} -> ADVANCE
   An aggregate-only owner may now acknowledge a page ONLY when it is correctly
   accounted for (offered === page length AND the seven counters sum to it) and reports
   NEITHER unknown NOR queued (aggregateAcknowledgesPage). A holding page leaves the
   cursor exactly where it is; the next evaluation re-offers the SAME immutable events.

2) A DEDUPED ANSWER'S RECORDED OUTCOME WAS DISCARDED.
   Meri's HTTP boundary serialises the whole receiver result
   (source-event-http.mjs: `response({outcome, sourceEvent}, 200)`), so
   `sourceEvent.recorded` — the store state of the row the replay matched — is on the
   wire. The transport read only `sourceEvent.disposition`, and delivery cast any
   non-UNKNOWN disposition straight to a state: a SETTLED replay naming a recorded
   UNKNOWN row (receiver:237) became a terminal DEDUPED and advanced the cursor.

   FIX (preserve + validate the real field, no new endpoint, Meri's 0.3 protocol
   untouched):
     - transport `event()` now reads `sourceEvent.recorded`, keeps it ONLY when it is one
       of Meri's store states (ACCEPTED/QUEUED/DISPATCHED/SKIPPED/REFUSED/UNKNOWN) and
       normalises anything else to null; it also refuses a disposition string the
       protocol does not define (-> null -> UNKNOWN), so an unintelligible answer can
       never be cast into a terminal state.
     - SourceEventDeliveryResult carries `recorded: string | null`; the disposition is
       reported VERBATIM (DEDUPED stays DEDUPED — never rewritten into a terminal state).
     - The recovery disposition carries `recorded` through to the runner, normalised
       again there against the same vocabulary, so a foreign owner cannot smuggle an
       unrecognised outcome into a completed handoff.

INDEPENDENT-REVIEW CROSSING (review 17472 / session a6404f) — FOUR CORRECTIONS

D1 — THE RECOVERY PAGE WAS WATCH-WIDE WHILE THE CURSOR IS PER FAMILY.   [FIXED]
   readDeliveryRecoveryPage() filtered on (tenantId, watchId) only, but the cursor it
   advances lives inside the (watch, sourceFamily) source-state row's scan metadata
   (schema prisma:17636-17638). In a watch scanned by more than one family the page mixed
   families, so one family's alerts spent the other family's per-source budget
   (maxRecordsPerSource), advanced the other family's cursor, and were delivered against
   the other family's approved binding — duplicate/foreign binding + cross-family budget.
   FIX: the existing canonical family is now BOUND TO THE QUERY. readDeliveryRecoveryPage
   takes `sourceFamily` and adds it to the WHERE clause; the caller passes
   `state.sourceFamily` (the very family whose row the cursor belongs to). The alert row's
   own `sourceFamily` is the same canonical family the family's draft builder emits
   (bizdev-watch-runner.ts: draft.sourceFamily -> businessDevelopmentAlert.sourceFamily),
   so the page is exactly the channel the cursor is evidence about. Keyset order
   (firstObservedAt, id) ASC and the contiguous-oldest-first prefix are unchanged.

D2 — THE BOUNDED PAGE COULD OUTLIVE THE LEASE IT RUNS UNDER.   [FIXED]
   A page of maxRecordsPerSource (50) alerts can occupy 50 x (binding read + 2 bounded
   attempts) — with SOURCE_EVENT_REQUEST_TIMEOUT_MS=3000 and SOURCE_EVENT_DELIVERY_ATTEMPTS=2
   that is 9s per alert, i.e. ~450s against a 300s lease: delivery could still be running
   when the lease expired and another evaluator could legitimately claim the row.
   FIX (no new lease manager, no renewal owner invented, no queue): the page is SIZED TO
   FIT the lease the pass already holds. SOURCE_EVENT_WORST_CASE_PER_ALERT_MS is exported
   from the transport itself (binding read + every bounded attempt, derived from the real
   timeout constants so it cannot drift), and recoveryPageBound(maxRecords, leaseUntil, now)
   = min(maxRecords, floor((leaseUntil - now - RECOVERY_FINALIZE_MARGIN_MS) / worst case)).
   A page that does not fit is simply SHORTER: the unread alerts stay behind the cursor
   (which only advances over what was actually answered), so nothing is skipped, nothing
   is delivered under a possibly-foreign lease, and the next evaluation resumes at the
   same cursor. Cursor/CAS/UNKNOWN semantics are untouched; the existing source-state lease
   remains the ONLY lease owner.

D3 — DEAD COMMENTS/CODE.   [CORRECTED LOCALLY, trivial only]
   The `committedAlerts` array (declared outside the transaction, pushed in two places,
   never read after the recovery step was rewritten to read committed custody) is deleted,
   and the two comments that still described the old "offered after the transaction
   resolves" hook and the sink type's old wording now state what the code does: the
   bounded oldest-first page is read from committed custody AFTER the commit.

D4 — A 200 WAS TRUSTED WITHOUT CHECKING IT NAMED OUR EVENT.   [FIXED]
   The transport consumed `sourceEvent.disposition` without ever checking the response was
   about the event we sent, so a foreign or garbled success could be read as a completed
   handoff. Verified the real wire first (READ-ONLY Meri 25eede1b4): source-event-http.mjs
   answers `response({outcome: inert.disposition, sourceEvent: inert}, 200)` where the
   receiver's own `result()` (source-event-receiver.mjs) always carries
   `eventId: unit.event.eventId` and `eventHash: unit.event.eventHash` — i.e. the identity
   is echoed on EVERY 200 path, and snapshotSourceEvent() has already refused an envelope
   whose hash is not its own canonical fact hash (SOURCE_EVENT_HASH -> 400), so an echoed
   200 proves the response named the event we sent. Error responses carry no `sourceEvent`.
   FIX: SourceEventTransport.event() now also reports `eventId`/`eventHash` exactly as the
   answer named them (absent/unreadable -> null), and the delivery owner accepts a 200
   disposition ONLY when `answer.eventId === envelope.eventId && answer.eventHash ===
   envelope.eventHash`. A foreign event id, a different fact hash, an absent or garbled
   identity -> UNKNOWN ('SOURCE_EVENT_RESPONSE_IDENTITY') and the cursor HOLDS — never a
   terminal advance. The bounded replay resends the same bytes, which Meri's identity dedup
   makes the same one event. No new public endpoint; Meri's 0.3 protocol stays frozen.
   (Retained by design from the review's own limits: an explicit 4xx refusal and a CONFLICT
   are still read as recorded-terminal dispositions, and a systematic producer-side contract
   drift still presents as a definite refusal — D5 below, a product decision, not a silent
   one; the finite first producer keeps its generation/authority target unchanged.)

J1 — MERI'S APPROVED CATCH-UP / OVERLAP / BACKPRESSURE (READ-ONLY TRACE, NO MERI EDIT)
   Traced against the live receiver at 25eede1b4 (my checkout's HEAD; read-only; Meri has a
   live native qualifier 57697 and a separate owner). The receiver's step 7 hands the
   occurrence to the EXISTING scheduled-dispatch owner ("its own fence, catch-up window,
   overlap barrier and backpressure apply unchanged"), and scheduled-occurrence.mjs derives
   the occurrence with `scheduledAt: occurredAt` — the alert instant Core sends:
     * STALENESS (already owned by Meri): scheduled-dispatch.mjs:89
       `missed = now - Date.parse(occ.scheduledAt) > catchupWindowMs + spec.jitterMs`
       -> 'SCHEDULE_OCCURRENCE_MISSED'; the receiver does not list it retryable, so it
       settles REFUSED (pinned by source-event-receiver.test.mjs:312) -> a recorded-terminal
       refusal Core may advance on. Crucially the check applies ONLY to an occurrence that
       was never admitted: scheduled-dispatch.mjs:189
       `refusal = fence(...) ?? (admitted ? null : missed(...))`.
     * HELD-REPLAY LIVENESS: an already-admitted occurrence is NOT stale-refused; if its run
       already started, a replay settles DISPATCHED (scheduled-dispatch.mjs:187). While
       another row of the schedule is OPEN the barrier returns
       'SCHEDULE_OCCURRENCE_UNRESOLVED' (scheduled-dispatch.mjs:154), which the receiver maps
       to QUEUED/accepted-retryable (source-event-receiver.test.mjs:361) — the durable
       acceptance that now correctly HOLDS the Core cursor until it settles on evidence.
   CONCLUSION: no required catch-up gap exists for Core to close. Core adds NO staleness
   semantics and silently drops no unknowns. The known remaining exposure (an OPEN barrier
   row that never settles on evidence holds the cursor indefinitely, by design and visible
   in counts) is Meri's owner's semantics, reported here as a count/liveness limit rather
   than retargeted from Core.
