# Core passive Institutional Memory recall: owner proposal

Source review pinned to Core PR #86 `b40971b1f8de888687a8fb92fbdf4ff653fe10d3` and Meri memory adapter `4192e85dd97dee9652d75ef3ef6a49278bf3d051` (which includes `78f72f28ed9f5cce1146ac5b061bd3bdb6c7aed0`). Audit: Meri PR #121 comment `6249424994`; Core coordination: PR #86 comment `6250394327`. This packet changes no runtime source, route, credential, listener, migration or deployment setting.

## Source finding

- Meri's `apps/gateway/sources/client-knowledge/http-adapter.mjs` sends one canonical HTTPS POST body `{input,metadata}` for `search_memory@0.2.0`. The Core `POST /api/clio/tools/search_memory` method passes its body directly to `MeriToolsService.executeFromAuthenticatedUser`; `searchMemory` reads top-level `query`, `clientId`, `k`, `cursor`, `memoryItemId`, and `contentCursor`. With the Meri body it returns `{error:'Provide a search query.'}`, which the Meri output validator rejects because its normalized input has a query. A fixed endpoint pointing at the existing route therefore cannot connect recall.
- Core's native `searchMemory` already builds the memory family projection from `searchCapiroData` and `projectMemoryContent`. Its `institutional_knowledge` adapter uses `canonicalMemoryEligibilitySql` and `clientMemoryAllowed` inside `withTenantUser`; the predicate checks the owner/visibility, selected client wall, active status, governed approval and conflict suppression, sensitivity, expiry and `effective_from`. Keep this retrieval and the existing content cursor. The source output looks aligned with `ClientKnowledgeMemoryOutput`, but no cross-repository response contract test has qualified it.
- Meri's `memory-eligibility.mjs` calls `readMemoryEligibility` **after** validating the full page. The callback receives the current operation/input/metadata, trusted normalization context, canonical argument and request hashes, binding, subject, policy revision, source IDs, bounded deadline, page hash and exact `{memoryItemId,recordSha256}` list. It requires a fresh, same-pin receipt for the entire page, including an empty page. Core has no such route or producer, and Meri's production broker/composer does not yet supply this callback.
- The Core preview listener's fixed P1 POST rule already admits `/api/clio/tools/[a-z][a-z0-9_]{1,63}`. Its P3 native-operations rule is at the three-path-value limit, and the optional memory POST rule is allocated only by a held v6 listener readback. A special service-only path under the existing tools prefix can use P1 without claiming a new listener slot; a new `/api/clio/memory/...` path would need central listener allocation.

## Shared Core owner patch

The owner of `apps/api/src/meri/meri.controller.ts` and `apps/api/src/meri/meri.module.ts` should implement the following together, with a small memory-specific parser/eligibility service under `apps/api/src/meri/memory-receiving/`. Do not add `search_memory_eligibility` to the model tool manifest or ordinary tool allowlist.

1. On `POST /api/clio/tools/search_memory`, admit exactly the passive `{input,metadata}` branch only when `hasVerifiedToolServiceIdentity(req)` is true, after the ordinary native bearer and `standard_user` checks. Require the six normalized input fields and the five frozen `false` metadata flags of `search_memory@0.2.0`; reject extra fields and rewritten values. Then call the **same** `MeriToolsService.executeFromAuthenticatedUser(ctx,'search_memory',input)` within `withMeriToolRequestControl`. Preserve the existing raw-tool branch and all its observation, attachment, read-delegation, telemetry and allowlist behavior. Do not treat metadata as an authorization assertion. The service secret guard's development observe mode is not proof; this branch must check the verified marker explicitly.
2. On an exact service-only `POST /api/clio/tools/search_memory_eligibility`, require the same native bearer, `standard_user`, verified service marker and no-store response. Handle it as a distinct protocol operation before `assertMeriToolAllowed`; it must never enter `MeriToolsService` or the model schema list. Parse a closed request with the exact Meri callback pins and `{resultSha256,records,deadlineMs}`. Check `operation={id:'search_memory',version:'0.2.0'}`, `sourceIds=['client_knowledge_memory']`, the five frozen metadata flags, `normalizationContext={tenantId:ctx.tenantId,userId:ctx.userId}`, `binding.tenantId/actorId` against the authenticated context, and `subject` actor/tenant/kind/entity against `input.clientId`. Recompute RFC 8785 SHA-256 for `input` and `{input,metadata}` and require the supplied `argumentsSha256` and `requestSha256`. Check matching policy revision and subject scopes, bounded deadline, UUIDs, SHA-256s, unique IDs and a maximum of three records. Fail closed on any mismatch or unavailable owner check.
3. Inside a single `PrismaService.withTenantUser(ctx.tenantId,ctx.userId,...)` transaction, recheck the selected client with `clientMemoryAllowed` even if the page is empty. For every listed item ID, query the *current* `memory_items` row using `canonicalMemoryEligibilitySql({tenantId,userId,allowedClientIds,memoryItemId})`, and require its `client_id` to be null for null selection or null/the exact selected client otherwise. Require one distinct eligible row per requested ID. A revoked wall, superseded/corrected row, owner change, unpublished/pending proposal, expired or not-yet-effective fact, disallowed sensitivity or query error yields no positive receipt. Do not convert an unavailable Core read into an empty eligible result.
4. When all checks pass, return the exact Meri receipt fields: `operation`, `argumentsSha256`, `metadata`, `normalizationContext`, `requestSha256`, `binding`, `subject`, `policyRevision`, `sourceIds`, `resultSha256`, `checkedAtMs`, `expiresAtMs`, and `records`. The receipt omits `input` and tokens; `checkedAtMs=Date.now()`, `expiresAtMs` must be strictly after that check and no later than the caller's deadline. Copy each input record with `eligibleForRecall:true`. Echoing record hashes is correlation to the Core HTTPS response, not a claim that hashes alone prove content. The native read is trusted because it came from the fixed Core origin over HTTPS and the Core route used the ordinary canonical retrieval. The callback must check current row eligibility immediately before Meri releases that page. Keep the receipt very short lived and do not persist page content.
5. The Core service may verify the authenticated actor/client and current memory facts. It cannot independently establish Meri's current run, writer fence, task grant or policy revision from an arbitrary JSON claim. The Meri `getCredentials`/`readMemoryEligibility` owner must reacquire current run/selection/rights and bind the *same* pins and native user bearer on both calls. Do not mint a new bearer or treat the service secret as a user/session grant. If Meri cannot provide that live task binding, leave the source disabled.

## Qualification before composition

Add focused Core HTTP regressions for the literal `{input,metadata}` request, raw-tool compatibility, wrong actor/tenant/client, missing verified service marker in observe mode, forged hash/operation/source/policy, duplicate or extra record, empty-page client-wall revocation, and changed/expired/superseded canonical row between read and receipt. Execute one cross-repository test using Meri's actual `createClientKnowledgeHttpAdapter`, frozen `ClientKnowledgeMemoryOutput` validator and Core route response for client and personal scopes, content continuation, empty and unavailable pages. Meri's composer/P2 owner then binds the exact fixed HTTPS endpoint and current credential/eligibility ports and measures coverage. An isolated fixture or a receipt shape test cannot mark recall connected.

The optional frontend memory review routes, Core listener priorities, live credentials, migrations, model calls and deploys are outside this proposal.
