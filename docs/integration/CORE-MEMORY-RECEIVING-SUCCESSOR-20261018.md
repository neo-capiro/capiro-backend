## Bounded helper admission contract for the receiving owners

The existing `tool` slot is **one per `(run_id, call_key)` in both code and SQL** (`READ_TOKEN_CEILINGS.tool = 1`; `meri_read_delegation_slots_tool_check` is `BETWEEN 0 AND 1`). The token table also permits only `tool`, `mode`, `reference`, and `current`. An eligibility call cannot take a second ordinary tool token or claim a new, unrelated model invocation. `search_memory_eligibility` is an internal helper target, never an admitted model operation or discovery entry.
The page operation `search_memory` is also absent from Core's current delegated-tool allowlist; its addition belongs with completed page admission, not this source-only patch.

A compatible addition needs its own narrowly scoped, one-use helper admission and additive schema migration. The recommended shape is a distinct `memory-eligibility` credential/counter with a ceiling of one per existing `(run_id, call_key)` slot. Do not widen `tool_tokens`; do not issue a helper if the original `search_memory@0.2.0` page token was not consumed for that same slot, delegation, actor, selected client and canonical arguments. At issue and consume, reuse the current `readRunFacts` snapshot budget lock and exact original ADMITTED grant check, active delegation/consent/member/client checks, and `assertToolReservation` for the **parent** `search_memory` operation and its original `UNKNOWN` reservation. The helper target is fixed to `POST /api/clio/tools/search_memory_eligibility`, with the exact eligibility request bytes bound by `bodySha256`, and its claim must bind the parent page token JTI and page body hash, run/attempt/fence, subject, input hash, canonical page request hash and page result hash. The Core receiver compares those claims with the parsed callback and authenticated grant before the canonical eligibility SQL. No helper reissue is needed for the first version; a lost issuance response fails closed. This is a proposal for the shared read-delegation owner, **not implemented by this PR**.

The parent page and helper both need Core's pre-byte delegated release recheck. The helper returns a receipt whose `expiresAtMs` is at most the request deadline and five seconds after its check. Meri must carry that exact receipt through authorization, retention and settlement, then require `now < expiresAtMs` at the final dispatcher release alongside its final authorization. An expired receipt refuses output; after settlement, do not mint a fresh helper using a reservation that is no longer `UNKNOWN`. The Meri memory owner must compare the receipt's page hash and record hashes to the actual page before release. Personal recall remains held.

For each page call, `requestSha256` hashes the canonical `{input,metadata}` value, while `target.bodySha256` hashes the **emitted UTF-8 JSON bytes**. These can differ with property order. The token admission checks the latter against the raw HTTP body; callback and output validation check the former against the normalized value. The focused passive-source spec asserts that distinction. Meri's shared gateway test should compare emitted bytes to `target.bodySha256` and retain its separate canonical `requestSha256` assertion.
