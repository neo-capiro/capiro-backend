# Core OS findings: read-only remediation research

Checked 2026-10-19. Frozen application source: `50475125275853299798fc40f8cb119f0b865464`, tree `c01138fed2e0e89e50f0f54f35c0ff4d4415c9b4`. The receiving checkout remained clean. No repository edits, image builds, package installs, AWS operations, or vulnerability suppressions were performed by this research task.

**Decision: no safe one-line GNU/Debian fix was established.** Current Bookworm packages remain classified vulnerable to all seven reported HIGH findings. Current Trixie packages resolve only two of the six util-linux findings and leave zlib unresolved. Alpine offers relevant patched packages, but changing Core from glibc to musl requires repairing and qualifying the existing AMD64 candidate. No replacement image is established as fixed or deployable.

Metadata discrepancies remain material. For 53613, the current CVE description says `2.41.5`/`2.42.2` fix the new mount API; `2.42.4` fixes a legacy path using `/proc/self/fd`, while its legacy fallback without `/proc` remains affected. This is narrower than a universal fixed-version claim. The 78409 upstream affected range starts at `2.42`, and 78408 at `2.40`, while Debian classifies Bookworm `2.38.1` vulnerable; 78408 advisory header versions also differ from Debian's explicit `2.42.4` fix. The zlib CVE description starts at `1.3.1.2`, but [Debian bug 1146895](https://bugs.debian.org/1146895#50) keeps older packages affected pending scope resolution. None of these discrepancies justifies suppressing the current scan.

## Official Node 22 base options

The [official image catalogue](https://raw.githubusercontent.com/docker-library/official-images/master/library/node) lists Node `22.23.3` families for Bookworm, Bookworm slim, Trixie, Trixie slim, Alpine 3.23 and Alpine 3.24. Node 22 is in Maintenance LTS until [2027-04-30](https://raw.githubusercontent.com/nodejs/Release/main/schedule.json). The floating `22-slim` family remains Bookworm slim, and `22-alpine` currently selects Alpine 3.24.

- [Bookworm slim recipe](https://raw.githubusercontent.com/nodejs/docker-node/main/22/bookworm-slim/Dockerfile): no available Bookworm fix for these findings was verified. Changing the tag or adding `apt-get upgrade` cannot be represented as resolving them.
- [Trixie slim recipe](https://raw.githubusercontent.com/nodejs/docker-node/main/22/trixie-slim/Dockerfile): four util-linux findings plus zlib remain classified vulnerable. A Trixie switch does not satisfy the seven-finding gate.
- [Alpine 3.24 recipe](https://raw.githubusercontent.com/nodejs/docker-node/main/22/alpine3.24/Dockerfile): a relevant alternative base family, with an ABI change. Its x64 musl Node binary comes from Node's unofficial-builds project. [Node Docker documentation](https://github.com/nodejs/docker-node#musl-builds-for-alpine) classifies AMD64 musl as Experimental despite publication as an official container variant.

The [Alpine 3.24 zlib recipe](https://raw.githubusercontent.com/alpinelinux/aports/3.24-stable/main/zlib/APKBUILD) explicitly fixes 85091 in `1.3.2-r1`; its [patch](https://raw.githubusercontent.com/alpinelinux/aports/3.24-stable/main/zlib/CVE-2026-85091.patch) is upstream commit `df84af25dc1942490e1d1c899a07619152a46148`. The [x86_64 package directory](https://dl-cdn.alpinelinux.org/alpine/v3.24/main/x86_64/) publishes `zlib-1.3.2-r1.apk` and `util-linux-2.42.3-r1.apk`. Availability is not inclusion in an image.

The [Alpine util-linux recipe](https://raw.githubusercontent.com/alpinelinux/aports/3.24-stable/main/util-linux/APKBUILD) lists 78408 fixed at `2.42.3-r1`, and 53613/76642/78409/78410 at `2.42.3-r0`. It omits 53615 from secfixes; coverage is inferred from the upstream `2.41.4` fix, not an explicit Alpine CVE entry. The 53613 legacy caveat still prevents treating that package floor as a universal semantic fix. The existing Core candidate instead requires no installed util-linux-origin packages.

Parent's separate registry/package inspection reports the existing pinned AMD64 Alpine base has **no util-linux origin but has zlib `1.3.2-r0`**. Therefore that base digest alone does not resolve all seven; the recipe's authenticated upgrade to `1.3.2-r1` is necessary. That inspection was performed by `core_aws_plan`, not repeated in this research. Current floating-tag image contents and the public ECR mirror's exact digest were not independently attested here.

## Relevant existing AMD64 candidate and prerequisites

At source 504, `apps/api/Dockerfile` ships `public.ecr.aws/docker/library/node:22.23.3-bookworm-slim`, with fresh production dependencies and a targeted Perl upgrade only. It does not contain a util-linux/zlib fix.

The relevant PR48 lineage is `apps/api/Dockerfile.alpine-amd64-qualification`, not just PR20's ARM64 experiment. It pins `node:22.23.3-alpine3.24` AMD64 child manifest `sha256:2c752226d477b4a886378baa95b9af252be59301b725fdb0b7e15208131505a8`, requires `zlib>=1.3.2-r1` in base/runtime, uses a separate musl pnpm cache, and generates `linux-musl-openssl-3.0.x` Prisma engines. The [Prisma 5.22.0 target list](https://raw.githubusercontent.com/prisma/prisma/5.22.0/packages/get-platform/src/binaryTargets.ts) includes this target. [Sharp 0.35.5](https://raw.githubusercontent.com/lovell/sharp/v0.35.5/package.json) has a distinct x64 musl optional binding; [Sharp installation requirements](https://sharp.pixelplumbing.com/install/) require musl >=1.2.5 and SSE4.2 for x64. Neither fact establishes this application's installed graph or native behavior.

PR20/21/22 history already records failed probes and later source repairs, not an accepted Alpine image. Fresh production-closure work removes the rationale for assuming retained development Sharp/LibSQL/SWC/ONNX packages are present; actual installed-owner/closure evidence must decide. Parent's independent `core_features` review reports four of seven frozen closure inputs and raw x64 schema evidence are stale at source 504. Thus selecting the existing AMD64 Dockerfile is not a drop-in release fix.

Before any separately approved build, the owner must bind the candidate's source, lock/manifests, closure contract, image-local Prisma schema and derived-owner evidence consistently; review the glibc-to-musl change; and preserve fail-closed native/closure checks. Qualification then needs actual APK origins/versions, complete installed production/native ownership, real Prisma/canvas/esbuild operations and any genuinely retained native dispatchers, full compiled API startup and health/shutdown against approved isolated fixtures, and a supported COMPLETE scan of the exact resulting immutable digest. The earlier Alpine verifier's zero-HIGH/CRITICAL minimum does not relax the receiving release's zero-findings gate. An unreachable-database entrypoint check alone does not satisfy full startup. No spend, source-archive replacement, ABI switch or deployment is authorized by this report.

Read-only research is complete. The remaining blocker is lack of a reviewed, internally current and runtime-qualified replacement image, not a claimed absence of advisory data. Parent owns remediation and any further build decision.
