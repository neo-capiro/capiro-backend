## Why a small Debian update is not an established fix

The current [official Node Bookworm recipe](https://github.com/nodejs/docker-node/blob/main/22/bookworm-slim/Dockerfile) still selects Node 22.23.3 on Debian Bookworm. Its [Trixie sibling](https://github.com/nodejs/docker-node/blob/main/22/trixie-slim/Dockerfile) changes the Debian base but does not establish remediation of all findings. Current Debian security records do not provide Bookworm fixed versions for all seven; Trixie also remains affected by several of them. A tag refresh or unversioned `apt-get upgrade` cannot therefore be represented as a complete fix.

For zlib, the [Debian tracker](https://security-tracker.debian.org/tracker/CVE-2026-85091) marks Bookworm vulnerable, while its description and upstream discussion identify a narrower introduced range beginning at 1.3.1.2. This applicability discrepancy needs a reviewed disposition; it does not permit silently clearing the recorded scan finding. The upstream patch is `df84af25dc1942490e1d1c899a07619152a46148`. Alpine 3.24's [zlib package recipe](https://github.com/alpinelinux/aports/blob/3.24-stable/main/zlib/APKBUILD) explicitly applies that patch in `1.3.2-r1`.

No mixed Debian-release packages, unreviewed source backports, package-database removal or scan suppression are proposed.

| --- | --- | --- |
| Patched digest in the current Node 22 / Bookworm family | Lowest runtime change. The actual build already pulled the recorded digest; its affected package versions are independently verified. No current Bookworm fixed package set covering all seven was found. | Prefer this path when verified fixes exist; no patched digest is attested now. Rebuilding the same family is not demonstrated remediation. |
| Targeted Bookworm package upgrade | Keeps glibc, Node and application dependencies. Would upgrade only installed affected packages, with advisory-backed minimum versions. Current repository/security records supply no complete fixed set. | No invented package floors or speculative upgrade patch. |
| Node 22 / Trixie base | Retains glibc but changes Debian release and system libraries. Debian classifies only 53613/53615 fixed; four util-linux findings and zlib remain unresolved. | Not a seven-finding solution; no Trixie switch proposed. |
| Existing Node 22 / Alpine 3.24 candidate | Removes the inherited util-linux family by using a different OS base and requires patched zlib. Changes libc and native engine/binding selection. Official AMD64 musl Node support is experimental. | Reviewable fallback only. This branch prepares its source gates; it does not authorize or recommend automatic migration. |

The current distro is not intrinsically incapable of a future fix: supported backports or a patched base could resolve it. The conclusion is narrower: **no currently verified Bookworm package/digest update resolves the original seven-HIGH subset**. The full 11-finding release disposition is separate and remains held. A custom backport would introduce a new package-maintenance and provenance burden and was not substituted for a supported update.

## Existing Alpine candidate and the actual follow-up

PR48 already added `apps/api/Dockerfile.alpine-amd64-qualification`, and it is included in frozen source 504. It pins official Node `22.23.3-alpine3.24` AMD64 child `sha256:2c752226d477b4a886378baa95b9af252be59301b725fdb0b7e15208131505a8`. Its public base package inventory contains no util-linux family, but contains zlib `1.3.2-r0`. **The base alone is insufficient:** the existing recipe's `zlib>=1.3.2-r1` requirement in both build and runtime is necessary. Do not duplicate that Dockerfile or claim a newly implemented fix.

Node maintainers classify AMD64 musl builds as [experimental](https://github.com/nodejs/docker-node#musl-builds-for-alpine). Moving from glibc to musl requires the retained native-module and full-startup checks; a distribution package fix is not application compatibility evidence.

The concrete ABI implications are:

- Node stays **22.23.3 on AMD64**. JavaScript behavior and Node-API version compatibility do not make glibc-linked native binaries loadable by musl. Both build and fresh production dependency stages must use the same pinned Alpine base as runtime; no GNU dependency store is reused.
- Prisma remains **5.22.0**. The image-local target changes from the canonical schema's explicit ARM64 GNU target to **`linux-musl-openssl-3.0.x`** for this AMD64 candidate, while `native` is generated inside Alpine. The canonical schema/models are unchanged. The real Rust engine, OpenSSL 3 detection, zlib/libgcc dependencies and query behavior require Linux image evidence; Windows source formatting proves only schema bytes.
- Any installed Canvas, esbuild, Sharp/libvips, LibSQL, SWC or other native owner must match AMD64/musl, its exact locked package and active loader resolution. Packages outside the declared production graph require actual absence evidence, not guessed optional-dependency pruning. Retained byte/owner and real-operation probes stay mandatory.
- The existing recipe's derived-owner repair is restricted to byte-identical pinned artifacts; it does not authorize substituting arbitrary binaries. A clean scan cannot waive its admission failures.
- The real entrypoint and compiled Nest application must complete full startup, health and shutdown against an approved isolated fixture. The included unreachable-DB probe covers only that boundary. Existing native auth, Meri behavior and serving configuration require separate qualification before any rollout.
