# Core saved-history selected-client owner source

Status: unmounted source leaf and batch composition, based on backend PR96 `784b1c3a91eb6d78f16d92c42e71f05c12c5b5bb`. No route, migration, role grant, or runtime activation. Meri PR181 is `a50ce248337f3ce1ab7103e045bb8ab826ca92dc` and still uses sequential currentness; its whole-page retention fence stays in place.

`assertSelectedClientHistoryReleaseWithinTx` accepts the caller's transaction and refuses every subject unless it names one active conversation owned by the authenticated tenant/actor, one nonarchived selected client, and exactly one matching `client` scope. It locks owned conversations, clients, then required actor wall grants in sorted order with explicit tenant/actor predicates. It returns nothing: a later subject failure cannot yield a partial receipt. It refuses prospect and research-portfolio metadata because those owners have additional mutable facts and their current methods open independent transactions. Other scope kinds and clientless conversations also refuse. The scope's `policyRevision` is Meri-owned and opaque to this Core leaf; it cannot serve as Core authorization.

The composition owner must start one tenant-scoped `REPEATABLE READ` transaction, establish and lock local membership/impersonation facts in that same transaction, run this leaf, and then perform a **new** online Clerk observation while locks remain held. It must compare the principal and identity revision with the initial identity, enforce receipt expiry, and return a receipt only after commit. A separate transaction or earlier cached Clerk observation does not close the race. Core cannot make Clerk and PostgreSQL jointly atomic or prove the response bytes represented by the Meri-supplied digest.

`createHistoryReleaseBatchPort` now composes that order for source tests with a mandatory `HistoryReleaseNativeIdentityOwner` interface. It rejects impersonation and nonexact/non-Bearer targets, calls the selected-client leaf in one bounded `REPEATABLE READ` tenant transaction, and returns the decision only when the transaction commits. **The current middleware does not implement the required original-provenance row-lock and same-transaction fresh-online identity methods, so there is no production native owner and no route using this port.** A previous exploratory middleware change was reverted additively: `tenant-context.middleware.ts` explicitly requires Neo's prior approval for Clerk/tenant middleware edits. Its existing `readApplicationAuthority()` opens a separate local transaction and cannot serve as the final check under the batch locks. For the first slice the future approved owner must lock the original user, tenant and exact selected membership, reject impersonation, make a new online Clerk observation, then compare its locked local identity facts and original revision on the same transaction. An implicit current membership lookup or cached online session is insufficient.

Meri must keep the whole-page retention fence, derive the complete ordered subjects from the filtered response (including cursor-visible identifiers), freeze and hash exact response bytes, make one final Core batch call, verify the receipt, then publish the frozen bytes synchronously. The native bearer relay and special-scope owner adapters remain unresolved. No release should be enabled on this leaf alone.

Meri PR181's `nextBefore` may name a row later removed by retention filtering. That cursor must be included in the verified response subject projection or withheld before final release. Meri also needs its final release call after product HTTP membership recheck, exact response-byte freeze, receipt validation and native bearer relay qualification. None of those receiving changes is implemented by this Core source branch.
