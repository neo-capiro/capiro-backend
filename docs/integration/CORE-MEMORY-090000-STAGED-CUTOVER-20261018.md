Historical PR86/content-free bytes have a different checksum; no target's applied checksum or table shape has been read back in this packet.
- The current Prisma `ClioMeriMemorySubmission` model and `MeriMemoryReceivingService.submit` omit `candidate` on insert. On the original `020000` table shape, a new memory review submission fails its `NOT NULL` constraint. Existing receipt rows can contain the entire submitted candidate. A later deleted `memory_candidate` row may leave that receipt as the only surviving copy, so the existence of a review owner is not proof that the receipt payload can be discarded.
- `MemoryPurgeService` previously assumed the receipt had no candidate payload and retained submission rows while deleting client `memory_candidate` rows. A legacy non-null receipt can therefore retain client payload after purge. Stage 1 deliberately preserves those rows. Client purge execution must remain **held whenever the legacy receipt column exists, even if a point-in-time count is zero**, until Stage 2 or a separately reviewed, race-safe client inventory and purge correction is installed and read back. Do not claim right-to-be-forgotten completion from Stage 1.
- The `migrate` entrypoint runs `prisma migrate deploy`; the `serve` entrypoint starts `dist/main.js` separately. The old built source's `090000` hold does not directly prevent process startup, but blocks normal migration-before-rollout for the whole Core schema. This successor removes that unconditional hold from source; a wrong ledger or schema shape still fails closed. Starting the API without a qualified migration leaves the memory write mismatch and other unverified schema dependencies. It is not a supported cutover.
- The old built `090000` transaction raises before its column drop. The new Stage 1 file contains no column or constraint drop. A failed, applied or manually resolved target ledger must be inspected, not assumed clean from either source text.

## Stage 1 — preserve payloads and make new writes compatible

This source cut replaces the **presumed unapplied** held `090000` contents with a guarded, transactional compatibility migration. Its guard requires a finished original `020000` checksum (Git LF `090b3140…` or the exact LF-to-CRLF transformation `d7077202…`, both reproduced by the focused source test), the exact seven original column names/types/nullability/defaults including `candidate JSONB NOT NULL`, only the five original validated constraints with the original candidate and SHA check expressions, the one original unconditional immutable trigger with matching function source, and the one original public, permissive RLS policy with matching USING and WITH CHECK expressions. It also rejects table inheritance, partitions and temporary or unlogged variants; Stage 0 independently verifies the target definitions. The trigger's `tgtype = 19` corresponds to the original `BEFORE UPDATE FOR EACH ROW` definition (row bit 1 + before bit 2 + update bit 16). The object-check guard normalizes PostgreSQL's deparsed parentheses, spacing and identifier quotes, then admits only the original `jsonb_typeof(candidate) = 'object'` expression, with or without its inferred text cast. An unfamiliar deparse or different ledger/schema stops before the sole DDL statement; the explicit guard uses SQLSTATE `55000`, while a missing table or lock timeout can fail earlier. A synthetic local rehearsal passed; compatibility with each actual target remains unproven. It then runs `ALTER TABLE public."clio_meri_memory_submissions" ALTER COLUMN "candidate" DROP NOT NULL`. The JSONB column, object check, all existing values, receipt IDs/hashes/review IDs, immutability trigger, RLS and grants remain. PostgreSQL's `CHECK (jsonb_typeof(candidate) = 'object')` accepts `NULL`, so the current Core insert can omit the column and old non-null JSONB rows remain unchanged. This is **not** a content-erasure migration. Source acquires `ACCESS EXCLUSIVE` before catalog checks and holds it through `ALTER TABLE` and commit, closing the schema-change race; review a low-traffic window. It bounds `lock_timeout` to five seconds and the statement to thirty seconds. A timeout rolls back the transaction and requires ledger inspection before any retry. Static source tests validate original migration bytes, guards and absence of destructive DDL; the isolated local rehearsal below ran only against synthetic data.

The nullable physical `candidate` column is deliberately absent from the current Prisma model during this transition. Record that temporary model/database difference in the release ledger; do not let a generated Prisma diff or development migration silently turn it into a column drop. Stage 2 is the only authorized path to remove it.

Do not edit the original `020000` bytes.
