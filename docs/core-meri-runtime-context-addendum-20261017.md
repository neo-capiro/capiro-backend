## Placement decision and the source that must change

Neo's current direction is to place separately isolated Meri control, poller, runner, Temporal, and model-proxy services in the **existing `capiro-dev` VPC** (`vpc-0ac26cfac7ed972be`, account `967807252336`, `us-east-1`), using distinct service roles, security groups, private ingress, and ownership boundaries. Reuse the selected Aurora cluster where its PostgreSQL version, logical stores, grants, backup, and restore behavior are proved compatible. **A new VPC is not a prerequisite.** This is a placement decision, not an assertion that Meri services, network rules, or SQL already exist.

The [dated Meri product change set](https://github.com/neo-capiro/meri-greenfield/blob/72fe5aec1d955e1675e58493365009be15d97e49/infra/product-preview/CAPIRO-DEV-CHANGE-SET-20261016.md) and [Temporal deployment plan](https://github.com/neo-capiro/meri-greenfield/blob/72fe5aec1d955e1675e58493365009be15d97e49/infra/product-preview/temporal-deployment.md) still require a separate Temporal VPC/cluster. Their placement requirement is superseded by Neo's current direction; the checked-in templates **must be revised and reviewed** for same-VPC isolation before any change set. Do not apply them as written or infer that existing application SG access is sufficient. The Core preview already uses private `capiro-dev` subnets and the selected Aurora PostgreSQL 16.11 writer; reuse means new Meri-specific schema/role/network proof, not reuse of Core's application role for Temporal.

Temporal server source pins 1.32.1 and proposed persistence schemas `temporal` 1.19 / `temporal_visibility` 1.14. Their compatibility with this Aurora target, schema ownership and migrations, TLS, backup/restore, namespace and queue, issuer/JWKS, token renewal, and failover/replay remain unverified. Product source currently holds the Temporal join. A separate qualification VPC/build bucket/ECR and roles exist from earlier Meri image work; this decision concerns the **unstarted product/Temporal service placement**, not deletion of those historical resources.

The `/dev` path is an AWS reference namespace, **not a Clerk application identity**. Metadata does not reveal a matching application ID or key fingerprint.

PR60's original preview proposal targeted Test `*.clerk.accounts.dev` and `/capiro/preview/clerk/*`, creating a real source/config mismatch with Core. PR64 conditionally corrects the frontend source to the Core issuer and existing dev references, but has no accepted successor image or proof that the two configured secret payloads belong to that application. In the frontend owner's [read-only Dashboard note, PR71 `a841d5aa8f683c8f1497685c1a6d96f3afe577a6`](https://github.com/neo-capiro/capiro-frontend/blob/a841d5aa8f683c8f1497685c1a6d96f3afe577a6/docs/non-meri-continuation-20261016/CLERK-PRODUCTION-DOMAIN-READBACK-20261017.md), checked on **2026-10-17 during approximately 03:04–03:18 UTC**, the **Capiro Production** instance lists verified primary domain `app.capiro.ai`, verified Frontend API DNS name `clerk.app`, and a `capiro` JWT template. Together these establish its `https://clerk.app.capiro.ai` issuer domain and template presence only. The frontend owner will ask an authorized Clerk/AWS holder to compare the two configured publishable/secret values privately with that Production instance's API keys and return **both-match yes/no**, without publishing values, fingerprints, tokens, cookies, or private IDs. Until that result, configured Core issuer and observed Dashboard domain must not be treated as proof of the deployed key pair.

Core's [native authority verifier at PR48](https://github.com/neo-capiro/capiro-backend/blob/6542f5b089656b6d255465edd464d06c2a0b408f/apps/api/src/auth/clerk.service.ts) requires `sid`, `sub`, unexpired `exp`, and a live Clerk session lookup for `/identity`, `/membership`, and `/context`. Bootstrap and other frontend operations retain their existing custom token path and still need actual route acceptance proof. Neither a listed template nor a native token source edit proves an active `capiro-internal` tenant/member, actor, selected client, or Core/Meri identity join. After separately authorized service activation, an authorized server-side holder must check the native route statuses and current membership/context privately, publishing only sanitized pass/fail/source/time receipts. No bearer or user/client ID belongs in Git.

The frontend `0.1.8` is a **consumer distribution**; Meri's producer package remains `0.1.7`, while its private initial-input protocol is `0.1.8`. The [Meri handoff's exact schema comparison](https://github.com/neo-capiro/meri-greenfield/blob/72fe5aec1d955e1675e58493365009be15d97e49/docs/handover/20261017/fable-shipping/MERI-CONTRACT-COMPATIBILITY.md) found no wire mismatch.
