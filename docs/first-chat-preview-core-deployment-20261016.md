The PR #43 image boots the full API module, which otherwise defaults to running background work. The task explicitly sets Engagement to shadow with background owner and external actions disabled, callbacks and Recall webhooks false, both client profile fill workers false, and the Meri job sweeper, research portfolio delivery, and newsletter send flags false. Do not activate if that unrelated read is prohibited; a separately pinned route-only image would then be required.

## Ordinary first-chat authority contract

`POST /api/clio/conversations/bootstrap` accepts the native Clerk bearer and `{ "schemaVersion": 1, "requestId": "<stable UUID per New Chat intent>", "clientId": "<UUID>" }`. It returns HTTP 200 `{ "schemaVersion": 1, "requestId", "conversationId", "tenantId", "actorId", "clientId" }`. Core atomically binds `(tenantId, actorId, requestId)` to one active owned conversation and exact client. An exact replay returns the same `conversationId`; request ID reuse with another client conflicts, and a replay after conversation/client currentness is lost refuses without reallocating. This is the [PR #43 source contract](./first-chat-core-bootstrap-contract-20261016.md); it does not depend on Objective JWT.

Meri's configured native Core origin uses POST `/api/clio/application-authority/identity`, `/context`, and `/membership`. Its initial-run journal checks identity and context before/after admission, and its session and history gates recheck membership and conversation currentness. All three calls must use this preview origin together. The frontend's `GET /api/me`, `GET /api/clients` and `GET /api/clients/{id}` can continue through ordinary `CORE_API_BASE_URL` only while both Core services use the same database and Clerk tenant, as this proposal does. Meri's `/api/conversations/*` history routes are local to Meri.
