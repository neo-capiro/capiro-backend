## Authority and side effects to accept explicitly

PR #48's full `serve` AppModule applies [TenantContextMiddleware](../apps/api/src/tenant/tenant-context.middleware.ts) to all three GETs. It verifies a native Clerk bearer, chooses an active local tenant membership, cross-checks present tenant/org/slug claims, and honors the frontend gateway's fixed `X-Capiro-Tenant: capiro-internal`. `ClientsController` requires at least `standard_user`; client queries explicitly filter tenant ID because the deployed `capiro_app` writer role can bypass table RLS through its owner-role membership. There is no actor-specific client assignment check in these GETs. Core's separate `/context` remains the stronger conversation-admission authority. Confirm the chosen initial client is active and visible to the designated actor before enabling the frontend binding.

These GETs have ordinary API side effects **before** the handler: on a missing user the middleware can create a User or rebind an email-matched User to a Clerk ID; it can self-heal a missing tenant membership from verified org claims; it best-effort updates `user.lastSeenAt` on every allowed call; denied calls can append a tenant audit row. The ordinary path does not require the isolated `111f` service's online active-session recheck, does not test an existing membership's tenant `status === active`, and permits `capiro_admin` impersonation when a valid impersonation session and header are supplied. The frontend gateway rejects browser-supplied tenant/impersonation/override headers and sends only its fixed tenant hint, but a public ALB GET route can be called directly. A host+method+path rule alone does not pin `capiro-internal`: any otherwise authorized tenant member can call those same three GETs for their own tenant, and an authorized admin's impersonation can change the resolved tenant. This is not a demonstrated cross-tenant leak; it is a difference from the isolated internal-tenant contract.

PR #48's `GET /me` and clients handlers do not themselves set `Cache-Control: no-store`; the frontend proxy uses `cache: no-store` upstream and `private, no-store` downstream. The old `111f` bootstrap sets `no-store` on every response and uses an effective SELECT-only database identity. PR #48's writer-capable role and middleware behavior are compatible only if the owners accept these ordinary API semantics for the preview GET lane. The top-of-file change-control note in `TenantContextMiddleware` requires explicit Neo approval before editing authentication, tenant resolution, JWT/session handling, or webhook paths. This proposal changes none of those source files.
