## Actual composition and construction

`apps/api/src/main.ts` disables persisted Meri policy-pack enforcement at module load, validates Engagement runtime env before Nest construction, creates `AppModule`, configures HTTP/raw-body behavior and shutdown hooks, then listens. A non-listening check should mirror its preflight and HTTP configuration with `NestFactory.create(AppModule)` and `app.init()`, and close in `finally`. It must not import `main.ts` merely to get its bootstrap function, because that file invokes `bootstrap()` at load. The non-listening check is an HTTP application initialization check, not proof of `listen`, container command, serving image or live health.

`AppModule` directly imports `EngagementModule`, `EngagementWorkersModule`, `MeriModule`, `MeriMobileModule`, `CapiroAdminModule` and `WorkspaceAssistantModule`. The actual Engagement module registers `RAW_ENGAGEMENT_SERVICE` using the published `EngagementService` class, with a governed wrapper under the public token. Its factories also create guarded Google/Microsoft sync, OAuth, token, Gmail, Notetaker and AI providers. The Meri module registers actual raw Meri/MeriTools classes and governed wrappers; its funding-assessment factory installs collaborators and a lazy provider callback. Keep these real modules and business classes; an opaque Engagement token or omitted module would test a different graph.

The published EngagementService constructor reads configuration, constructs an S3 client, and gives EvidenceSourceService an attachment reader callback. It does not itself implement a Nest lifecycle hook or perform a direct network request in the inspected constructor. DirectoryService likewise constructs an S3 client; ClerkService constructs the Clerk SDK client; Workspace collaboration and newsletter email owners construct SES clients. Construction of an SDK client is separate from authorization to use the network. AnalyticsDbService constructs its separate Prisma client lazily on an operation, not on Nest initialization. The Meri module's assessment callback contains an Anthropic `fetch` but is installed lazily, not called by the factory. These claims concern inspected constructors/factories; instrumentation of the full import/init path must still catch any other eager side effect.

## Minimum synthetic environment and bounds

`ConfigModule.forRoot` does not specify `ignoreEnvFile`, so launch from an isolated empty cwd and supply an explicit scrubbed process env; do not read a repository `.env`. For a production-like `NODE_ENV=development` fixture, the validator requires synthetic `DATABASE_URL`, `CLERK_SECRET_KEY`, `CLERK_WEBHOOK_SIGNING_SECRET` and `CLERK_JWT_ISSUER` (the issuer check is bypassed only for `NODE_ENV=test`). Provide syntactically valid, nonsecret, unreachable placeholders; use `AWS_EC2_METADATA_DISABLED=true`, a synthetic `DIRECTORY_S3_BUCKET`, no provider/API keys, no OTel endpoint, and the inert controls in the table. Independently deny DNS, sockets, HTTP/fetch, provider SDK and DB calls before importing the app. Keep the actual business classes, guards, controllers, factories and module metadata. `NODE_ENV=test` is a legitimate narrower fixture but disables fill hooks and must not be labeled a production-default startup.

On completion, report exact emitted/source closure, successful real `AppModule` import/DI construction, HTTP `init()`, expected Directory prewarm denial, zero actual egress/database writes/provider calls, observed timers and shutdown cleanup. Failure to hydrate an exact emitted dependency or a denied unexpected I/O call is a failed/held startup result, not a pass. Native DB/RLS, live image/start command, externally reachable health, provider execution and runtime retirement remain separate gates.
