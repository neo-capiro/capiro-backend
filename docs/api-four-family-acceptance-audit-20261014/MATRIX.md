Existing `packages/shared/src/client-objective-destination.ts` and Objective service 57 delegate current Objective revision authority, while each resource owner verifies its current same-client authority. Workspace service 93 uses the exact saved version as `workspace_saved_revision`. Their receipts are read-only resolution observations; they do not implement durable work creation/association. Strategy and Planner retain their existing distinct owner guards; the Strategy planner rollout does not automatically gate Planner. Those separate contracts are not prerequisites for basic Objective CRUD or a basic preview. `docs/portfolio-31/objectives-contract.md:54` explicitly leaves activation/orchestration and additional lifecycle semantics to separate contracts.

The smallest useful feature-completion lane is to qualify the **already implemented Core Objectives** family on the selected current entrypoint and its schema, with one disposable same-tenant client, existing authorization and creation/version/recovery semantics. Ordered-owner qualification can follow with its coordinated legacy writer. Only a reproduced current failure should trigger implementation. Calendar needs controlled authoritative evidence qualification; saved staging needs the existing Engagement API owner and state admission and remains outside the initial live check. This audit recommends no duplicated controller, new store, revived commitment semantics or whole-source substitution. The migration-name handoff can be corrected independently.
