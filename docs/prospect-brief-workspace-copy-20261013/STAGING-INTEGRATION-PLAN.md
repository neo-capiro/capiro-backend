## Automation and Neo's manual work

Use distinct non-production tenants and actors for automation and Neo whenever supported. Automation gets only synthetic clients/prospects/drafts and request IDs recorded in its own run manifest. Neo gets a separate manual tenant/client/prospect/draft scope and keeps ownership of all manual changes. If resources share a verified non-production database, the two manifests and tenant boundaries must still be distinct and every cleanup action must name exact automation-created IDs and expected ownership.

Automation cleanup must not reset a shared database, seed a whole tenant, delete by display-name prefix, sweep all drafts/versions, or alter Neo's manual IDs. Preserve failed/replayed/conflicted request receipts needed for review. A retry verifies current scope and receipt first; a missing destination after cleanup is unavailable and is never silently recreated as Neo's resource. Cleanup plans name only automation-owned objects and the exact run manifest; cleanup must be reviewed and authorized separately from these source checks.

Write E2E opens only after shipping publishes the backend/Meri/database/auth isolation proof and approvals for the necessary resource/config changes. Until then, the local synthetic command/rollback/concurrency tests continue, and Neo's preview can be treated only according to the separately verified read-only scope. No production write or customer-data fallback is authorized by the frontend hostname.
