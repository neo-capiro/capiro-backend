# Prospect Contacts and explicit client carry-over

The existing registered ProspectContactsModule owns Contacts under `/api/business-development/prospects/:prospectId/contacts`. The existing role and Business Development guards remain mandatory, with current Core prospect/member/client/wall authorization inside each transaction.

Root allocated the accepted Contacts DDL to the active forward migration `20281024120000_portfolio_prospect_contacts`. Its statements are byte-identical to the accepted reserved source; only explanatory comments changed. It requires the existing Phase 4 `business_development_prospects(tenant_id,id)` unique key and Core tenant/RLS foundations. The superseded reserved SQL and unallocated proposal have been removed. Historical migration inventories remain historical evidence. Root must reconcile actual migration history/catalog and snapshot before deployment; no shared database was changed by source promotion.

Contacts GET is paginated by UUID, with at most 50 rows and a next cursor. POST consumes a prospect-scoped request UUID. PATCH and DELETE require an exact positive integer version; removal is soft and increments the version. Converted or archived sources remain readable with current authority but reject ordinary contact writes. Source contacts remain firm-owned; no automatic copy, email, hierarchy merge, or client sharing occurs on conversion.

After a completed conversion, an explicit POST to `contacts/transfers` accepts one reviewed batch of 1–50 distinct source IDs/versions and a create, link, or skip decision for each. It binds the current linked client and reviewed prospect timestamp. Create uses the canonical ClientPeople transaction helper and title placement. Link requires an explicit person ID, updatedAt, and exact normalized name/title/email/phone/notes tuple. Existing target fields and all source contacts remain unchanged. Conversion remains independent.

The contact mutations, audit and immutable actor/request transfer outcome commit together. `GET contacts/transfers/:requestId` recovers the historical completed/refused result under current authority. Same request with another manifest conflicts. Unknown infrastructure/commit failures are not presented as proof of no effect. Transfer history uses forward migration `20281024110000_portfolio_contact_transfer`; it has no source-contact FK, so applying the receipt table before the Contacts prerequisite is safe. Both migrations must be applied before the transfer route is used.

Focused current authority and registered HTTP coverage is in `prospect-contacts.integration.spec.ts` and `prospect-contact-transfer*.spec.ts`. Actual Prisma/capiro_app concurrency, transaction, revocation and migration coverage is in `test/a2-postgres/prospect-contact-transfer.pg.spec.ts`, which now applies the active forward migration. Local source qualification does not establish deployed acceptance; paired frontend review/recovery and root-owned actual PostgreSQL qualification remain tracked separately.
