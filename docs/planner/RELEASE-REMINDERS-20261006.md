# Planner date rules and Capiro notifications

Live and verified on October 6, 2026 (final checks October 7 UTC). The owner approved Planner updates and reminders in Capiro's main notification bell, alongside Planner Inbox. No other integration or authentication change is included. Strategies revision 38 and web-vNext revision 446 are stable with one desired/running task each and completed rollouts.

The bell merges an authorized Planner feed with the existing Workspace, committee/hearing and Business Development sources. Its unread count is calculated before limiting rows, using current project/task grants. Revoked rows cannot inflate the badge or crowd out visible work. Read-one and read-all share durable state and React Query invalidation with Planner Inbox; read persistence precedes navigation. IDs are namespaced, failures are isolated, and Planner makes no bell requests during Admin impersonation or without a signed-in organization. Routes derive from typed Planner identities.

Project rules support approaching/overdue triggers, bounded calendar-day/hour/minute offsets, existing conditions/actions, and optional reminders. Project date rules operate on unfinished top-level tasks. Personal My Tasks date rules operate only on the configuring owner's assigned work, can change private sections and send a reminder, and preserve shared task/project data and versions. Calendar-day offsets preserve local wall-clock time across daylight-saving changes; date-only work approaches at midnight and becomes overdue after its due day ends. Unset time zones use UTC. Approaching rules catch up after their threshold while the task is still due; overdue rules catch up after their threshold. A zero-offset trigger whose threshold equals the deadline catches up at the first available poll after that instant, instead of requiring an exact timestamp match. Zero-offset reminders say "Task is due." Each semantic rule configuration and due schedule executes once.

The Strategies scheduler polls every 60 seconds, discovers only active canonical membership tenant IDs through the existing system lookup policy, then leaves that transaction. Every Planner query and mutation uses `withTenant` and the tenant advisory lock. It scans bounded pages (20 tenants, 50 eligible tasks per tenant), resumes cursors, and isolates failures per tenant/task. Current active authors, project grants, recipients, assignment and sections are rechecked. A claim, task action or private move, recurrence copy and notification delivery commit together; failures roll everything back. The scheduler is independent of Meri/Watcher switches and can be stopped with `PLANNER_SCHEDULER_ENABLED=false`.

The additive seventh Planner migration creates append-only execution receipts with compound tenant/resource/task references, forced tenant RLS with no bypass branch, an immutable trigger and SELECT/INSERT-only runtime privileges. Semantic configuration/due keys survive restarts and manual saves. Scheduled completion uses the same approval/recurrence persistence as manual completion; hidden descendants roll back the receipt and completion.
