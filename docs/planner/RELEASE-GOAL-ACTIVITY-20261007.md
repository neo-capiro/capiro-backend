# Planner goal updates, history and reminders

Goal status posts, progress history and reminders extend the existing Planner goals on the Strategies API. This release is being qualified; production promotion and live checks are pending. The full Asana work-parity goal remains active.

Goal editors can post named status updates with formatted, named sections, a status or closing outcome, and a manual progress value. Automatic progress remains derived from connected work. Posts and their progress snapshots are immutable; ordinary comments support the existing append-only corrections. Expected versions protect drafts from competing writes. The responsible owner can configure reminders in the same transaction as a status post or separately. Viewers can follow a goal they can already read, without gaining new access. Creator, responsible owner and followers receive others' posts and comments in Planner Inbox and Capiro's notification bell only while active and currently authorized. Bell links open the goal. Other access members opt in by following.

Progress history captures the original value, starting value, target, units, status and measurement. Task completion/intake, project archive/access changes, goal edits and parent rollups append changed snapshots without a notification for every data point. A historical number is withheld unless the current viewer can read every captured contributing goal, project and selected task. Source IDs remain private authorization metadata. Authored update text remains available to current goal readers. The history graph leaves gaps for withheld values and paginates older entries with the activity stream; it shows loaded entries rather than inventing a complete history for older goals.

Manual and numeric-total measurements now support signed starting values and increasing or decreasing targets, including reduction toward zero. Percentage is the distance covered from start toward target, clamped to zero through 100. Existing zero-start increasing goals retain their behavior. Automatic percentage modes keep zero-start increasing progress.

Owners can set weekly, every-two-weeks, monthly or quarterly reminders with a first date, local time and time zone. Month-end recurrence clamps each occurrence to the last valid day without drifting; existing daylight-saving scheduling handles gaps and folds. Only the latest due occurrence is delivered after downtime. A closing reminder arrives one week before an explicit custom due date at 09:00 in the goal's time zone. Freeform time-period labels are not parsed as deadlines. Closed or archived goals pause reminders. Inactive owners or owners without current edit access receive no reminder. Ownership transfer clears the former owner's cadence. Stable, owner-specific immutable receipts commit with the event and Inbox row, protecting concurrent cycles, retries and restarts from duplicates.

Shared, Strategies and web production builds pass. Exact-source ARM64 builds are pending final confirmation.

All eight additive Planner migrations applied to a fresh disposable PostgreSQL database with inherited broad legacy grants. Catalog assertions pass for nine forced-RLS tables, four immutable streams, tenant-only receipt policy, restricted application grants and the receipt foreign key tied to the same goal/event. The eighth migration adds a nullable goal reference and JSON details to existing events and an immutable goal reminder receipt table. Existing task/project activity is preserved.

Local browser checks verified a decreasing incidents goal moving from 70 of a 100 start toward zero (30%) to 20 (80%), a structured status post, historical values, monthly reminders retaining a native 09:25 UTC input, and an edited comment. Production migration, runtime-role verification and private live QA are pending.

## Promotion / recovery

Capture the current serving Strategies and web-vNext definitions before promotion. Clone them changing only immutable image references and release identifiers. Run the additive migration under the existing DDL task before the new API, then prove forced row security and privileges under the actual non-superuser, non-BYPASSRLS application role. Do not deploy Compute/CDK/IAM, canonical API, shared authentication or routing changes.

An old serving API can read existing task/project events after the additive schema change. New goal JSON carries fields an older strict API cannot edit; retain a compatible API or prefer a forward fix after creating richer goals. Keep immutable history and delivery receipts for recovery; do not drop or rewrite them. Synthetic live QA must remain private to the signed-in user and be recoverably archived with its Inbox rows.
