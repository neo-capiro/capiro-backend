# Canonical Objective reservation: source-only transaction slice

This slice starts from reviewed local `8d4aa29decf86cb242f2f8de0faebe546d8b64ae`. The proposed composite and workload contracts remain unfrozen. A newly confirmed ready revision now reserves private canonical IDs in the same Core transaction as its revision and intent. The public confirmation response is unchanged. The publication fence is unregistered; no worker, dispatcher or product-publication consumer is added.

## Intended transaction boundary

`confirm_ready` creates its actual revision, locks current authority for that actual revision, appends its actual inert work intent, and reserves canonical IDs within the existing Core transaction. Any failure aborts all three with the Objective update. An already-ready no-op remains inert; this slice does not backfill historical Objectives. Reconfirmation of a newer saved ready revision keeps the reserved Strategy/project IDs and initial epoch, advancing only requested intent/source and binding version. The same intent is idempotent; conflicting same/older intent fails.

Reserved UUIDs identify future canonical targets. They prove no Strategy/project row, applied publication, completed operation, public locator, current availability or execution authority. Routine regeneration will retain these IDs; explicit replacement is a future, separately allocated operation. Manual projects, multiple groups, shared task memberships and empty manual Strategy edits are unaffected.

## Fence and lock order

`requireCanonicalObjectiveFence` is a transaction-local precondition for future publication owners. It calls the existing shared Core Objective authority helper with the current native actor and Clerk subject; validates the current ready Objective and actual immutable ready revision/intent witness; then locks and compares the exact canonical reservation. It must be called inside the same short transaction that writes the future product output and publication receipt. It grants no workload identity, operation, run, deadline, continuation, cancellation or retained-result authority.

Publication fence order is current tenant/member/user/client authority, memory-wall access if required, Objective, immutable intent/revision witness, canonical reservation. The existing authority helper holds SHARE row locks on authority and Objective. Confirmation already owns its Objective UPDATE before creating the revision; it then acquires current authority SHARE locks before intent/reservation. These authority SHARE locks are mutually compatible between the two paths. Avoid adding an old-revision Objective SHARE preflight followed by UPDATE: concurrent confirmations would introduce a lock-upgrade cycle. Never acquire the reservation lock before Objective. No network/context/model work belongs inside this span. A consumer's existing job claim lock may precede the authority sequence only after its complete lock order is reviewed. Deadlocks or stronger-isolation serialization failures must abort the whole transaction; native concurrency is unqualified.

The application has SELECT/INSERT-only access to existing work intents; do not use intent `FOR UPDATE` or `FOR SHARE`, which would require UPDATE privileges. The locked parent Objective blocks its edit/delete and cascading intent deletion. Existing application intent mutation is disallowed. Privileged administrative/bypass mutation is outside this application immutability assumption. Cancellation needs a separately allocated mutable authority owner and reconciled lock order.

The migration adds no GRANT, role or default privilege expansion. The new migration revokes unnecessary direct DELETE on this table; it changes no existing intent grants. The scoped FK needs one redundant work-intent scope unique constraint. Reserved IDs cannot FK to output rows that do not exist. Existing applied output/receipt rows are untouched; advancing requested revisions cannot rewrite them. Future mutable publication/stage journal, cancellation and replacement remain separate allocations.
