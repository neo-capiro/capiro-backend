# Meri Phase 3: next dark `run_analysis` readiness package

Date: 2026-09-25. Design and acceptance gate only; no runtime implementation, tests, deployment, or JEV activation is claimed by this note.

## Source boundary

The current internal proof recomputes a fingerprint of the exact final provider-facing tool schemas, binds a nonce and chat/research surface to the authenticated tenant/user and persisted conversation/client, and reports permission for three fixed client tools plus an offered `run_analysis` row. All rows still say `runtimeAvailability: unresolved`, `eligibility: unresolved`, and `executable: false` (`apps/api/src/meri/meri-tool-availability-proof.{contract,service}.ts`). The orchestrator verifies the fixed policy digests, scope, fingerprint, row order, and proof age, under literal opt-in `MERI_TOOL_AVAILABILITY_PROOF_SHADOW=true`; its private proof request has a one-second timeout (`apps/meriv2-orchestrator/src/meri/meriv3/{api-tool-availability-proof.repo,meriv3-assistant.service}.ts`). The proof never filters the provider tool list.

`analysisSandboxEnabled()` requires the global switch, URL, nonblank API bearer token, and tenant feature gate before `run_analysis` is offered or invoked (`apps/api/src/meri/meri-tools.service.ts`). These are configuration prerequisites. The sandbox's unauthenticated `/healthz` is process liveness; `/run` requires a matching bearer, can reject a full queue, and can fail at Python spawn or import (`apps/clio-sandbox/src/{server,run}.ts`). A ready result at one instant neither reserves later capacity nor authorizes a later invocation.

## Smallest source package

1. Add a bearer-authenticated, bounded, fixed-code sandbox self-test that passes through the same queue admission and Python image path as `/run`, verifies the libraries `run_analysis` needs, and returns only a versioned readiness outcome and observation time. It must reject a missing/wrong bearer and must not accept caller-provided Python, datasets, or arbitrary tool names. Keep `/healthz` out of the readiness decision. The API samples this independently of the one-second turn proof exchange and retains only a short-lived observation; absence, expiry, cancellation, authentication failure, queue refusal, timeout, spawn failure, or import failure is unresolved/unready. A probe may consume capacity, so bound and rate-limit sampling.
2. Add a separately versioned, API-owned per-offered evidence envelope to the internal proof. Every row follows the exact final provider schema order and is bound to the existing nonce, scope, schema version/fingerprint, policy digest, and check time. Preserve the existing three client permission checks and the distinct `run_analysis` permission check, including clientless conversations. Only an offered `run_analysis` row may carry the authenticated fresh sandbox observation. All other native and managed tools retain `permission: unknown` unless a reviewed server-owned check exists, and `runtime: unresolved` unless they have a capability-specific probe. Denied or unknown permission cannot be promoted by positive runtime evidence. The orchestrator must pin and validate the new version/digest, row names/order, provenance, and freshness; malformed or mismatched evidence fails closed in the diagnostic only.
3. Keep the new observation diagnostic: no offered-schema filtering, JEV candidate construction, tool execution, approval bypass, or `executable: true`. Keep the current Phase 3 and JEV gates off. Runtime invocation must continue to recheck current tenant/client policy and its own sandbox gate; a future executable route would additionally require a reviewed invocation-time readiness/capacity policy.

Do not infer offered skills from the shared skill registry or Quick Action telemetry. The browser submits the starter prompt as turn text and sends `skillId` separately to fail-open telemetry (`apps/web/src/components/chat/MeriWorkspaceConversation.tsx`); the relationship recipe planner does not receive the skill ID (`apps/meriv2-orchestrator/src/meri/meriv3/meriv3-retrieval-recipes.ts`). A later package needs a server-attested, exact turn-bound offered-skill set and per-skill scope/entitlement/recipe checks. Until then every skill remains unknown and outside JEV candidates.

## Minimum authored tests after the RAM hold

- Sandbox: missing/wrong bearer; `/healthz` success with unusable `/run`; full queue; cancelled/timed-out probe; missing Python or required import; fixed-code-only request; bounded response and no secret or arbitrary code exposure.
- API proof: no observation, stale/future observation, wrong protocol or failed probe, unoffered `run_analysis`, permission denial despite a ready observation, clientless allowed analysis versus three client-only `needs_input` rows, and changed persisted owner/client/wall. Reordered or substituted final schemas, nonce, surface, and digest must not validate.
- Orchestrator: new envelope version/digest and exact row-order verification; reject forged ready, stale, wrong-scope, or executable claims. With the shadow flag off, assert zero new probe/proof calls and unchanged provider schemas, tool dispatch, and model-visible behavior. With it on, probe/proof failure logs a bounded diagnostic and leaves the turn's tool list unchanged.

Focused Jest, API/orchestrator typecheck and build, sandbox image/auth/queue/library checks, persisted ordinary-user permission checks, and coordinated API/orchestrator source compatibility remain unrun under the host RAM hold. A deployed fresh observation still requires live validation and cannot certify subsequent call success. The actual **JEV executable subset is empty**: `capability_routing` is `lifecycle: inactive` with `maxRolloutMode: off` (`packages/meriv2-core/src/jev/task-registry.ts`); no JEV selection is wired to this proof; most tool permissions and all turn-bound skill identities remain unresolved; readiness is at most transient; and invocation-time authorization, protected routing evaluation, and calibration have not qualified activation.
