# Phase 4 worker-progress publication fence — source-only follow-up

The run repository now offers `publishWorkerProgressIfLive`. Its Postgres implementation locks the Meri run row in a tenant transaction, checks the consumer lease and the committed Stop marker, then commits one nonterminal worker status, its event, an approval interaction when present, and `output`/`outputSeq` when applicable in that same transaction. An eventless nonterminal text snapshot uses the same guard. Stop's status/timestamp write takes the same row lock: progress that commits first is durably sequenced before Stop, while Stop that commits first refuses the later progress write. A worker `run.stopping` event commits its own `cancelling` status under that lock; a subsequent worker frame is refused. The in-memory repository mirrors this ordering without an `await` between its check and mutations. A refused write leaves the adapter's local output unchanged. Same-replica listeners are notified after the progress transaction commits, but concurrent postcommit callback timing is not itself an ordering guarantee; durable sequence replay remains authoritative.

A repeated `approval.requested` for the same run/request ID is an explicit idempotent no-op under the run lock: the original interaction prompt and expiry remain, and no second public event, status, or output write occurs. The adapter does not advance its local output for this `duplicate` result. This only deduplicates the native approval request receipt; it does not settle approval resolution or worker-side effects.

This is only a worker-progress fence. The consumer still persists usage before reaching this guard, so that write can race Stop. An `approval.requested` interaction is now coupled to its public event, but approval resolution/resume remains separate. The terminal wire-event branch is unchanged and still appends before `finalize`; the finalizer can also fall back to the worker's terminal output when its stored output is empty. Neither terminal publication nor public terminal-body semantics are qualified by this change. Stop's `cancelling` event is still appended in a separate transaction after its marker, so this package alone does not prove a fully ordered public Stop receipt. Steer, broker effects, and uncertain `createRun` acceptance remain separate gaps. Explicit Stop does not change the conversation's Hermes session key, binding, or epoch.

Focused in-memory and real-local-Postgres regressions were authored for status/event and approval-interaction atomicity, duplicate approval no-op and original prompt/expiry retention, worker stopping, event/output atomicity, eventless text, Stop-first refusal, and concurrent Stop/progress ordering. They have not been run under the current test hold; no typecheck, build, database, Docker, browser, or live acceptance is claimed. Phase 4 remains off and unqualified.
