# Phase 3 API sandbox-readiness observer: source-only gate

Date: 2026-09-25. This records an authored, dark API package, not runtime acceptance.

The API now has a process-local `MeriAnalysisSandboxReadinessObserver`. It is off unless the literal `MERI_ANALYSIS_SANDBOX_READINESS_OBSERVER_SHADOW=true` is parsed by the API config, the existing analysis sandbox switch is on, and a URL and nonblank bearer are configured. With it off, no readiness timer or HTTP request is created. The existing permission proof marks demand only after an exact final-provider-schema `run_analysis` offer has been matched to an *eligible* server-owned permission check. That mark schedules the fixed-code `POST /readiness` request no sooner than 1.1 seconds later; the one-second internal proof call never awaits the sandbox. Per API process, probes do not overlap and start at most once per 30 seconds while recent eligible offers continue. The bearer is read at request time and is not stored or logged by the observer. Redirects are rejected.

The observer accepts only an HTTP 200 JSON receipt with exactly the four sandbox v1 fields, protocol version 1, `ready: true`, an allowed `fresh`/`coalesced`/`cached` source, a canonical ISO timestamp at most 30 seconds old and at most 5 seconds in the future, and a body no larger than 512 bytes. Authentication failures, refusal/HTTP 503, timeout, cancellation, redirects, malformed or oversized bodies, stale/future timestamps, and protocol mismatches yield no positive observation. A new probe clears an earlier positive observation; stale observations are dropped on read. This is a momentary process/import result, not capacity reservation, tenant authorization, or executable eligibility.

The v3 permission proof and v2 offered-diagnostic payloads, schema fingerprint, policy hashes, provider tool list, and invocation path are unchanged. In particular, `runtimeAvailability` and `eligibility` remain `unresolved` and `executable` remains `false` for every row. The observer's positive receipt is **not** returned in the proof yet. A next paired API/orchestrator package must version a separate evidence envelope, bind it to the existing nonce/scope/final-schema fingerprint/policy/check time, and pin/validate its exact row order, provenance, and freshness on the orchestrator before this result can become a verified diagnostic. It still must not filter provider tools or activate JEV. A future executable route would require a reviewed invocation-time readiness/capacity policy and new acceptance evidence.

Focused Jest specs were authored for strict receipt validation, default-off behavior, bounded bearer request, failure/refusal handling, single-flight invalidation, and the eligible-offer mark, but were **not run** under the host RAM hold. API typecheck/build, sandbox image/auth/queue/import checks, paired envelope validation, persisted ordinary-user permission checks, and deployed `os.capiro.ai` QA remain open. The separate active `/run` redirect boundary was hardened at `dd58e49e0`; its authored regression spec likewise remains unrun.
