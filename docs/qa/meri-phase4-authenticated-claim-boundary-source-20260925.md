# Phase 4 authenticated claim boundary — source only

Date: 2026-09-25. This package adds a dormant `MeriHermesDispatchClaimBoundaryV2` and changes the dormant intent repository's `claim` API. It is not registered in a Nest module, controller, runtime client, provider, or worker overlay. No tests, typecheck, build, migration, Docker, browser, network, provider, or Hermes action ran. Authored specs and static assertions are unexecuted.

## Security and race invariants

- The separately supplied dispatch-gate service secret is an explicit constructor dependency, at least 32 printable ASCII bytes. Its SHA-256 digest is compared with a fixed-length constant-time comparison before any tenant transaction. It is not `INTERNAL_SERVICE_SECRET` or the broker signing key; deployment must provision it independently. All service-secret failures return the same content-free V2 rejection.
- The untrusted tenant ID selects only a tenant-scoped transaction. Tenant/run UUIDs and request SHA-256 are shape-checked before DB access. The repository locks source and intent rows, then calls mandatory authentication before digest, state, or already-claimed status branches. The authentication callback receives a frozen copy of immutable identity only. No identity or row status is returned until the run-bound bearer verifies against that exact identity.
- The bearer resolver supplies API-owned keys; the boundary copies the key registry and key bytes before verification. It samples `clock_timestamp()` as Unix microseconds in the claim transaction after locks, then calls `verifyMeriDispatchGateBearerV1`. The bearer's exclusive `notAfterEpochMicros` is validated as a positive signed BIGINT deadline no later than the identity claim cutoff. The repository evaluates a fresh DB clock before any digest/state branch, including claimed-row status-only, and both conditional transition writes separately evaluate another fresh DB clock against the deadline. A late second write throws, rolling back the first worker-ID bind.
- Every claim attempt, including an already-claimed status-only replay, must supply the exact copied body bytes, copied `X-Hermes-Session-Key`, copied `Idempotency-Key`, and an API-owned copy of the session HMAC key selected by the stored key ID. `matchesMeriDispatchReceivedRequestV2` requires the exact idempotency header and committed body/session material. Only a prepared transition reaches the mandatory current-authority port, which must lock/check live membership and role, client/mailbox grants and revocations, conversation/session epoch, Stop, worker ingress/generation/credential, and route closure in the same transaction. A false decision rejects; a callback error produces content-free `UNKNOWN/commit_unconfirmed`.
- The repository atomically conditionally binds the proposed worker run ID and changes the intent from prepared to claimed. `launchAuthorized: true` is returned only for a newly committed transition. An exact same-ID duplicate is `status_only` with `launchAuthorized: false`; a different ID rejects. Every result is V2, content-free, and contains no identity, bearer, body, header, key, or worker run ID.

The active bearer is required for status-only claims too. At or after its exclusive expiry, neither claim nor status-only is available through this boundary. Post-expiry recovery needs a distinct future purpose-bound policy; this package does not create one.

## Residual blockers

P1: The current-authority verifier is a required port without a concrete transactional implementation. No worker ingress invokes the boundary before Hermes effects. The route, deployment identity, secret/key provisioning, all-ingress no-bypass proof, atomic Stop/revocation fences, and lost-response recovery remain open. A source-only unit spec cannot prove rollback or race behavior against migrated Postgres.

P2: Key rotation/retention, cross-language golden vectors for body/session/idempotency material and bearer claims, pinned worker-image qualification, and guarded integration evidence remain open.
