# Meri Phase 4 unknown-acceptance protocol gate

Date: 2026-09-25. This is a source-level design and acceptance boundary, not an implemented protocol, test result, deployment approval, or claim that a worker run was stopped. Keep Phase 4 planner-only.

## Why the current path is unsafe to expose

`meri-hermes-runtime.adapter.ts` still calls the legacy worker `createRun`. Its timeout/error path can finalize dispatch as failed without knowing whether the worker accepted; a later Stop may then return early because the API row is already terminal. On a still-live row with no worker ID, Stop can instead treat it as never admitted. The later known-ID compensation only helps if the API actually receives an ID. The worker's local SQLite idempotency store, including its EFS-backed deployment, does not establish a linearizable cross-host Meri admission fence; its in-memory fallback and finite retention cannot prove absence. A parked Postgres intent prototype is not wired to message/run creation or the worker ingress. These observations do not say a production run is currently exposed; the feature remains off.

## Versioned no-copy admission contract to implement

1. **Authority and identity.** API Postgres is the sole admission/seal authority for a Meri Phase 4 POST. Commit one immutable `prepared` intent, user message, and API run in one transaction *before* outbound delivery. Bind a versioned canonical-byte digest of the full authenticated outbound request: body, session header/key identity without storing a raw secret, tenant/actor/scope, conversation epoch, worker generation, authorization policy/grant version, tool-view/catalog digest, model, instructions, expiry, and run/idempotency key. Define canonicalization, digest algorithm, DB-clock cutoffs, signature/key rotation, and immutable constraints. Do not reconstruct or resend a lost request; a retry is status-only.
2. **Mandatory pre-effect gate.** Every possible receiver and ingress generation must authenticate the request and obtain a private API claim *before* session creation, provider/agent work, budget reservation, broker call, or any other mutation. The receiver proposes a stable worker run ID and recomputed full-request digest. A single transaction locks the intent, API run, conversation/scope, and the authoritative authorization fence shared with grant revocation; it checks Stop, current grants, generation, expiry, epoch, and digest, then binds that ID and seals `claimed`. An exact duplicate may read the committed outcome but cannot launch again; a different ID/digest fails. A timed-out/ambiguous gate response never grants work; the receiver may only reread status.
3. **Competing Stop/absence.** Stop and reconciliation use the same conflict domain. They may seal a still-`prepared` intent as `sealed_absent` only when all reachable worker versions/ingresses are proven to require the gate and delayed delivery is expired or ingress irreversibly closed. A delayed POST then cannot claim. If a claim won, Stop uses the durable ID and requires an acknowledged terminal worker outcome. If the transaction or read is uncertain, report `UNKNOWN` and retry observation; neither claimant nor stopper may infer which side lost.
4. **Separate facts.** `claimed` means admission authorization, not launch, execution, completion, or absence of effects. Track those independently. A worker crash after claim is known-ID/unknown-execution; a lost worker 202 is recovered from the Postgres claim record. No status replay may relaunch without a separately proven single-launch/idempotent recovery protocol. Do not let the current short pending-run reconciliation or 24-hour sweep turn an unresolved case into a false terminal success/failure.
5. **Generation and retention.** Reject stale generations at ingress; revoke old credentials/routes, drain or neutralize in-flight old receivers, and keep an auditable proof that none can bypass the claim gate. Retain the intent, claim/absence seal, run identity, effect ledger, and deduplication tombstones longer than the maximum delayed-delivery, retry, credential-validity, and recovery horizon. If that horizon cannot be bounded or receivers cannot be enumerated, leave absence `UNKNOWN` and do not activate.

## Separate broker-effect contract

Admission alone does not fence later effects. Every broker invocation needs a stable operation ID plus semantic digest and a durable result/uncertain ledger. Postgres domain effects, budget reservation, and audit/event recording must commit under the same run/Stop and authorization/revocation locks; Stop-first denies and effect-first precedes Stop. A grant revoked after admission must block subsequent effects if that is the promised policy. External S3/provider actions cannot be atomically committed with Postgres: stage privately, use provider idempotency where available, make publication conditional, reconcile crash/partition outcomes, and report `effect_uncertain` rather than claiming denial or exactly-once. Exclude native worker side effects until an equivalent fence is proven.

## Source-only sequence and acceptance

First implement the versioned state/wire contract and rework the parked Postgres intent migration/repository **without runtime wiring**: full-request identity, atomic prepared admission, `claimed` and `sealed_absent` transitions, transaction-uncertainty handling, retention/tombstone policy, and explicit `UNKNOWN`. Replace the active adapter's ambiguous-error terminal finalization and null-worker-ID Stop terminalization; prevent ordinary terminalization and TTL cleanup from closing an unresolved intent. A prepared/unknown intent cannot be publicly reported stopped until an authoritative `sealed_absent` outcome or acknowledged worker termination. Author rollback-only Postgres race/crash specs and worker-overlay contract/guard specs. The existing parked repository's `claimAndSeal` for a known proposed ID is not this protocol.

Only after private worker authentication, every receiver/ingress gate, shared revocation-writer lock, old-image cutover proof, and retention policy exist should a default-off claim endpoint and pre-execution worker guard be wired. Then test exact same/different concurrent POSTs across two worker hosts and API replicas, lost 202 and claim responses, Stop-first/claim-first, worker/API crash at each boundary, grant deletion, stale generation, mixed old/new ingress during cutover, DB outage, delayed delivery past expiry, sweep and purge/tombstones. Verify no native session/status mutation before claim. Separately test broker Stop/revocation races and external-action uncertainty. All of that requires exact-HEAD Jest/typecheck, isolated migrated-DB and pinned-worker contracts when the resource hold is lifted. No design review or source-only patch qualifies runtime exposure.
