# Phase 4 worker-status Stop monotonicity — superseded source-only slice

This was the first source-only, default-off Phase 4 slice: a standalone repository compare-and-swap replacing the consume loop's worker-status read-then-update. It is now **superseded** by `publishWorkerProgressIfLive` (see the [follow-up](meri-phase4-worker-progress-fence-source-20260925.md)). The standalone `updateWorkerStatusIfLive` method and call were removed because committing a status separately from its worker event could leave an incoherent receipt on Stop or crash. The revised provisional source path holds the Stop run-row lock while committing the nonterminal status, approval interaction when present, event and output snapshot together. It refuses a committed Stop or already-cancelling pre-state; terminal or lost-lease cases retain the consumer-fence exception. A worker `run.stopping` frame may publish its own `cancelling` status event once without an API Stop marker, and a later nonterminal worker frame cannot reopen it.

Focused store and migrated local-Postgres race specs were revised for the combined publication. Under the user resource instruction, neither they nor typechecks/builds/migrations were executed; only static review and `git diff --check` apply. This is not local acceptance.

The result remains deliberately narrow. Worker usage persistence still precedes the combined progress fence; dispatch binding with a late worker ID, approval-resume status, broker mutations, and terminal success after a committed Stop remain unresolved. A Stop request is not proof of worker termination. The full Stop/effect protocol and exact migrated concurrency tests in the [boundary audit](../../../outputs/meri-capability-jev-plan/PHASE4_BROKER_STOP_EFFECT_BOUNDARY_20260925.md) remain required before Phase 4 executable exposure or any release. No live QA or deployment occurred.
