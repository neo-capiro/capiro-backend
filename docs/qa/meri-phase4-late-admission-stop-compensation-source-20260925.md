# Phase 4 known-ID late admission/Stop compensation (source only)

This bounded package addresses only a live API process that **receives** a Hermes `createRun` acceptance after a Meri Stop. It is not the durable unknown-acceptance or effect-fencing protocol. `bindAcceptedRunIfLive` records the returned worker run ID under the same run-row lock as Stop. If the run is still live it commits running status and its internal event together; if Stop or terminal state won, it preserves the cancelled state, retains the worker ID, requests an idempotent worker Stop, and skips session binding and consumption. A failed compensation request logs both IDs and leaves an internal failure signal; it is not counted as a confirmed stop. The adapter persists the known ID before an optional session-status poll and uses the fresh binding/Stop result, not a stale caller snapshot.

For an accepted worker that remains live, the session-binding step now locks and re-reads the run and conversation rows and compares the current session epoch with the key used for the worker POST. A Stop committed before that write prevents a late metadata bind. An epoch change requests worker Stop and ends the turn conservatively as interrupted rather than consuming a worker on an old transcript. A Stop after binding already has the durable worker ID and the consumer continues to reconcile the cancelling run. This narrow guard does not assert that every concurrent revocation outcome wins a preferred terminal reason.

Focused cross-replica and repository regressions are authored for Stop-first/bind-first ordering, duplicate acceptance, failed worker-stop request, Stop during the optional status poll, and epoch change during that poll. Independent static review found no remaining P1/P2 in this five-file slice; `git diff --check` passed. **Jest, typecheck, build, migrated DB, worker image, provider, browser and live QA were not run** under the user's RAM hold. This is not a Phase 4 acceptance or deployment.

Still open: an API crash or lost acceptance response before the worker ID is durably bound cannot identify or stop that worker. A best-effort stop failure has no bounded maintenance retry/acknowledgment yet. Immediate worker effects between acceptance and compensation are not fenced. A protected exact-body outbox with authenticated worker replay/lookup or a separately reviewed cross-host reservation/seal protocol remains necessary, alongside broker-effect receipts, permission/catalog parity, a new pinned worker contract and final `https://os.capiro.ai` QA. Keep the broad tool view dark.
