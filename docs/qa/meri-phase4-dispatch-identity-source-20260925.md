Date: 2026-09-25. This is an unrun source-only slice, not acceptance, deployment permission, or a working admission gate. Phase 4 remains planner-only.

## Provenance and current path

At this checkout, `apps/api/src/meri/hermes/meri-hermes-runtime.adapter.ts` still invokes the legacy `runtime.createRun` directly. Its ambiguous exception path writes `dispatchStatus: 'failed'` and finalizes; Stop with no known Hermes ID can finalize as never admitted. The current schema has `MeriAgentRun` and `MeriExecutionScope` but no dispatch-intent model/migration/repository. A prior dormant prototype exists in Git objects `c981b6c69` and `3d8425a81` (migration `20280920060000_meri_phase4_dispatch_intent` and `meri-hermes-dispatch-intent.repository.ts`), but neither is in this checkout. That prototype bound selected semantic hashes and used `prepared -> sealed`; it lacked exact full-request bytes/session-header identity, `sealed_absent`, an authoritative unknown outcome, and the required all-ingress pre-effect gate. It must not be cherry-picked as a safety fix.

## What this slice adds

`meri-hermes-dispatch-intent.contract.ts` is not imported into runtime. Identity version 2 is intentionally restricted to the current `actorType: user`, Meri `audience: private`, and exact canonical `tenant:<tenantId>:user:<actorId>` execution scope. It binds the exact outbound `/v1/runs` body bytes; exact `Idempotency-Key` value; a keyed identity of the exact `X-Hermes-Session-Key` value; tenant, actor, client, workspace, scope, conversation, message, and run; the envelope's actual `authorizationVersion` separately from policy/grant labels; worker audience/ingress/generation/credential ID; catalog/tool-view digests; exact source-message/assembly digests; and claim/delivery/credential/reconciliation/retention horizons. `conversationEpoch` maps to the active conversation metadata's `sessionEpoch`: the required header is `<scopeId>:conversation:<conversationId>[:eN]` for epoch `N > 0`. The future gate must derive this from the authoritative conversation row using the active `sessionKeyFor` logic, not trust a caller's epoch. The actual `Idempotency-Key` must be compared to the persisted API run key; no old `meri:<userMessageId>` formula is assumed. The v2 migration explicitly blocks any dormant v1 row pending exact reconciliation rather than reinterpreting it.

Fixed-order, length-prefixed UTF-8 frames and domain separation determine the SHA-256 request digest. The body and session key are transient inputs; only digests and key IDs are returned. The private API gate must choose a **dedicated, versioned HMAC key** (not the worker bearer) by trusted key ID, recompute from received bytes/header, and compare the complete identity; the worker must not hold the HMAC key or choose authoritative tenant/grant facts. The API must hash the same immutable byte buffer it actually sends. The pure contract requires reconciliation at least 24 hours beyond both the delivery and worker-credential cutoffs, retention at least another 24 hours beyond reconciliation, and positive canonical Unix microseconds within signed-int64 range. These are minimum shape constraints, **not proof** that delayed delivery, old credentials, crash recovery, or tombstone purge are actually bounded to those horizons. PostgreSQL timestamp representability and DB-clock cutoffs still need migration checks.

The contract also defines mutually exclusive `prepared`, `claimed` (stable worker ID), and `sealed_absent` (absence evidence digest) durable shapes. `UNKNOWN` is a separate epistemic observation for an unconfirmed commit/read/gate response or unproven absence; no timeout mutates the durable state to `UNKNOWN`. A duplicate `claimed` observation is status-only, never a second launch grant. An observed `prepared` row requires an authoritative transaction; the pure helper cannot grant work. Authored specs cover exact bytes, header and context binding, retention shape, malformed states, and unknown/duplicate disposition. **No specs were executed** under the user’s resource hold.

## Required next protocol work before any exposure

1. Design a new migration/repository against the current schema. Insert the prepared intent, user message, and API run atomically before any POST. Store only digest/key IDs, immutable identity and cutoffs. Use DB clock for claim/absence expiry, reject updates outside `prepared -> claimed` or `prepared -> sealed_absent`, and preserve tombstones past a **proven** maximum delivery/credential/recovery horizon. A hash of absence evidence is not proof by itself. Make HMAC key-ID rotation immutable for each prepared intent and retain old verification keys through the complete reconciliation horizon.
2. Parse the immutable outbound body bytes to the expected `input`, `session_id`, instructions, model/provider/options and tool-view semantics before sending; check they match the prepared user message, session ownership and authorized request snapshot. Send a signed or otherwise strongly authenticated scope/generation/identity sidecar to every worker ingress. At claim, derive worker audience, ingress, credential identity, current tenant/actor/workspace/scope, session owner, and grants from authenticated authoritative sources, not supplied strings. All reachable images/routes must call the gate before native session, provider, budget, broker or status mutation. An uncertain gate response gives no work permission.
3. In one shared conflict domain, lock the intent, run, conversation/current `sessionEpoch`, Stop marker, and every authorization/grant revocation writer fence; compare recomputed request digest and current generation, expiry, actual run idempotency key, envelope `authorizationVersion` and grants. Bind one proposed stable worker run ID on the winning claim. Exact duplicate reads status only; different ID/digest fails. A Stop-side absence seal is legal only after all old ingress bypasses are excluded and delayed delivery is expired or irreversibly closed. Otherwise return `UNKNOWN`, not stopped.
4. Replace the active adapter’s ambiguous-error terminalization, null-ID Stop finalization and ordinary pending-run TTL reconciliation. Separately fence broker/database and external effects; this identity contract alone says nothing about exactly-once execution or effect absence.
