# Phase 4 dispatch-gate bearer and received-request match — source only

Date: 2026-09-25. This package adds dormant pure contracts and authored specs. No controller, module, provider, worker ingress, or active runtime path imports the new bearer. No test, typecheck, build, migration, Docker, browser, provider, or Hermes action ran. This is not an admission gate or Phase 4 acceptance.

## Why the broker guard cannot be the pre-dispatch gate

`MeriHermesWorkerTokenGuard` calls `MeriHermesBrokerService.authorize()`, which requires `X-Meri-Hermes-Run-Id`, resolves the API run by the **Hermes worker run ID**, and checks the broker worker token and current run authorization. The API binds that worker ID only after `/v1/runs` returns. If the Hermes acceptance response is lost, Hermes may already have admitted the run while the API has no ID to resolve. Using this guard to authorize the worker's initial `/v1/runs` claim is circular: the guard needs a post-admission ID to grant pre-admission permission. The broker guard also runs on later tool calls, after native worker and provider work could already have occurred.

The new bearer names the preexisting API `runId` and exact V2 request digest. It has a separate `mdgb1` version, `meri-hermes-dispatch-gate` purpose, signing domain, key ID and explicit key-validity registry. Its HMAC key must be provisioned separately from both `MERI_HERMES_BROKER_SIGNING_KEY` and `INTERNAL_SERVICE_SECRET`; neither existing secret is a dispatch-gate signing key. It binds tenant, user actor, private scope, worker audience/ingress/generation/credential ID, and the envelope's exact `authorizationVersion`. Its exclusive expiration is capped by both the claim and worker-credential deadlines. The caller supplies trusted Unix-microsecond time; verification fails outside bearer or key windows. A valid bearer is authentication evidence only.

The received-request matcher checks the exact raw body length and SHA-256, requires the exact printable `Idempotency-Key`, and re-HMACs the exact `X-Hermes-Session-Key` under the existing V2 session-header domain and framing. The API must select this separate, >=32-byte session-header HMAC key by the validated identity's stored key ID. The worker never receives that key. Neither helper retains or logs raw content. The checks do not prove that the body semantics correspond to the persisted message, that the worker is the named ingress, or that a claim transaction won.

## Intended private gate and remaining work

The future private **claim** route must require the independent service-to-service secret **and** this run-bound bearer, then independently bind the authenticated worker audience, ingress, generation and credential to its deployed identity. It must load the immutable intent and API run by trusted API run ID, compare the exact received bytes/header, persisted idempotency key, tenant, actor and scope, and recheck live authorization, Stop, session epoch, grants, credential expiry and worker generation under a shared DB-clock transaction. The worker must call it before any Hermes session, idempotency, native, provider, budget, broker or status effect. Only a winning `prepared -> claimed` transaction can authorize one launch; bearer replay during its live window is not a second launch grant.

The claim bearer expires no later than the exclusive claim cutoff. It therefore must **not** authorize status or recovery after expiry. Ambiguous delivery and later reconciliation need a separate, purpose-bound recovery credential or policy operating within the committed reconciliation/retention horizons. A historical status observation is content-free and never launch permission; any resumed launch still requires a fresh current authorization transaction. The package does not implement that recovery path.

Next gates remain: claim route/controller integration with service-secret authentication, a distinct authenticated recovery/status policy, key provisioning/rotation and retention, all-ingress worker patch and no-bypass inventory, atomic claim/Stop/revocation fences, launch and terminal evidence, lost-response reconciliation, cross-language golden vectors, migrated Postgres races, pinned worker-image tests and final guarded QA. The authored specs cover deterministic claim material, tampering, malformed/unknown/duplicate payloads, noncanonical encoding, mismatched keys and identities, and exclusive time boundaries; they remain unexecuted under the resource hold. Residual P1: there is still no active pre-effect worker claim, and ambiguous acceptance/Stop remain unresolved. Residual P2: bearer and session-key key lifecycle plus cross-language vectors and race evidence have not been qualified.
