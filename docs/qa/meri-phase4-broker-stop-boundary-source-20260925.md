# Phase 4 broker Stop boundary — source-only follow-up

Date: 2026-09-25. This note covers the provisional source branch only. No Jest, typecheck, database, worker, browser, deployment or live QA ran for this change under the user's host-memory hold.

## Narrow correction

`requestStop()` persists `status: cancelling` and `stopRequestedAt` before it asks the worker to stop. `cancelling` is not a terminal run status. The broker previously rejected terminal statuses at entry and on read release, but admitted a committed Stop until finalization. `assertLiveAuthorization()` now returns the existing `409 run_not_live` shape when it sees either `cancelling` or a non-null `stopRequestedAt`. Both checks matter: an already-admitted operation can overwrite the nonterminal status, while the Stop timestamp remains. Explicit Stop already owns finalization; this branch does not initiate a second revocation fence.

Authored regressions cover entry with `cancelling` alone, entry with a persisted Stop timestamp after a nonterminal status overwrite, and a recall whose Stop commits while the read is in flight. The recall test keeps an independent entry snapshot so it only proves the release re-read if the run store changes. It also checks that no `memory.recalled` event was appended. These assertions are **not run** and do not count as package acceptance.

## What is not guaranteed

This guard denies calls whose entry read or read-release reread **observes** Stop. A call admitted before Stop can still queue in the DB governor, reserve budget, and perform an effect afterward. Stop can also land after a read's release check but before the response leaves the process. The current budget reservation has no Stop predicate; candidate save, attachment retry, artifact publication and clarification use separate effect writes. The governor's timeout races the promise but does not cancel underlying work. A nonterminal update can overwrite `cancelling` in both run repositories. Therefore this patch is not a no-post-Stop-effect guarantee and cannot qualify or enable Phase 4.

The sound next boundary is a row-locked run/effect transaction: Stop atomically marks the run and emits its event, and every broker DB effect locks the same row, checks Stop, version and current authorization, then reserves budget and commits its domain write/event in one transaction. Authorization and revocation must acquire their own relevant membership/grant locks in a consistent order; a mere read of those rows is not an atomic revocation fence. Nonterminal status rewrites after Stop must be refused. Expensive OCR and object upload cannot run while that transaction holds a lock; stage them, then publish only after a fresh fenced transaction. Object storage needs a private staging key, durable idempotent intent and orphan cleanup. That can ensure no **visible** artifact is published after Stop, not literally prevent an already-started remote upload from placing bytes after Stop.

Acceptance still needs deterministic Stop-first/effect-first cross-replica Postgres races for each broker path, staged-upload timeout/crash and orphan cleanup cases, monotonic Stop status, authenticated worker reconciliation, exact candidate/image checks and final guarded QA on `https://os.capiro.ai`. The separately authored live acceptance-bind slice remains unmerged because late accepted worker IDs and terminal receipts are unresolved. A create attempt with no observed worker ID can still have been accepted; it must remain explicitly unresolved rather than produce a public stopped receipt until authoritative worker status or a proven non-admission fence resolves it. No Phase 4 activation or release GO follows from this source repair.
