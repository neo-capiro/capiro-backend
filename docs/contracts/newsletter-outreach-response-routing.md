# Existing newsletter Outreach response routing

This contract reconciles the existing legacy producer and the frontend PR16 response boundary before dispatch implementation. It changes no wire version, request DTO, record kind, schema, persistence owner or endpoint. The immutable source evidence is [the exact metadata audit](../cleanup-outreach-metadata-retirement-contract-audit-20261012/NEWSLETTER-METADATA-CONTRACT.md). The frontend's current parser discards metadata; preserving these fields and qualifying dispatch remains the frontend owner's implementation work.

The existing producer's record type is `outbound_campaign`. Its reserved response metadata fields are optional `newsletterStageId`, an RFC-variant UUID of versions1–5 accepted by the current stage owner, and optional `newsletterRevision`, a positive safe integer snapshot provenance value. An absent/null metadata object or absent stage hint remains an ordinary record. Preserve the response schema's existing handling of unrelated fields; add no blanket metadata passthrough. Reject malformed reserved fields through the response contract rather than silently moving them into another workflow.

A valid stage hint together with `outbound_campaign` is only a routing candidate. Generic create/update requests already accept arbitrary metadata, so this marker is not an authenticated origin stamp or a tenant/client/owner/sender/approval grant. The frontend must resolve the existing record ID through the dedicated newsletter record owner. That owner reloads the actual stage and verifies current record-client access; the stage owner verifies tenant, Clerk owner and every source client. Delivery additionally checks current active membership and source-client grants. Retry or actor/tenant/client change requires the same current authority. Metadata revision never replaces the authoritative stage snapshot/revision.

Decoding or routing must not POST open, associate a new record, prepare, test, send, upload, reinvite, generate content or approve an action. Explicit current owner intent semantics continue to govern those operations. Dedicated rich-record GET results retain their existing shape; they are not generic `outreachRecord` results or OutreachV3 session receipts. Effectful review/account-status GET boundaries must remain intercepted in synthetic qualification.

The rich Workspace stage UUID identifies `WsNewsletterStage`. Saved newsletter staging separately identifies an exact `WsDocVersion` snapshot/hash and uses an authorized existing OutreachV3 session, expected state version and durable command receipt. UUID syntax creates no relationship between these resources. Do not infer, copy or convert IDs between their endpoints or automatically migrate either flow.

Before enabling dispatch, the frontend owner must retain ordinary records, legacy producer marker/revision and unrelated-field stripping, while refusing malformed markers and forged/stale/wrong-type/cross-owner/cross-tenant/cross-client/revoked hints through canonical intercepted owners. A saved document-version UUID masquerading as a stage must be refused. No decode/routing fixture may invoke an effectful collaborator. The packed existing `@capiro/shared/newsletter` and `@capiro/shared/newsletter-render` exports supply rich content types/rendering; they confer no authority.

This is the accepted receiving contract for the existing producer, supported by published source and four inert probes. It does not claim the frontend parser or dispatch has been implemented, real customer behavior has been observed, or native RLS/concurrency acceptance has passed. No live send/provider/upload, database/migration, main merge or deployment is authorized by this document.
