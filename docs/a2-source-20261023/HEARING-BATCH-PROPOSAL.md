# PF16 hearing batch prerequisite — source proposal, not implemented

The ordinary attachment command is not sufficient for hearing-backed documents. No hearing batch command, new grant, shared transaction participant or deployment capability is implemented or assumed by this proposal.

## Evidence

- Core `apps/api/src/engagement/hearing-record-document-access.ts` verifies the immutable attachment/brief binding and current Clerk owner, then calls Intel `internal/hearing-record-retrieval`. Its returned content/source hashes prove identity only. The HTTP response does not hold authority locks through a later Core write.
- Intel `HearingRecordWorkflowService.brief` reads encrypted brief state, checks folders/client, calls `run` for current source/observation state and checks latest series/review state. These are separate actor transactions. `run` can require `HearingPublicationService.retainedVersion`, which checks owner, recording policy, retained media permission, folders and evidence hashes. A content hash alone cannot replace those current checks.
- `HearingRecordsRepository` uses Intel's canonical `PrismaService`, not a separate source-data connection. Its `event`/`snapshot` read the same database interface as the private brief tables. The existing global `legiwatch-published-record-commit-v1` advisory barrier has a SQL writer trigger in Core migration `20280913013000_legiwatch_record_commit_boundary`; the record owner takes the shared barrier before event-specific locks.
- `infra/cdk/lib/preview/services-stack.ts` passes the same `DataStack` host/name and app credential reference to Core and Intel. That demonstrates intended shared database wiring, not actual deployed task, database-role or schema availability. Its secret injection includes DB and Clerk identities but neither `HEARING_ENCRYPTION_KEY` nor `NOTES_ENCRYPTION_KEY`. Historical dev/prod Intel task definitions inject a dedicated hearing key; those are not evidence for newstack.
- `HearingCryptoService` requires the dedicated hearing key or existing notes fallback to decrypt. The file owner cannot reconstruct or bypass the encrypted folder/observation context without it. No key values have been read.
- Current hearing `lockContext` locks membership before client; Core `requireOwnerClient` locks client before membership. Reusing both unchanged inside one transaction would introduce an inversion. Existing source/retention/folder locks must also remain effective through the batch commit.

## Smallest viable owner composition to allocate

Prefer the existing Intel hearing owner committing the **entire** mixed batch on the same database connection, using an extracted canonical file transaction kernel. This keeps hearing decryption and its current policy in the service that already owns them. It avoids granting the hearing key to Core. This is a proposed extraction and composition, not a claim that a shared library already exists.

1. Extract the ordinary SQL batch/receipt kernel from `apps/api/src/clients/client-file-batch.service.ts` into `packages/shared/src/client-file-batch.ts`, with deliberate export in `packages/shared/src/index.ts`. It receives the caller's transaction, current verified actor and a mandatory per-file policy callback; no connection opening, nested transaction, ambient authority or service requests inside the kernel. Both Core ordinary and Intel mixed batches use that same implementation and receipt table. Domain error translation stays at the application boundary. Parser/digest ownership must move once, not be duplicated.
2. Add `apps/intel-api/src/hearing/hearing-file-batch.service.ts` and focused tests, plus a narrow authenticated internal controller method in `hearing-record-retrieval.controller.ts`. Accept the same versioned command and trusted Core actor identity, then independently verify actor/tenant/client/attachment access in the transaction. Intel owns the outer transaction and commits every ordinary and hearing item plus one immutable receipt together. No grant token is returned for a later Core write.
3. Extract transaction-bound current document validation in `apps/intel-api/src/hearing/hearing-record-document-policy.ts`; refactor existing `hearing-record-workflow.service.ts` brief/run readers to call it. The existing `hearing-publication.service.ts` retained-observation readers and `sourcedata/hearing-records.repository.ts` snapshot/event readers need caller-transaction variants so no authority lock is released early. `tracker/reports/report.service.ts` feature/member checks need a fresh transaction-bound variant; do not use a cached flag as commit authority. Reuse existing folder policy and crypto, never copy a weaker policy into Core.
4. Reconcile the actual lock order in the existing hearing owner: source barrier, deterministic event locks, current client, membership/identity, wall grants, sorted folder/version rows, then retained session/permission/capture and selected attachment rows. Acquisition order must be checked against existing publication, review, correction and revocation writers before editing. All reads used by the policy must use the same transaction. Global source writer triggers and feature/permission expiry checks remain authoritative.
5. Core's existing batch route may delegate a hearing-containing command to that Intel owner before any mutation, using the existing internal service identity transport. No fallback to an ordinary commit on timeout/denial. The same request identity/digest and exact receipt remain end-to-end. Recovery must delegate current hearing authorization too; neither an old receipt nor a current file ACL alone authorizes it. Ordinary commands continue through the Core adapter.

The shared package/public export and Intel paths above require root allocation. Current A allocation covers neither the extraction nor the hearing policy changes. Product behavior remains all-or-none for the reviewed selection; this proposal does not reduce hearing scope or create a new user permission model.

## Capability evidence required before activation

Sanitized task-definition/service metadata must establish the actual Core/Intel image heads, matching database endpoint/name and app-role references, Intel hearing-key reference/version, internal service identity/origin binding and enabled existing feature flags. A disposable fixture must verify the app role's existing table rights/RLS and both schemas, without adding a runtime bypass or broader grants. Current source wiring alone proves none of these deployed capabilities. No AWS changes, secret-value reads or database execution were performed here.

Qualification must use actual PostgreSQL and both extracted production owners: mixed-batch rollback, changed folder membership/version, revoked client wall, changed source/current-series/review, expired/revoked retained permission, missing/wrong crypto, concurrent ordinary/hearing batches, request-ID digest conflict, lost receipt and current-authority recovery. A denied hearing item must disclose no inaccessible metadata and move no ordinary item.
