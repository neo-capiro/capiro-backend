# ST27: local organization name and manual Clerk synchronization

Neo's 23 October decision: save the organization name in Capiro first, show Clerk synchronization failures, and offer manual Retry. No automatic background retry or outbox. Base: `194c96c92199ed180a2715e6cd69bcaba70917cf`.

The existing tenant-admin PUT `/tenant-admin/branding` now commits its existing tenant write before invoking Clerk. Its existing response fields remain and `clerkSync` is additive. Omitted name does not contact Clerk; generic logo fields remain refused. A failed write/commit makes no provider call. A post-commit read failure cannot discard the local receipt. Before dispatch, the scoped current name/org must still match the saved row; a known superseded request is skipped.

POST `/tenant-admin/branding/sync` accepts no fields (absent body or empty object). It remains behind the same tenant context and administrator guard. It reads the active current tenant by the server context, chooses that row's current saved name and Clerk organization, and returns `{id, name, clerkSync}`. It never writes a tenant name and accepts no client-selected name, tenant or provider organization. The service additionally rejects nonadministrator retry contexts. Existing middleware owns session/membership/impersonation authority; this change adds no parallel authorization protocol.

`clerkSync` is one of `confirmed`, `failed`, `unknown`, `not_linked`, `superseded`, `not_requested`. `confirmed` means that this SDK response's organization id and name matched the attempted update. It is not a persistent provider-state record or a convergence guarantee. `failed` means the SDK rejected; this does not prove remote nonexecution. Timeout/mismatched response is `unknown`. Manual retry reads again at the time of the new request.

The five-second caller deadline bounds provider waiting after the database commit; it cannot cancel Clerk's existing SDK request. Late settlement is consumed without rewriting the receipt or scheduling another attempt. Concurrent/late provider writes can finish out of order. No background repair, cross-process lock, provider readback, outbox, SDK replacement, webhook, schema or migration is introduced. Each explicit action makes one SDK invocation; the installed SDK's existing transport behavior is unchanged. Diagnostics use only fixed event/status strings, never names, identities, raw errors or credentials.
