## 3. Open issues, in priority order

**P0. Client memory saves fail (regression from #1990, live in orchestrator139).**
- **Symptom:** in a client conversation, "Remember for this client that X" → `save_memory` → `400 input.clientId: is not an allowed property`. Meri honestly says it was not saved. Evidence: `OUT2/capiro-internal/case-13/attempt-3/stream-1.txt`.
- **Cause:** the orchestrator now adds `clientId` to `save_memory`. The API write-input validator `apps/api/src/meri/meri-write-tool-input.ts` (`validateMeriWriteToolInput`) rejects properties that are not in the tool schema. The `save_memory` schema in `apps/api/src/meri/meri-tools.service.ts` (around line 1542) has `content`, `key`, `scope` and `ttlDays`, but no `clientId`.
- **Fix options:**
  - (a) Add `clientId` to that schema, described as server-set. The orchestrator's `augmentToolInput` already overrides it with the conversation client and blocks a mismatched one.
  - (b) Let the validator accept a server-threaded `clientId` for `save_memory`.

  Prefer (a): one line, validation stays strict. Add an API spec, ship the API only, then rerun cases 13, 17 and 02.
- **Afterwards:** an admin's client-scoped save becomes a pending candidate that **someone else** must approve. The product forbids self-approval, and that behavior is correct.

**P1. Budget and bill answers carry no attached citation records** (cases 20–24, 28, 31, 32), even when correct. Check whether structured tool results (`get_pe_budget_timeline`, bill status) mint citations, and fix if it is a real gap.

**P1. Case 21 adds an irrelevant evidence-limitation line** ("A member vote must resolve to the actual roll call…") to a budget answer. A limitation template is attached to the wrong claim type.

**P1. Context bloat:** about 340K input tokens per turn (see §2).

**Releases** (CI is intentionally broken; never deploy through CI):
1. Build immutable images with `OUT/launch-capture-budget-removal-build-v1.mjs`. Set env `BUILD_SERVICE`, `BUILD_SOURCE_SHA` and `BUILD_ROOT` (phase scripts and `extra-markers.json`), then run `launch` and then `collect`.
2. Ship with a release kit, `OUT/release-<name>/{archive.py,qualify.py,baseline.py,verify.mjs,ship.sh}`. Each kit runs: evidence PR → `scripts/meri-release.mjs prepare/promote` (rollback kept) → wait for the old tasks → served verification.
3. Copy the newest kit: `release-memclient` for the orchestrator, or `release-setaside` for the API. Wrapper chains are `OUT/run-*-release.sh`.

`OUT = C:/dev/main/outputs/meri-c2-20261003`.

**Gotchas:**
- **`ship.sh` needs a clean worktree** for its evidence commit. Do not edit the repo during that step; stage changes in the scratchpad.
- **`collect` refuses to run once `build-readback.json` exists.** Skip it in that case.
- **Never put nested double quotes in a `-m` commit message.** An unquoted `<x>` becomes a shell redirect.
- **The API buildspec override has a 25,600-character limit.** It is currently about 24,300.
- **The Bash tool's heredocs break on apostrophes.** Write scripts to files instead.
- **Run the API `tsc` with `NODE_OPTIONS=--max-old-space-size=8192`.** Without it the process may crash with code 134.
- **Check deploy ancestry first.** The live commit must be an ancestor of the candidate (`git merge-base --is-ancestor`), and `GIT_SHA` and `RELEASE_SHA` must match the source (the kit verifies this).
