# Superseded Meri Hermes Phase 4 — retirement handoff

Status: source retirement verified; deployment isolation proposed, not yet merged; native MeriV3 release qualification remains open. This document closes the *old delivery project*, not the live Meri service, the native V3 improvement program, or a release acceptance gate. Snapshot: 2026-09-27 UTC. Refresh GitHub/AWS state before acting.

## Decision and scope

The Hermes-based Phase 4 broker effects, signer, migration chain, and runtime integration are **not prerequisites** for MeriV3. Native MeriV3 remains the supported implementation path. Preserve its existing Context Plane, approvals, governed memory, research, JEV, and evaluation components. Preserve the old project's useful requirements—truthful outcomes, authorized source receipts, durable effect identity, write approval and reconciliation—but implement them against current V3 authorities when a measured gap warrants it. Do not revive the retired runtime or its tables to make old branch code compile. An evidence receipt, an operation result, and a cryptographic attestation establish different facts; signing remains deferred.

## Native MeriV3 handoff

1. Deployment prerequisite: review and merge build-only isolation separately; design a controlled, explicitly approved immutable-digest promotion path. Before any promotion, bind candidate commit/build to ECR digest, verify retirement-compatible source and migration histories in fresh/upgrade disposable DBs, compare expected task definition/config and running digest at dispatch, check the public route, and document application rollback versus DB compatibility. Retire/reconcile mutable `:latest` only after consumers are inventoried. Do not infer deployment from image publication.
2. Release 0: keep the 26-case offline Promptfoo mechanism suite distinct from live model acceptance. The 75-case benchmark definition on `release/meri-v3-release0` and live harness on `feat/meri-live-eval-harness` are branch work—not an accepted 75-case authenticated result. Rebase selectively onto the safe main; verify fixtures, approved real prompts, and independent answer/tool/evidence/multi-turn thresholds before acceptance.
3. Release 1: reproduce and repair false successes, evidence receipts, document/transcript reads, memory isolation and older-fact recall, approvals, and applicable B1–B6 capability fixes in small slices.
4. Releases 2–3: bound retries/tool calls, give writes stable operation identity and reconciliation, preserve long-thread constraints, and qualify research reconnect/recovery without duplicate effects.
5. Release 4 of the *new* plan: calibrate JEV with human labels and improve answer usefulness; this is unrelated to declaring the *old* Phase 4 shipped.
6. Release 5 of the *new* plan: wire selective tools into the served V3 request-local path, test broad-versus-selected exposure and safety, then improve playbooks and observability. This absorbs the old project's useful product goal without reviving its implementation.

## Acceptance boundaries

- PASS: exact pre-merge source tree restored by the rollback; old Phase 4 broker/signing source is not on the audited main.
- PASS: read-only AWS check distinguished running Meri orchestrator digest from the newer mutable ECR tag and observed healthy orchestrator target at the snapshot.
- PROPOSED, NOT MERGED: build-only / generic-deploy-denial workflow patch on this branch. It does not qualify or promote any new image.
- NOT RUN: production-like database migration-ledger/permission read-back, fresh and upgrade rehearsals, final native V3 builds, authenticated Playwright, Promptfoo live and DeepEval thresholds, 75-case benchmark, image promotion/rollback drill, and post-merge runtime verification. No Phase 4 effect/signing acceptance can be inferred from the old branch's tests or receipt.
- BLOCKED for final deployment-safety closure: code review and authorized merge of the isolation change, reviewed manual digest-promotion process, migration compatibility and live acceptance against the precise candidate. Until then, do not characterize the live system or the full native MeriV3 plan as 'Phase 4 complete.'
