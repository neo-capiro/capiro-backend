## 11. Bot Mode / persistent specialists (`message_agent`, Bot Chat, hosted rooms, `hermes peer`)

### Evidence

### Config/env keys
- `agent.bot_mode_protocol` (default `True`, `hermes_cli/config_defaults.py:156`).
- `profile.yaml` -> `ui_meta: {hermes-bots: {...}}` (must be a mapping) marks a profile as Bot-Mode-managed (`tools/bot_mode_probe.py:96-104`).

### Reachable over POST /v1/runs (api_server platform)?
**Conditional.** `message_agent` is injected per turn by `agent/turn_context.py:958-964` regardless of platform, but only when `_session_title(agent) == "Bot Chat"` **and** `is_bot_mode_managed(home)` (`tools/bot_mode_dm.py:114-125`). A `/v1/runs` request whose `session_id` is the profile's session titled exactly "Bot Chat", on an install where some profile.yaml carries `ui_meta.hermes-bots`, gets the tool; any other session does not. `hermes peer run` is exactly this path (`peer.py:314-330`). The Bot Chat session can be created headlessly via `POST /api/sessions` (`peer.py:124`).

### Limitations
- The tool never appears in `/v1/toolsets` or any toolset (`bot_mode_dm.py:9-10`); it cannot be enabled via `toolsets`.
- Local delivery shells out to `hermes -p <name> chat ...` as a background terminal process; the reply comes back as a completion notification, not inline (`bot_mode_dm.py:5-14`).
- `find_canonical_live_owner` requires an active-session registry entry advertising capability; otherwise the legacy unowned CLI lane is used (`cron/scheduler_delivery.py:657`).
- Hosted-room authority takeover is "storage primitives only"; when takeover happens is caller policy (`hosted_room_replicas.py:7`).
- Profiles are the unit: the roster is "default + every dir under `<root>/profiles`" (`bot_mode_probe.py:71-74`); one canonical Bot Chat per profile (`run_turn.py:238-240`).

### Empirical test needed
- Whether a headless install with no Desktop and only a hand-written `profile.yaml` `ui_meta: {hermes-bots: {}}` yields the protocol section + tool on a `/v1/runs` Bot Chat turn (the gate only checks "is a dict"; an empty mapping was not exercised in tests read here).
- Whether the background-completion notification (reply to a DM) reaches an api_server run's event stream or only the originating session transcript.

## 12. Goals, heartbeat, cron, kanban — what process runs them and what wakes them

### Evidence
- **Goals (`/goal`)**: `gateway/run_goals.py:1-6,25-31` — `GatewayGoalsMixin` ("Goal/heartbeat continuation, post-turn hooks and loop-wakeup watcher methods for GatewayRunner"), bound onto `GatewayRunner`. `hermes_cli/config_defaults.py:1297-1304` — "persistent cross-turn /goal loop: after each turn an aux-model judge checks if the goal is satisfied, else a continuation prompt re-enters the session until done, budget exhausted, or paused. Judge failures fail OPEN; the budget is the backstop." `goals.max_turns: 20`. `:734` aux model slot `goal_judge`. `gateway/slash_commands_goals.py:1-2` — the entry points are gateway slash commands `/goal, /subgoal, /heartbeat, /loop, /refine, /review` bound via `GatewaySlashCommandsMixin`. `gateway/run_goals.py:58-75` — manager state is per session entry from `async_session_store.get_or_create_session(event.source)`. `gateway/run_turn.py:1793,3449` — post-turn hooks read the turn return value; pending text starting with "/" is treated as a slash command.
- **Loops (`/loop`)**: `hermes_cli/config_defaults.py:1305-1313` — `loops.min_interval_seconds: 30`, `loops.max_ticks: 100`, `loops.self_paced_floor_seconds: 60`, `loops.self_paced_ceiling_seconds: 900`. In-session re-run of a prompt on a cadence; self-paced backs off exponentially while replies stop changing.
- **Heartbeat (conversational)**: `gateway/run_goals.py:110-135` — `_register_heartbeat_watch` starts `_start_heartbeat_poller()`; `_heartbeat_poll_once(watch)` wakes each idle watched session once and leaves busy sessions unclaimed; `_heartbeat_poll_watch` re-resolves the current session id via `session_store.peek_session_id(quick_key)` and delivers through `_adapter_for_source(source)`. Related modules: `gateway/run_heartbeat_acceptance.py`, `gateway/run_heartbeat_restore.py` (restore watches after restart). All are methods of the gateway process.
- **Cron**: `cron/scheduler.py:1-3` — "tick() runs due jobs (gateway calls it every 60s from a background thread). A file lock (`~/.hermes/cron/.tick.lock`) keeps overlapping processes to one tick at a time." `cron/scheduler_provider.py:1-4` — `CronScheduler` provider interface (EXPERIMENTAL): providers decide only *when* a job fires; execution + delivery stay in `cron.scheduler.run_job / _deliver_result`. `:20` `DEFAULT_MISFIRE_GRACE_MINUTES = 10`. `gateway/run.py:4586-4591` — `_start_cron_ticker` (deprecated shim) starts `InProcessCronScheduler().start(stop_event, adapters, loop, interval=60)`; housekeeping chores at `:4560-4583`. `gateway/run_startup.py:1205,1223` — gateway "will continue running for cron job execution" even when platforms fail. `hermes_cli/cron.py:237-247` — `hermes cron tick` runs due jobs once and exits; if a fresher gateway holds the runtime lock the CLI yields (`CronTickYielded`). `plugins/cron_providers/chronos/` — the only shipped alternative provider; `gateway/platforms/api_server.py:3480-3488` — `POST /api/cron/fire` is the Chronos fire webhook (NAS -> agent), authenticated by a NAS-minted JWT via `plugins.cron_providers.chronos.verify.get_fire_verifier`, NOT `API_SERVER_KEY`; returns 202 and runs in background; store CAS claim guards double-fire. Route registered only if `_CRON_AVAILABLE` (`api_server.py:1020-1029,1569-1570`). Jobs API `GET/POST /api/jobs`, `GET/PATCH/DELETE /api/jobs/{id}`, `POST /api/jobs/{id}/pause|resume|run` (`api_server.py:1558-1565`) delegates to `cron.jobs` + `cron.scheduler.create_job_with_scheduler_registration`. `cron/scheduler_detached_worker.py:1-7` — workers that outlive `run_job` own their own SessionDB teardown.
- **Kanban**: `plugins/kanban/` contains only `dashboard/` and `systemd/hermes-kanban-dispatcher.service` (no `plugin.yaml` read). `gateway/kanban_watchers.py:1-8` — "Background loops that subscribe to kanban boards, deliver notifications and artifacts, and drive the multi-agent dispatcher... live on a mixin GatewayRunner inherits"; per-tick work in `kanban_watchers_notifier` / `kanban_watchers_dispatcher`; `_acquire_singleton_lock` / `_kanban_dispatch_allowed` in `kanban_watchers_common`. `hermes_cli/kanban.py:217,1244` — CLI verbs include `dispatch`, `daemon`, `promote`, `repair`, `schedule`, `unblock`, `archive`. `agent/kanban_stop.py` exists (stop gate for kanban workers).

### Config/env keys
- `goals.max_turns` (20); aux slot `goal_judge`.
- `loops.min_interval_seconds`, `loops.max_ticks`, `loops.self_paced_floor_seconds`, `loops.self_paced_ceiling_seconds`.
- Cron: tick interval 60s (in-process provider); `~/.hermes/cron/.tick.lock`; `agent.cron_drain_timeout` / `agent.restart_drain_timeout` (`gateway/run_startup.py:807-817`); Chronos provider config under `plugins.cron_providers.chronos` (fire verifier).
- Kanban: singleton lock + dispatch-allowed gate (`gateway/kanban_watchers_common.py`); optional systemd unit `plugins/kanban/systemd/hermes-kanban-dispatcher.service`.

### Reachable over POST /v1/runs (api_server platform)?
- Goals/heartbeat/loop: **conditional** — they are gateway slash commands (`gateway/slash_commands_goals.py:1-2`) handled by `GatewayRunner`; the api_server platform is a gateway platform, so a run whose input begins with `/goal ...` reaches the same mixin if the api_server run path routes slash commands through `GatewayRunner` (pending-slash detection at `gateway/run_turn.py:3449`). Delivery of judge status lines and continuation turns goes to `_adapter_for_source(source)` (`run_goals.py:198-219`), i.e. back to the api_server adapter for that session. Not settled from source read here whether `/v1/runs` input is passed through the slash-command dispatcher or only as a plain user message.
- Cron: **yes** for job CRUD and manual fire (`/api/jobs...`, `POST /api/jobs/{id}/run`); scheduled firing itself is not a `/v1/runs` call — it is the gateway background thread or the Chronos webhook.
- Kanban: **no** direct endpoint; watchers run inside the gateway process (or the systemd dispatcher unit).

### Limitations
- **Cron does not fire when the gateway process is stopped** with the in-process provider: the 60s tick thread is owned by the gateway (`cron/scheduler.py:1`, `gateway/run.py:4586-4591`). Alternatives are `hermes cron tick` from an external scheduler (`hermes_cli/cron.py:237`) or the Chronos provider whose NAS calls `POST /api/cron/fire` — which still requires the api_server (and thus the gateway) to be up (`api_server.py:3480`). Missed jobs are subject to `DEFAULT_MISFIRE_GRACE_MINUTES = 10` (`cron/scheduler_provider.py:20`).
- Goal continuation and heartbeat wakeups are in-memory gateway state keyed by session; `run_heartbeat_restore.py` exists to restore after restart, but the loop stops with the process.
- Goal judge fails open (`config_defaults.py:1299`); `goals.max_turns` is the only hard stop.

### Empirical test needed
- Whether `POST /v1/runs` with `input: "/goal ..."` is dispatched as a slash command or literal text on the api_server platform.
- Whether heartbeat/goal continuation turns emit `run.*` events on an api_server run stream or only write to the session transcript.
- Whether `hermes cron tick` invoked by an OS scheduler while the gateway is down fires jobs with delivery to api_server sessions (delivery adapters are absent without the gateway).

### Reachable over POST /v1/runs (api_server platform)?
- Image/video generation: **yes** when the `image_generate` / `video_generate` tools are in the run's toolset and a provider is registered+available (`agent/image_gen_registry.py:3-5`, `agent/video_gen_registry.py:1-10`).
- Vision input: **yes** — multipart input with `image_url`/`input_image` parts using `http(s)` or `data:image/...` URLs (`api_server_runs.py:449-487`).
- TTS/STT: **conditional** — these are gateway voice-message features (`stt.echo_transcripts` refers to "gateway voice messages", `config_defaults.py:1072`); no `/v1/runs` audio-input part type exists in `_IMAGE_PART_TYPES` (`api_server_runs.py:451`).
- Media file delivery: **conditional** — image `MEDIA:` tags become inline base64 data URLs in `final_response` for files up to 5 MiB (`api_server.py:843-875`); non-image files remain as text tags. Whether the `/v1/runs` `run.completed` payload passes through `_resolve_media_to_data_urls` (call sites at `api_server.py:3129`, `:3184`) versus only the chat-completions/session-chat handlers was not confirmed from the lines read.

### Limitations
- Data-URL inlining is images-only and capped at 5 MiB; larger or non-image media is not delivered as bytes over api_server (`api_server.py:843-866`).
- `[[as_document]]` semantics ("unmodified sendDocument for large images") are platform dispatch-site behavior (`base.py:2956-2957`); api_server has no document-send equivalent in the lines read.
- Artifact download is one-shot (`api_server.py:2619`).
- Provider selection fails closed when a configured provider is not registered (`video_gen_registry.py:5-6`).

### Empirical test needed
- Whether `run.completed` / `run.output` events on `/v1/runs/{id}/events` contain the base64-inlined image or the raw `MEDIA:` tag.
- Whether audio input can be supplied to `/v1/runs` via an artifact upload receipt (no part type found in source).

## 14. Plugins & hooks: manifest, `register(ctx)` surface, plugin dirs, gating, `plugins.entries.<id>`
