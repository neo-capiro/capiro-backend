# Phase 2 handoff — accepted interfaces and what remains

Prepared 2026-09-19 as part of the Phase 0/1 closeout. **Read `closeout-report.md` first for the actual PASS/FAIL/BLOCKED verdict.** This document describes what Phase 2 may build on and what it must not assume. It does not itself declare Phase 1 complete, and **a Phase 1 requirement that did not pass is listed as a Phase 1 blocker in the closeout report — it is never laundered into this document as a "Phase 2 carryover."**

## 1. Interfaces Phase 2 can treat as accepted

These are stable, tested and should be reused rather than reinvented. Changing them is a breaking change that needs its own review.

| Interface | Where | What Phase 2 gets |
|---|---|---|
| Authorization envelope | `hermes-runtime.contracts.ts` (`MeriHermesAuthorizationEnvelope`) | Server-created, immutable per run, never sent to the model. Carries tenant, actor, conversation, execution scope, audience, authorized client/mailbox ids, tool policy, authorization version, budget. **Add fields here rather than passing scope out-of-band.** |
| Broker boundary — **partially accepted, see §1.1** | `meri-hermes-broker.service.ts` | The *only* path a worker has into application data. Per-call re-authorization (token, run binding, scope equality, liveness, envelope expiry, authorization version, current membership) is accepted. **`assertTool`'s policy enforcement is NOT accepted — it currently fails open in three ways (§1.1).** New Phase 2 tools must still be added behind `assertTool`, but only after the §1.1 defects are fixed. |
| Revocation fencing | `meri-hermes-broker.service.ts` → adapter stop path | On membership revocation, authorization-version mismatch or envelope expiry the worker is actually stopped and the run fenced terminal, not merely denied its next call. Phase 2 tools inherit this for free. |
| Pre-release authorization recheck | `MeriHermesBrokerService.assertStillAuthorizedBeforeRelease()` | A single shared primitive, invoked by every broker path that **returns governed data** (`recall`, `getAttachment`), so a read authorized at entry cannot deliver its payload if authorization was revoked while the read was in flight. Phase 2's mail, MCP and data-gateway reads **extend this same call** rather than each re-implementing a recheck. |
| Durable run/event/interaction store | `meri-hermes-prisma-run-repository.ts`, tables `meri_agent_runs` / `meri_agent_run_events` / `meri_agent_interactions` / `meri_execution_scopes` | Atomic admission with single-writer-per-conversation, request-fingerprint idempotency, atomic `seq` allocation, fenced terminal transitions, transactional finalize, durable dispatch tracking, ordered cross-replica delivery and a pruning-safe recovery snapshot. |
| Event contract | `meri-hermes-event-translator.ts`, contracts.md §4 | Hermes wire event → Meri durable event (`kind`, `visibility`, `payload.frames[]`) → browser SSE frame. New event kinds go through the translator; **never stream raw tool payloads or hidden reasoning.** |
| Governed recall port | `meri-hermes-recall.ports.ts` (`ContextPlaneRecallPort`) | Institutional memory stays authoritative in Meri, reached through the canonical Context Plane rail. There is no ungoverned local-memory fallback and Phase 2 must not add one. |
| Pilot gate | `meri-hermes-flags.ts` + `meriv3-runtime.proxy.ts` | Three independent keys, default closed, canonical tenant ids only, client fields ignored. Phase 2 capability flags should compose with this, not bypass it. |
| Interaction UI contract | contracts.md §6, `HermesApprovalCard.tsx`, `meri-hermes-interactions.ts` | Approvals expose **Run once / Deny** only; clarifications are durable continuations answerable after their run ends. |

**Ticket #6 (governed recall) is accepted once here and reused.** Phase 2 does not re-litigate the recall path; it extends it with additional authorized sources. **This acceptance is conditional on the §1.1 defects being fixed** — one of them corrupts the very input the recall path's client dimension rests on.

## 1.1 Authorization defects found during closeout review — NOT accepted, fix required in Phase 1

Surfaced by the Phase 2 orchestration session's read-only review and **each independently re-verified in source here** before being recorded. These sit inside interfaces this document would otherwise hand to Phase 2 as settled, so they are called out rather than inherited.

| # | Defect | Verified location | Why it matters |
|---|---|---|---|
| A1 | **A revoked or expired client grant still authorizes a walled client.** `authorizedClientIds` is built with `memoryAccessGrants: { some: { userId } }` — filtering on `userId` **only**. `MemoryAccessGrant` carries `status` (default `active`), `expiresAt` and `revokedAt`; none is tested. | `meri-hermes-security.port.ts` (envelope builder); model at `prisma/schema.prisma` | `authorizedClientIds` is the single input the entire client dimension rests on — `proposeMemory` checks it, recall filters on it. Restricted-client revocation is a property the pilot is explicitly sold on. |
| A2 | **No downstream net.** `fetchDeniedClientIds()` re-derives the wall with `NOT EXISTS (… a.user_id = $2)` and is **also** lifecycle-blind. | `src/memory/memory-wall.helpers.ts` | Defence in depth does not exist here: both layers treat a dead grant as live. Note this is **shared memory-system code**, not Hermes-specific, so the exposure predates and extends beyond this integration. |
| A3 | **`assertTool` allow-list fails open.** `if (policy.allow.length && !policy.allow.includes(tool))` — with `allow: []`, `0` is falsy, the check is skipped and **every tool is permitted**. The contract comment says "Empty = none". | `meri-hermes-broker.service.ts`; contract in `hermes-runtime.contracts.ts` | The code does the opposite of its documented contract, in the method Phase 2 tools are meant to sit behind. |
| A4 | **Tool budget is not a cap under concurrency.** `brokerCalls + 1` is computed from a snapshot taken at `authorize()` and written as a plain `SET` (`brokerCalls: patch.brokerCalls`), not an atomic increment. | broker service + `meri-hermes-prisma-run-repository.ts` | Parallel tool calls are normal for an agent runtime, so the declared 40-call budget is reachable-bypassable, not theoretically so. |
| A5 | **`MUTATING_TOOLS` is a hand-maintained two-element set**, so any tool absent from it is treated as read-only and is permitted on a `readOnly: true` run. | `meri-hermes-broker.service.ts` | Fail-open by default for every future write tool — precisely the Phase 2 growth path. |
| A6 | **The F-1 pre-release recheck has a fail-open fallback.** `phase === 'release' ? ((await this.runs.get(run.runId)) ?? run) : run` — a missing row silently substitutes the **entry-time snapshot**, validating against exactly the stale state F-1 exists to reject. | `meri-hermes-broker.service.ts` | Undermines the guard added for F-1. A missing row for a live run should be a hard `run_not_live`. |
| A7 | **The whole gate is untested.** A repository-wide search across `*.spec.ts` for `tool_not_allowed`, `tool_denied`, `read_only_run` and `tool_budget_exhausted` returns **nothing**. | — | Zero direct coverage is how A3–A5 coexisted in one twelve-line method. |

Also noted, and owned by Phase 2 rather than fixed here: `ContextPlaneRecallPort.recall` receives `authorizedClientIds` from the broker but its body never reads it, relying on the downstream governed rail instead — only the *prototype* port enforces the envelope list. The recall path should therefore **not** be described as envelope-enforced on the production rail.

### A8 — a Hermes answer emits no citations (Phase 1 acceptance gap, not Phase 2 carryover)

Verified here: `grep -il citation` across the non-spec sources in `apps/api/src/meri/hermes/` returns **nothing**, while the consumer contract is fully built and in use on the V3 path (`meri-citations.helpers.ts`, the SSE citations frame, source chips, the evidence tab).

This is **not** a Phase 2 item, because P1-08's own vertical-slice criterion reads *"performs a permitted broker read, emits supported progress/**citations** and saves one final response"*. What the Hermes path does emit today is the `tool.completed → {type:'sources'}` trust-step frame (tool name, label, summary) — tool provenance, not record-level citation. The underlying data is already present at the broker boundary: governed recall demonstrably returns a real `sourceId` plus `provenance{source, sourceType}` and coverage. It is simply never translated into the citation contract the Meri UI consumes, so the pilot would answer without sources while V3 answers with them — a visible regression against "preserve the existing Meri experience".

Recorded as a **Phase 1 gap against P1-08**, not signed off. Raised by the Phase 2 orchestration session (which had generously taken it as its own P2-08b) and reclassified here after checking the acceptance wording.

### A9 — no untrusted-content handling on the Hermes path (informational)

Also verified: nothing in `apps/api/src/meri/hermes/` mentions untrusted content, whereas the legacy path sanitizes MCP tool descriptions and labels results `untrusted: true`. Phase 1's exposure is bounded — the pilot's only tools are the six broker tools, whose outputs are Meri's own governed records rather than third-party text — and the adapter's instructions already tell the model to treat tool results as data, never instructions. It becomes materially more important the moment Phase 2 admits MCP, mail and web content, and the master plan's launch evidence (prompt injection cannot change scope, reveal credentials or bypass approval) is not satisfied by the current state. Tracked for Phase 2.

## 2. What Phase 2 must not assume

- **Not proven at scale.** The tested envelope is 1 tenant / 2 users / private scopes, with the numeric limits in `decisions.md` §4. Nothing here demonstrates 25, 100 or 500 scopes. Phase 2's new data/mail/MCP call paths must be brought under the *same* budget and fairness controls — a new call path that bypasses the parent reservation is a regression, not a feature.
- **Not a coverage claim.** `data-inventory.md` counts **Prisma model declarations** across 12 schemas including explicit projection schemas — not distinct business tables (see `checks-report.md` correction C7). Real coverage requires the Phase 2A catalog and per-field policy classification.
- **Proposed ≠ saved.** The runtime can propose a governed memory candidate; it is never an admin and Phase 0/1 never observed a commit. Any Phase 2 feature that reports a memory as "saved" must be reading the authoritative service, not the proposal.
- **Background learning is off.** Automatic skill learning, the skill registry, curator, staged approval and persona settings are **2B** and are explicitly disabled in Phase 1. Do not enable any of them without also delivering the lifecycle guarantee that an idle timer cannot discard enabled unfinished work.
- **The pre-release recheck covers read paths by design — write-path source revalidation is Phase 2 work, not an oversight.** `assertStillAuthorizedBeforeRelease()` is deliberately scoped to the paths that return governed data to the model, because that is the property Phase 1 had to close: data must not reach the model after authorization is revoked. The mutating paths (`proposeMemory`, `publishArtifact`, `requestClarification`, `recordTurn`) are guarded at entry by `authorize()` + `assertTool` and return no governed payload, which is sufficient for the Phase 1 capability set. It is **not** sufficient once Phase 2 gives the runtime a real memory-write lifecycle: a `proposeMemory` admitted while the actor was genuinely authorized can cite source material the actor may no longer read by the time the candidate is committed, leaving a governance-queue candidate carrying now-forbidden content for a reviewer to see. Closing that needs a pre-commit revalidation of the **sources a proposal cites**, not of the caller — entry-time authorization cannot catch it, because at entry the caller was authorized. Tracked by the Phase 2 workstream with its own acceptance test (revoke a client grant between a governed read and the propose that cites it; the candidate must not be created, and if created must not be reviewable). Raised by the Phase 2 orchestration session during closeout review.
- **No external business writes exist yet through the runtime.** Business actions remain with Meri's own executor and approval records. This is load-bearing for the current rollback story (rollback cannot un-send something the runtime never had the power to send). Phase 4 changes that and must re-establish the property with idempotency keys and reconciliation.

## 4. Known defects and debts carried forward (not Phase 1 blockers)

1. `/v1/skills` returns **HTTP 500** on the pinned build (`TypeError: _find_all_skills() got an unexpected keyword argument 'include_editorial'`) — re-verified during this closeout. Skill listing must come from the scope volume or the 2B registry, not this endpoint, until upstream fixes it or the pin moves.
2. Upstream seeds **58 bundled skills** at first boot; only the top-level MIT license was reviewed. A bundled-skill license review is a prerequisite for distribution sign-off.
3. Cross-replica **live push** is delivered by ordered durable polling rather than a push bus. Correct and replica-agnostic, but it trades latency and adds steady database read load; a notification bus is a reasonable Phase 2+ optimisation, not a correctness fix.
4. Tool-progress events below the recovery snapshot are intentionally not replayed after pruning. Pending interactions are unaffected (they are recovered from their own table).
