F1 — HIGH: checkpoint arithmetic can accept malformed numeric types and unvalidated accounting mutations
File: evidence/candidate/case12-setup-reservation-owner.mjs:21-25, 68-77.

`checkedCheckpoint` validates `eventCount` as a safe integer, but does not validate types/ranges for `committedCostMicros` or `remainingReservationMicros`, nor the other accounting counters. Reserve then compares `committedCostMicros` with JavaScript `+` and `remainingReservationMicros` with subtraction. A string committed-cost value therefore receives concatenation semantics. The post-hold validator also does not require untouched snapshot accounting fields to remain unchanged or validate any per-case accounting fields.

Exact source-level reproduction: construct a native-current pre-checkpoint identical to `prior`, with `snapshot.committedCostMicros` set to the string `"16200909"` and a valid numeric remaining amount. Have the native reserve response make the expected row/event/file changes, set post `committedCostMicros` to `"16200909125460"` for a 125460-micro hold, and subtract 125460 numerically from `remainingReservationMicros`. The existing strict comparison evaluates `"16200909125460" === ("16200909" + 125460)` as true. The owner has no numeric guard, so this malformed arithmetic can be accepted. Separately, a native reserve response can alter `knownSettledCostMicros` or `conservativeApprovalCostMicros` while keeping the checked event/committed/remaining fields valid; those changes are not compared with the pre-checkpoint.

Impact/boundary: this is reachable bad behavior in the owner factory’s validation, not merely the documented absence of production ports. It could bless a malformed or internally inconsistent native checkpoint. It does not establish that a real journal currently has this state. Fix by validating all arithmetic operands as safe integers and positive/nonnegative as the protocol requires, computing expected deltas only after those checks, and requiring every snapshot field other than explicitly defined reserve deltas to be unchanged. Validate the exact expected post snapshot key set and any per-case counters too.

F2 — HIGH: API task-definition command and role configuration are not inspected/pinned
File: evidence/candidate/case12-setup-native-census.mjs:8-12, 41-43, 51-53.

The inspector checks API task-definition ARN, ACTIVE status, one container, image, absence of environment files, and a hash of the container `environment` array. It does not check or hash the API task definition’s `taskRoleArn`, `executionRoleArn`, container `command`/`entryPoint`, or other task-definition execution configuration. Task-role/execution-role and command checks at lines 51-52 apply only to task *overrides*, not the task definition. Thus a task definition with a malicious/different command or privileged role passes if its supplied ARN/image/environment still match the pins.

Exact repro against the supplied synthetic fixture: add `taskRoleArn: 'arn:aws:iam::967807252336:role/unexpected'` and `executionRoleArn: 'arn:aws:iam::967807252336:role/unexpected-exec'` to `census.definition.taskDefinition`, and add `command: ['unexpected']` to its API container. Leave the pinned ARN/image/environment unchanged. `inspectCase12SetupCensus(...)` has no predicate over those fields and returns inspection facts. The existing tests cover task-level role/command overrides, but not task-definition roles/commands.

Impact/boundary: this is reachable bad behavior in the pure inspector and means its diagnostics do not establish the requested exact API execution configuration. A genuine `consumeCostAuthority`/native census owner and root’s real ECS self-authentication remain mandatory and must independently reject the mismatch; this finding does not claim the JSON inspector is cost authority. Add immutable reviewed role/command/task-definition configuration hashes (or exact expected values) to pins and check them, with negative tests.

F3 — MEDIUM: the owner does not itself bind dispatch registration to the compact input or authenticate the task acknowledgement
File: evidence/candidate/case12-setup-reservation-owner.mjs:94-101.

`bindDispatch` accepts any syntactically valid Case12 task-definition ARN and any 64-hex `inputByteSha256`; it never recomputes or compares that hash to `compactInput(handle)`. `bindTask` accepts any syntactically valid task ARN after `bindDispatch`, without a registration response/task-definition join. Phase gates prevent a second bind/claim, and current-scope readback is tied to the handle’s stored task ARN, but these methods alone do not prove that the registered task used the compact input or that the returned task ARN is the acknowledged task for that registration.

Exact repro: after reserve → provider-plan bind → claim, call `bindDispatch` with the allowed task-definition ARN and `inputByteSha256: '0'.repeat(64)`, then call `bindTask` with any syntactically valid task ARN. Both pass their local shape checks; `currentScope` reports those supplied values after a fresh checkpoint read. The independent tests only reject an unknown dispatcher key; they do not test hash mismatch or forged task acknowledgement.

Boundary: the notes explicitly assign actual ECS dispatch, input authentication, and durable consume to root, so this is not by itself evidence of an external authorization bypass. It is a source seam limitation that must be closed by the root composition before use: derive/verify the exact serialized helper bytes and hash, authenticate the task-definition/task registration response and input identity, and make post-deadline readback query only that same known task without permitting another dispatch. Task census alone does not prove future quiescence; owned dispatch/worker controls remain separate.
