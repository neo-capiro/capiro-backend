Composition findings

- The CLI has no file or argument-based plan/dependency ingress, resume mode, or retry mode. It requires exactly `execute` and an environment input no larger than 7,000 bytes, parses a JSON object with exactly `kind|native|providerEnvelope|recipe|version`, and rejects an invalid recipe before importing the factory or compiled native modules. It never accepts a caller-supplied full setup plan, readiness/corpus proof, or generic serialized capability. The eight recorded ingress cases cover missing/extra command arguments, missing/bad/oversized input, array input, unexpected serialized plan/authority, and an invalid recipe; their hook asserts factory/compiled-native import was not attempted.
- After recipe resolution, the helper imports and calls the actual zero-argument `createCase01SetupDependencies` factory. The factory source rejects arguments and composes a fixed, scoped Nest application-context graph rather than starting the API application, workers, chat, or model calls. The helper uses the fixed recipe, performs fresh `inspectCase12Setup`, requires `PLAN_ONLY`, and builds a deterministic 510-row provider plan from that fresh plan plus the held provider envelope. The planner validates the exact recipe/plan shape, canonical hashes, 510 definitions beginning at MA510, fixed request identities/body hashes, and budget calculation; the native admission binds the fresh plan and provider-plan hash to the input envelope.
- Compiled native admission is invoked with the exact raw input and computed plan. Its source binds the one-use opaque handle to fixed ECS task identity, task definition/image and exact task override. The helper then composes the durable budget owner with current-scope inspection and the native terminal-row inspector; it passes only the opaque admission handle to `executeCase12Setup`, never serialized authority. No `cloudRunTask` call exists in this helper composition. Input is capped at 7,000 bytes and the admission source also checks the serialized AWS container override is at most 8,192 bytes.
- Ordering is source-consistent with fail-closed one-use admission: the executor obtains its fresh plan, compares the exact expected plan hash, checks current scope and empty corpus under the transaction, then consumes admission in that same transaction before claim-slot CAS. The native admission marks its handle consumed before its first awaited DB operation; it locks the tenant row, checks the current admission window and vacant slots, then performs and verifies the admission-slot CAS. The budget owner creates its durable provider budget slot in that transaction. Any failed transaction/uncertain write is not converted to success or replay authority. The native-admission prior review explicitly leaves actual rollback/commit behavior pending; source ordering is not proof of the runtime transaction outcome.
- Per-row ownership preserves ordered 510-row processing, exact provider request hashes, reservation-before-dispatch and settlement accounting. The budget owner verifies both distinct provider kinds settled before advancing a row and joins returned canonical bindings to a bounded native terminal proof (maximum 4,096 serialized bytes) in the completion transaction. Completion readback requires 510 completed rows, 1,020 settled attempts, zero pending attempts, ordered claim progress, and matching terminal proof metadata and hashes. The source graph places the provider AsyncLocalStorage scope around the per-row callback; the compiled provider consumers and same-graph runtime binding have not been qualified here.
- The helper's progress pipe is explicitly only local delivery, not durable authority. Durable claim/provider-ledger state and fresh native completion/current-corpus readback are used instead. An executor reconciliation result, incomplete corpus, exception, failed factory close, or failed terminal-output acknowledgement leads to nonzero/uncertain failure and does not emit a successful terminal record. Failure text is suppressed in favor of fixed stderr codes. The operator's full hold remains the recovery boundary until separate native readback/quiescence authorizes settlement; neither partial progress nor a progress log is promoted.
- The emitted terminal object is a bounded summary: native admission proof, provider-plan hash, setup binding, current verification and physical-map hashes, charges, row/attempt/pending counts, and explicit false/not-run authority labels. Its `terminalSha256` hashes the JSON serialization of the terminal object before adding the hash field. No exception text or provider/database configuration is returned. The output is emitted only after factory close succeeds. It asserts no capture authority, aggregate settlement, human acceptance, or live acceptance.
- The entrypoint's new `meri-case12-setup-native` case dispatches to this helper and does not make it the default `serve` path. It composes the database URL before dispatch; the helper itself enforces the explicit `execute` argument. Docker copies the helper through `apps/api/scripts`, the compiled API `dist`, its scripts/source, and the required Case12 fixture-provisioning modules and stable library paths.
