## Correction assessment

- **F1 — one-use settlement under concurrent reuse: corrected.** In `meri-case12-setup-provider-scope.ts:89-114`, scope/capability validation happens first, then `reservation.settled = true` at line 104, synchronously before invoking/awaiting the trusted owner's `settle` at line 107. JavaScript execution therefore marks the shared capability consumed before a concurrent invocation can pass the `reservation.settled` guard. The owner is entered at most once for that capability. A failed/unknown owner commit remains consumed, marks the scope uncertain at lines 108-110, and leaves the capability pending rather than retrying a possibly committed write. The added gated concurrency test in the scope spec (lines 51-74) checks one owner call and rejects the competing call. Ordinary one-use success remains viable: a successful known settlement deletes the pending capability at line 112; the added test awaits the first completion and exits the scope normally.
- **F2 — strict scalar identity validation: corrected in the reviewed validation paths.** `meri-case12-setup-budget.ts:145-167` now requires actual strings before UUID/hash regex checks on plan IDs, actor IDs, and plan hashes; the proposer/reviewer inequality is applied to those validated scalar strings. Lines 192-208 require a string UUIDv5 candidate ID before uniqueness checking and require a scalar payload hash. Lines 209-220 require scalar request body hashes. This closes the array-to-string coercion path for the affected identities and hashes while preserving valid lowercase UUID/hash scalar inputs. The updated unit spec adds representative array mutations at `meri-case12-setup-budget.spec.ts:203-220`, including plan ID/hash, candidate ID/payload hash, and body hash. The supplied v3 repro record separately reports rejection coverage for the full listed plan identity/hash arrays, same-actor and duplicate-candidate array cases, and candidate/body hashes; I did not rerun it.
- **F3 — sibling uncertainty fencing pending reservation completion: corrected.** `meri-case12-setup-provider-scope.ts:73-80` rechecks `current.open` and `current.uncertain` after the awaited owner reservation returns and before registering/returning a capability. If a sibling has made the scope uncertain during that await, this result cannot become a dispatch capability. The pending marker is not silently removed on this failed result, so scope completion remains conservative and requires reconciliation. The added test at `meri-case12-setup-provider-scope.spec.ts:76-96` models a delayed sibling reserve, marks uncertainty through a sibling settlement, then verifies the delayed reservation rejects and the enclosing scope requires reconciliation.
