# Case 01/14 canonical memory source proof — independent review

**Overall: PASS for the v1 same-policy cross-call replay finding.** The revised source closes the demonstrated replay path end-to-end in the supplied pipeline: each actual `search_memory` fetch gets a newly minted call ID/UUID nonce/body hash, the API authenticates that binding against its admitted policy and parsed request body, the API signs the current projected records with the authenticated binding, and the orchestrator verifies against the binding retained for that actual invocation before recording the source. A prior response signed for call A cannot be accepted for call B under the same policy, even with the same input and records.

**Acceptance caveat:** cited tenant-wide memory records (`clientId: null`) are faithfully represented by the proof but become `UNKNOWN` in the capture-source observation, while the supplied receipt validator requires an observed source client matching the policy client for Cases 01/14. Such otherwise valid tenant-wide citations therefore cannot satisfy the receipt’s source-client authority check. This is a conservative acceptance failure, not cross-tenant misattribution or a false trust claim; decide whether that limitation is intended.

## V1 finding resolution: PASS — same-policy response replay is invocation-bound

1. **Actual request identity is minted at the fetch boundary.** In `evidence/apps/meriv2-orchestrator/src/meri/controlled-read-observations.ts:52-89,104-115`, the invocation owner supplies `callId`; for an enabled Case 01/14 `search_memory` invocation the fetch-boundary helper refuses missing/mismatched invocation state, a non-first HTTP attempt, or a second mint. It creates a fresh `randomUUID()` nonce and SHA-256 of the exact outgoing JSON body string, then HMAC-encodes `{purpose, policyBinding, request}` with the internal secret. `api-tool-executor.repo.ts.excerpt.txt:157-205,223-230` shows the outgoing body is built once and the dedicated header is added to the real fetch. The actual tool call ID is passed by the assistant invocation owner (`meriv3-assistant.service.ts.excerpt.txt:117-121`); completed tool output is assembled against that call ID (`:9-20,31-39`).

2. **The API authenticates the header against the admitted policy and actual request body.** `meri.controller.ts.excerpt.txt:502-551` admits the existing capture policy and calls `withMeriToolRequestControl` around the authenticated-user tool execution. In `meri-tool-request-control.ts:40-47,67-79`, only enabled capture-policy `search_memory` requests are decoded, using the dedicated request header, actual `req.body`, and `INTERNAL_SERVICE_SECRET`, before authenticated request data is placed in request-local ALS. `memory-capture-source.ts:60-109` checks bounded encoding, exact request shape/types, UUID nonce, policy binding, body hash and HMAC; missing/malformed/wrong-secret/cross-policy/body-drift inputs throw. The API service reads the request from that ALS store and signs the projected records with it (`meri-tools.service.ts.excerpt.txt:40-46,83-95,116-124`). A missing ALS request does not silently create an unbound proof: the asserted argument reaches request validation and fails closed.

3. **The response proof is tied to that same authenticated invocation.** The response proof carries both policy binding and the request tuple (`memory-capture-source.ts:30-42,196-230`). Verification recomputes expected sources from the actual response records and the expected current request and requires exact structural equality before checking the HMAC (`:233-262`). At the raw response observer, the expected request comes from the active invocation’s private ALS store, not from response JSON (`controlled-read-observations.ts:104-115,117-149`). It stores the source observations only after status/outcome checks and successful verification; it labels them with the active clock row’s call ID and response hash. It cannot relabel call A’s valid response proof as call B because B’s newly minted request differs at least by nonce and call ID, and verification compares both. Same call ID/input with a different nonce, same nonce/input with a different call ID, or same call/nonce with changed input all fail the expected-request comparison; the unit test explicitly covers these dimensions (`memory-capture-source.spec.ts:139-149`).

4. **Observation is joined to one completed actual response, not merely a proof-shaped object.** The real executor observes parsed HTTP response payloads before returning them (`api-tool-executor.repo.ts.excerpt.txt:240-269`). The observer stores the response hash with the verified source (`controlled-read-observations.ts:117-149`). Source readout filters against a unique completed `search_memory` clock invocation with `returned`, one attempt, HTTP 200, matching call ID and matching response hash (`:187-200`). The clock invocation transitions to `returned` only after the executor call resolves (`:53-89`). Citation joining further requires same call ID, source/record ID, memory kind, current version, nullable-client equality and SHA-256 of the exact citation snippet (`meriv3-capture-evidence.ts:106-125`). A modified snippet/version or unobserved call is not promoted to observed source evidence.

5. **This addresses the exact v1 exploit.** V1’s response signature proved policy and record bytes but lacked invocation binding; the old observer could attach those bytes to whichever current call received them. Now the signed response includes `request` (`memory-capture-source.ts:30-36`), and the verifier compares it to the active invocation’s authenticated request (`:244-258`). The included loopback test exercises `ApiToolExecutorRepo.execute` through a real loopback fetch, decodes the actual request header with the API decode helper, returns a first valid signed body, then replays those exact proof bytes for a second fetch. It expects the second invocation to reject and the first observation to remain the only one (`controlled-read-observations.spec.excerpt.txt:137-188`; also diff around lines 156-212). This is materially stronger than the core helper-only tests and directly exercises the v1 replay scenario.

The signer requires a UUID canonical tenant from record provenance and an actual nullable-or-UUID client from payload, and refuses disagreement with policy rather than deriving ownership from policy (`memory-capture-source.ts:144-193,204-216`). Missing owner, foreign tenant and disallowed client fail closed.
- **Policy binding:** request and response HMAC bindings include policy ID, case/run, request/trace/turn IDs, tenant, actor, client, conversation, policy times, physical-map hash and semantic-clock object (`memory-capture-source.ts:111-141`). - **Exact projected records and paging:** response proof is generated from the same `records` that are returned, after projection (`meri-tools.service.ts.excerpt.txt:83-95,116-124`). Source construction checks record identity, current version, content hash, offsets, truncation and cursor consistency (`memory-capture-source.ts:146-193`). A complete page’s source hash must match the projected text plus version; partial pages are explicitly `fullRead: false`. Content cursors are rebound to tenant/user/client and current content hash on every read (`meri-memory-content.helpers.ts:31-63`); citation evidence cannot elevate a partial page to full-read (`meriv3-capture-evidence.ts:117-125`).
- **Proof/model separation:** model projection removes `memoryCaptureSources` and `canonicalTenantId` (`changes.diff:326-339`). The loopback test also asserts neither proof nor canonical tenant/signature reaches model-visible projection (`controlled-read-observations.spec.excerpt.txt:165-169`).
- **Caller JSON/direct helper paths:** the visible API path does not take proof authority from caller JSON: it admits policy, executes the existing authenticated tool, reads canonical projected records and writes a fresh `memoryCaptureSources` field (`meri.controller.ts.excerpt.txt:511-551`; `meri-tools.service.ts.excerpt.txt:83-95,116-124`). Arbitrary JSON cannot set the ALS request; the request-control wrapper derives it from the authenticated header. The exported signer is a cryptographic helper and can sign any correctly shaped records if called by code that already possesses the internal secret and trusted policy; that alone cannot create an orchestrator observation. Acceptance still requires a real response at the fetch boundary and verification against that invocation’s private request. No demonstrated caller-controlled route to invoke the signer with arbitrary records or substitute a helper result into the API response appears in the supplied path. The excerpts do not prove the absence of every other callsite.
- **Missing secret/header, malformed and cross-policy/body drift:** encode/decode and sign/verify require a nonempty secret; decode requires a bounded encoded header, strict fields and valid HMAC; body and policy mismatch throw (`memory-capture-source.ts:60-109,219-262`). API request-control invokes decode for the qualified tool before execution (`meri-tool-request-control.ts:40-47`). - **Ordinary traffic:** the dedicated request header and response proof are gated to semantic-clock, non-budget fixture policies for Cases 01/14 (`memory-capture-source.ts:111-119`; `controlled-read-observations.ts:104-115`). The API only decodes this request for that policy and `search_memory` (`meri-tool-request-control.ts:45-47`); the service only projects owner metadata and emits proof when the same policy gate is enabled (`meri-tools.service.ts.excerpt.txt:83-95,120-124`). Other tools/policies get no new header/proof from this path. Broader controller capture-policy admission is pre-existing and not altered by this proof change.

## Actionable acceptance caveat: nullable client source

`memory-capture-source.ts:161,184-185,204-208` intentionally allows an actual row with `clientId: null` under a client-bound capture policy (tenant-wide source) and signs the null rather than substituting the selected policy client. But `meriv3-capture-evidence.ts:117-125` turns that into `clientId: UNKNOWN` with reason `canonical_memory_has_no_client`. The receipt validator then requires `source.clientId` to be `OBSERVED` and equal `receipt.clientId`, except for a specifically qualified Case 20 public-source exception (`capture-evidence-receipt.ts.excerpt.txt:117-126`). Cases 01/14 are not that exception. Therefore a citation to a valid tenant-wide/null-client memory source cannot yield an acceptable source-client authority join for these cases. This is an acceptance blocker only for that source shape; it does not permit a wrong client to pass. Either document that such rows are out of scope for accepted Case 01/14 evidence or extend the receipt contract to represent and authorize an observed null canonical client distinctly from unknown.

## Optional hardening and test gaps — not demonstrated trust bypasses

- **No API-side nonce-consumption cache is shown.** A captured, correctly signed request header can be replayed to the API with the same policy/body; decode authenticates it but does not mark the nonce one-use. This does not reopen the v1 acceptance exploit: the orchestrator mints a fresh nonce for a different invocation, and its response verifier requires that new request binding. Consider nonce replay tracking if duplicate API execution/context-packet effects matter. This is defense in depth, not a demonstrated cross-call source-acceptance failure in the supplied flow.
- The included loopback checks the real orchestrator fetch and the shared API decode helper, but does not instantiate the actual API controller, middleware/body parser, `withMeriToolRequestControl` or `MeriToolsService`/database in one integration test. API controller and ALS wiring are source-reviewed; the supplied `meri-tool-request-control.spec.ts` tests cancellation/isolation but not capture header admission (`meri-tool-request-control.spec.ts:17-43`).
- Add explicit integration cases for missing/malformed header at the controller boundary, missing API/orchestrator secret, bad HMAC/cross-policy, raw-body formatting/body drift, policy scope changes, and the exported direct signer not being reachable from caller-controlled tool input. Core tests cover several helper-level failures, but not all controller/transport failure modes.
- Extend the loopback cases to cover empty-result signed proofs, partial continuation pages and page-specific citations, tenant-wide `clientId: null`, and non-200/logical-error responses. Existing source logic is conservative for partial pages; the nullable-client receipt caveat above is visible by composition of supplied code, not a reported execution result.
- Response hashes are over `JSON.stringify` of the parsed payload (`controlled-read-observations.ts:129,149`), not the original HTTP wire octets. The request signature is likewise checked against `JSON.stringify(req.body)`, as requested for the actual parsed body. This establishes a stable semantic JSON hash but should not be described as a raw-wire-byte digest.
