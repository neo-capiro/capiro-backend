# Capability routing shadow evaluation preparation

This is an offline schema, signed sample-membership verifier, and report utility. No runtime producer, Jev call, candidate execution, live traffic, feature activation, or rollout is implemented. The current repository has no trusted membership/telemetry producer key or approved tenant pseudonymization key policy, so no report can verify production shadow evidence today.

## Locked sample membership

The producer must create and sign the membership manifest before the sample is evaluated. Its canonical payload locks a unique turn-key HMAC, a deduplicated evaluation-unit HMAC, tenant HMAC and key versions, source/cohort/split, eligibility, strata, versions, and registry allowlists. Every assignment and observed event is checked before split filtering. Reused turn hashes are rejected across the complete input. A repeated evaluation-unit hash cannot be assigned to different splits. Reports for tuning and heldout must be generated separately.

The CLI requires a public key and its SHA-256 SPKI fingerprint pinned out of band. Supplying an arbitrary key and its own fingerprint only proves self-consistency; it does not make that key trusted. No such trusted key is currently registered by this package. The producer must use approved keyed HMACs for tenant pseudonyms and evaluation-unit deduplication. Plain or unsalted tenant hashes are not acceptable. HMAC secrets remain outside the event, manifest, and repository.

Surface, domain, task-family, route, reason, and tool values must match the signed manifest's bounded code allowlists. Version values use a bounded `name.vN` form and must match the locked manifest. Free text, prompt fragments, answers, source contents, raw tenant IDs, and client IDs are not accepted.

## Isolated event-trust primitives (Phase 6, off)

`capability-shadow-event-trust.ts` provides pure, unused-by-runtime primitives for a future producer and independent verifier. A signed event envelope contains the existing strict event plus `event_ed25519.v1` signing key ID, `tenant_hmac.vN` key ID, and `eval_unit_hmac.vN` key ID. Its signed payload is strict-schema parsed, recursively sorted by object key, encoded as UTF-8 JSON, and prefixed with `meri.capability_shadow.event_signature.v1` and a NUL byte before Ed25519 signing. Arrays retain their order. A verifier rejects malformed or noncanonical base64, wrong signatures, an unpinned SHA-256 SPKI fingerprint, missing key IDs or versions, and keys outside their explicit `[notBefore, notAfter)` validity windows. The caller must supply a trusted **public verification registry** containing the Ed25519 public keys and pseudonym key ID/version/window metadata; it must not contain HMAC secrets. There is no environment lookup, key fallback, or built-in trust anchor. Historical public key records may remain in the registry for verification after rotation; their windows still apply to the event's `occurredAt` value.

Tenant and evaluation-unit pseudonyms use HMAC-SHA-256 with distinct secret bytes and IDs, separate fixed domain labels, and a four-byte length prefix on each 1–1024 byte identifier. The API requires exactly 32 secret bytes per key; the key custodian must generate independent random keys. Fixed length prevents HMAC's zero-padding rule from making a 32-byte key equivalent to its 33-byte zero extension. The API rejects reused HMAC material across purposes or rotations. It takes identifier bytes explicitly and never reads secrets from the environment. The signed envelope binds the two key IDs and versions to the event's version fields. Signing payloads are capped at 64 KiB. Signature verification establishes authenticity only under the supplied public verification registry; it cannot prove that the HMAC values correspond to raw identifiers. The separate pseudonym verifier takes an additional secret-bearing keyring and authorized raw identifiers. It checks secret key references and validity windows against the public registry, rejects secret reuse, then recomputes the HMACs. Do not place raw identifiers or HMAC secrets in events, manifests, reports, or the public registry.

The separate `capability-shadow-signed-ingest.ts` module and signed-report CLI provide an opt-in offline path. The original report CLI still accepts structural events by default. The new path requires an out-of-band SHA-256 pin of the exact public registry JSON file, verifies every signed envelope against that registry, then passes extracted events to the unchanged offline report builder. It rejects unsigned lines, malformed envelopes, duplicate raw JSON keys at any nesting level (including escaped aliases), untrusted or expired keys, tampering, and secret-bearing registry fields. Limits are 32 MiB for the JSONL input, 128 KiB per envelope, 128 KiB for the registry, 2,000 events, and 64 JSON nesting levels. Membership input is bounded at 32 MiB and 2,000 assignments, and also rejects duplicate raw keys. The event count is checked before signature verification; the assignment cap is checked before membership signature verification in the CLI and again before the signed wrapper invokes the offline report builder. This conservative 2,000-row ceiling is four times the structural 500-turn floor and limits CPU work while the existing report builder still performs quadratic grouping scans; a linear-time report rewrite is needed before raising it. Empty signed input fails. The CLI rejects malformed UTF-8, checks file sizes before and after reading, and computes registry and input digests over the exact decoded-and-re-encoded file bytes. The reporting process reads only public keys and metadata; pseudonym HMAC secrets are never supplied to it.

The signed path does not alter `buildCapabilityShadowReport`, runtime routing, producer behavior, or the permanently false `liveEvidenceVerified` and `qualified` fields. The registry file pin only helps when its expected digest is obtained through an independently trusted channel; computing the pin from an untrusted registry and passing both together establishes no trust. A key window checks the event's signed but self-asserted `occurredAt`; a holder of an old signing key could backdate an event within that key's window. Event signatures cannot independently prove production time, live provenance, correct pseudonym derivation, or 500 actual live turns. No organization-approved signing or pseudonym key registry, custody policy, tenant ID encoding, evaluation-unit identity rule, or rotation schedule has been configured here. Those decisions and independent live-evidence review remain prerequisites for use beyond isolated verification.

`capability-shadow-producer-boundary.ts` is a dormant, API-unregistered preparation helper. It reads the verifier's private locked membership snapshot rather than the mutable public typed view, derives tenant and evaluation-unit HMACs from explicitly supplied authorized identifier bytes and purpose-separated keys, builds a strict content-free event from a supplied server-observation receipt, and checks it against the signed membership. Before using its injected signer, it checks registry-wide key ambiguity and exact public/secret HMAC references, versions and windows against an exact-byte SHA-pinned public registry; afterward it verifies the exact signed bytes and derived pseudonyms. The `off` branch touches none of those dependencies. It has **no runtime caller, key loader, selection policy, trusted clock, authenticated sink, or persistence receipt**. Its `prepare_only` path is a structural/cryptographic scaffold, not authenticated production evidence: an eventual caller must prove observation provenance, pre-evaluation cohort selection, source-of-truth time, trustworthy key custody, append-only delivery and gap accounting independently. It neither changes routing nor raises either report flag.

`capability-shadow-append-boundary.ts` adds the next dormant delivery contract without registering a runtime caller or network route. Its default `off` branch reads no producer, signer, registry, clock, or sink dependency. The explicit `append_only` branch first pins and preflights a separate public sink-receipt registry, prepares and verifies the existing content-free event, refuses in-flight `attempted` or `dispatched` lifecycle snapshots, and domain-separately authorizes the canonical append-request payload with the producer's registered Ed25519 key. The deterministic event ID is also the idempotency key. The request binds the exact event payload digest and both exact-byte public-registry digests. The injected sink receives a copy of a private, bounded, canonical UTF-8 JSON snapshot and is called once; callback mutation or retention cannot change the returned bytes or digest. The full sink-side verifier rejects a UTF-8 BOM, malformed UTF-8, duplicate raw keys, noncanonical JSON, an unpinned producer or sink generation, an invalid event signature or digest, invalid request authorization, in-flight lifecycle evidence, a producer key not valid at trusted verification time, and event time beyond a caller-bounded future skew before storage. A narrower historical verifier authenticates the same exact bytes and key at signed event time only; it is exclusively for immutable lookup after ambiguous delivery and never authorizes an absent row to be appended.

The sink response must be a signed `appended` or `replayed` receipt under the pinned sink audience, endpoint, key ID, SPKI fingerprint, and validity window. It binds the authenticated request digest to one immutable ledger entry, including a positive JavaScript-safe integer sequence capped at `2^53 - 1`, predecessor digest, append time, event ID, idempotency key, and event digest. The producer recomputes the ledger-entry digest and verifies the receipt signature. Receipt and append times cannot exceed the same trusted verification time by more than the explicitly bounded skew, and the receipt key must be valid both when the receipt was issued and at trusted verification. A replay returns the original immutable entry and a newly authenticated replay disposition; it does not describe a second append. The append boundary alone does not enforce idempotency-key uniqueness or same-request comparison; those belong to the transactional append-only store described below. A signed receipt is evidence from the entrusted sink, not an independent proof that its storage is immutable. No activated sink, service authentication transport, custody configuration, availability policy, gap reconciler, trusted clock provider, runtime wiring, or live evidence exists in this package, and the boundary cannot raise `liveEvidenceVerified` or `qualified`.

The API's dormant `meri-capability-shadow-ledger.repository.ts` and `20280928020000_meri_phase6_capability_shadow_ledger` migration add source-only lookup/append mechanics without registering a runtime caller. Historical event-time verification returns a module-private unique-symbol-branded `replay_lookup_only` capability before an ungranted exact-row lookup; only absence proceeds to the full current-key verifier, which returns a distinct `current_append_authorized` capability required by the repository's private mutation method. The brands are constructed only inside the verifier module, are non-enumerable symbol properties, and cannot enter JSON or be reproduced by ordinary typed object construction. A locked head serializes each `(audience, endpoint)` chain, and database uniqueness over `(audience, endpoint, idempotencyKey)` makes an exact request-digest retry return the original immutable entry while rejecting changed identity under the same key. Database processing uses a separate explicit trusted `[notBefore, notAfter)` window capped at five minutes; it does not reuse event future-skew policy. For a new append, the repository also requires the processing window's exclusive `notAfter` to be no later than the producer authorization key's exclusive expiry, so the database clock predicate prevents a commit at or after key expiry. Historical lookup remains available after expiry and cannot call the branded mutation path. The database computes the domain-separated ledger-entry digest and the repository recomputes it before return. Every error after a possible append commit becomes an integrity/commit-unknown result that permits only identical-byte recovery. The stored row is content-free except for an internal tenant UUID excluded from the public entry and receipt.

Both security-definer functions and both tables are explicitly revoked from `capiro_app` and `PUBLIC`; forced RLS is defense-in-depth for a future properly bound role, not proof that a definer owner is tenant-confined. No EXECUTE grant should exist until a dedicated non-login, non-`BYPASSRLS` sink service identity and database-enforced mapping from authenticated service tenant to authorized tenant pseudonym are implemented and rehearsed. Therefore this is not an activated sink: tenant mapping, service identity, trusted clock, key custody, receipt signing, database/concurrency rehearsal, chain export, recovery/anti-fork controls, and independent live evidence remain unresolved.

## Attempt lifecycle and cost accounting

Each event distinguishes `not_attempted`, in-flight `attempted` but not dispatched, in-flight `dispatched`, and terminal `settled`, `cancelled`, `timeout`, or `error`. The in-flight `attempted` state has no dispatch time, finish time, duration, provider usage, or cost. A local cancellation, timeout, or error can finish before dispatch; its finish time and duration describe the local attempt, not provider latency, usage, or billing. A `settled` result requires dispatch. An undispatched terminal result cannot claim provider usage or cost. A censored attempt must set `costUsd` to `null`. A dispatched attempt with unknown cost stays null; the report shows a known subtotal, an unknown dispatched-attempt count, and whether all dispatched costs are known. It never converts unknown to zero. Duration p95 uses settled attempts only and excludes censored or in-flight rows. Baseline is the only executor; Jev's route and candidate tool list remain advisory.

## Offline report and sample gate

The builder reports the signed selected denominator, observed/missing rows, dispatch/settlement lifecycle counts, per-turn tool exposure, route agreement, settled latency, known cost subtotals, and strata grouped by tenant HMAC pseudonym. Signed eligibility and an observed Jev proposal are distinct: a candidate proposal requires a settled Jev response. An eligible turn with no candidate must keep its baseline route and record an explicit allowlisted fallback reason with no candidate confidence or candidate tool exposure. Proposal and fallback counts are separate. Route agreement uses only observed proposals as its denominator and is `null` when there are none; fallback is never counted as a candidate disagreement or tool-coverage success. It never accepts or emits raw tenant identifiers. Tenant pseudonymization and evaluation-unit deduplication must use separately approved, keyed HMACs; the manifest's key-version labels alone do not establish that policy.

The 500-turn check is explicitly structural. It counts eligible representative live assignments, then separately counts records attempted, dispatched, and settled. `structurallyReady` only describes those offline inputs. `liveEvidenceVerified` and `qualified` are permanently false in this utility because there is no trusted runtime evidence producer. This package does not verify sample representativeness, selection probabilities, sampling bias, provider billing, runtime event authenticity, factual accuracy, or canary safety. No fabricated fixtures or signed test keys count as live evidence.

To produce local artifacts after the system owner registers a trusted producer key and approved HMAC policies:

```text
pnpm --filter @capiro/meriv2-core eval:meri-capability-shadow-report -- --events <events.jsonl> --membership <signed-membership.json> --trusted-key <public-key.pem> --trusted-key-sha256 <pinned-SPKI-fingerprint> --out <new-or-empty-directory> [--split exploratory|tuning|heldout]
```

The command refuses to create artifacts on any rejected line, invalid signature, membership mismatch, missing trusted-key fingerprint, duplicate, or non-empty output directory. Use a separate invocation per split; `all` intentionally fails when the locked manifest contains more than one split. The runner must separately prove the producer's selection method represents the intended organic population before treating the structural count as evidence.

For the explicit signed-envelope path, pin the SHA-256 of the exact trusted public registry file through an independent channel, then use:

```text
pnpm --filter @capiro/meriv2-core eval:meri-capability-shadow-signed-report -- --signed-events <signed-events.jsonl> --public-registry <public-registry.json> --public-registry-sha256 <pinned-file-sha256> --membership <signed-membership.json> --trusted-key <public-key.pem> --trusted-key-sha256 <pinned-SPKI-fingerprint> --out <new-or-empty-directory> [--split exploratory|tuning|heldout]
```

The public registry JSON shape is `{ "signing": [{ "keyId", "version": "event_ed25519.v1", "publicKeyPem", "trustedSpkiSha256", "window": { "notBefore", "notAfter" } }], "tenant": [{ "keyId", "version": "tenant_hmac.vN", "window": { "notBefore", "notAfter" } }], "evaluationUnit": [{ "keyId", "version": "eval_unit_hmac.vN", "window": { "notBefore", "notAfter" } }] }`. Each JSONL line must contain one `{ "payload": { ... }, "signatureBase64": "..." }` envelope. No unrelated lines are accepted. A verified signature means the payload matches an entrusted key; it does not raise the structural 500-turn count into a live-evidence verdict.
