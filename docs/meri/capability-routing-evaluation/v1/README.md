# Capability routing evaluation seed v1

This is a manually authored, non-scoring seed for the dormant `capability_routing` contract. It contains 24 synthetic request cases for rubric and validator development. It is not a representative evaluation set, does not include authoritative factual or execution oracles, and must not be used to select thresholds.

The Phase 5 plan calls for at least 300 natural-language cases, at least 50 per promoted capability family, a development/calibration/locked-holdout split, independently recorded routing, execution, answer handling, accuracy, and coverage outcomes, and authoritative versioned references for exact facts. This seed does not meet those gates. All cases have `split: unassigned`; no calibration or locked holdout membership is selected.

Each `acceptableOutcomes` entry names a canonical capability label or one of the contract's fixed outcomes (`multi_intent`, `needs_context`, `no_match`). `acceptableSequences` describes valid semantic tool sequences where order matters. Every prompt context is either explicit in the prompt or supplied by a versioned synthetic `contextFixtureRefs` entry; the validator rejects unresolved references and candidate/sequence IDs absent from the canonical registry source. These are routing expectations only. They do not certify that a capability is available, authorized for an actor, successfully executed, factually correct, or complete. Capability labels are used as labels; the dataset makes no claims about real data values, IDs, or outcomes.

The case prompts and attached context are synthetic. MRE-023 places the misleading command in a lower-trust email-draft fixture, not in a user instruction. MRE-024 is deliberately a direct user request to skip a prerequisite; the route may identify `create_client`, while deterministic policy must still require the canonical registry lookup, resolve its result with the user, obtain approval, and enforce all backstops. This case is not prompt injection. Do not run these prompts against production or a provider as part of this package.

MRE-019's permission-limited fixture records a denial. Its expected route label is not authorization to access private notes; execution must be denied, no private content returned, and answer handling must explain the limitation.

The seed's acceptance record is: schema and deterministic structural checks can be verified locally; semantic labels have one author and have not been independently adjudicated; no model/provider runs, tool executions, factual oracle checks, scores, confidence intervals, thresholds, or calibration were performed. Residuals include insufficient sample size and family coverage, no representative traffic sampling, no second annotator, no authoritative execution/factual fixtures, and no held-out partitions. Expand and adjudicate before any evaluation claim.

`coverage-report.json` is a generated, aggregate-only inventory of this synthetic seed. It includes case IDs and prompt hashes, taxonomy counts, fixture dimensions, and candidate-label appearance counts/gaps; it excludes prompt and fixture text and all authored acceptable outcomes. Candidate appearances are not positive-route evidence. The generator accepts only this `manual_synthetic` seed while all splits remain `unassigned`; it does not assign or inspect a locked holdout. Do not use its counts as evaluation scores or representative coverage.

`coverage-historic-qa-intake.json` separately inventories the historical QA artifacts: 81 read-QA rows (`MRO-001`–`MRO-081`) from `meri-read-results.json`, plus 23 action-safety QA rows (`MWR-001`–`MWR-023`) filtered from `updated-results.json` under its existing `Meri Approval Actions` category. It contains source-artifact SHA-256 fingerprints, exact IDs/counts, and aggregate safety-mode counts only. It does not include prompt, displayed result, evidence, status/verdict, or source text. These rows were not independently adjudicated as routing cases; QA `PASS` is not a factual-accuracy or route-correctness result. Do not pool them with the 24-case synthetic routing seed or credit them toward its 300-case/50-per-family gates. The intake generator and synthetic seed coverage generator are separate tools; neither assigns development/calibration/locked-holdout splits.

The historical Phase 0 QA material under `docs/meri/hermes/phase-0/` is a separate Hermes compatibility/harness audit (the README records 21 runner checks plus one labelled probe, against local fixtures/containers). Its capability ledger and data inventory are not natural-language routing cases and are not pooled into this report. The original Meri QA artifacts have now been located outside that tracked Phase 0 directory and structurally inventoried above: 81 read IDs and 23 action-safety IDs are verified as artifact counts, but none is independently adjudicated routing ground truth or credited toward this evaluation's coverage gate.

## Independent adjudication and promotion gate v1

`adjudication.schema.json` and `adjudication-gate.mjs` define a separate, versioned record for reviewed cases, independent labels, independent resolution, versioned execution/factual oracles, frozen split membership, and per-run scorecards. They do not change the v1 seed or assign splits. The gate checks the schema's required fields, types, nested route and sequence entries, and closed objects at runtime before applying the promotion rules; malformed records block evidence readiness. Promotion checks require at least 300 natural-language cases and at least 50 for every family named for promotion. The gate requires a non-empty `familyFreeze` manifest (`version`, `frozenAt`, `reference`, `familyIds`) and a separate `trustedFamilyFreezeSha256` supplied from the protected evaluation record. Empty, malformed, or duplicate promoted families block evidence readiness. Every case needs two distinct independent annotators, a separate adjudicator, reviewed source provenance, and available versioned execution and factual oracles. Missing or unverified score dimensions block the gate.

The score report retains separate routing, execution, answer handling, accuracy, coverage, cost, and latency results. Cost and latency means use an incremental calculation so finite high-value samples do not overflow their sum. Reports are split-specific; attempting to score a locked holdout while in development or calibration mode is rejected. An `agreement` adjudication requires all independent annotations and the adjudicator to give equivalent acceptable route sets and equivalent sets of ordered route sequences; an empty sequence set is valid. Different labels require `resolved_disagreement` and independent adjudication. The gate recomputes the SHA-256 of canonical `(caseId, split)` membership and checks it against `splitPlan.membershipSha256`; this catches accidental split edits but is not, by itself, proof that the split was frozen before evaluation or that the dataset is independently authentic. It also recomputes the promoted-family manifest digest and compares it with the expected digest supplied by the evaluator. The evaluator must authenticate that expected digest against the independently protected freeze record; this local script cannot establish when the freeze happened or who approved it. It also cannot dereference or authenticate oracle/source contents or execution receipts. Locked holdout evaluation requires an explicit `locked_holdout` mode after externally recording the frozen membership and remains a human-controlled release step. The 50-case minimum applies across the full adjudicated dataset per promoted family, not separately to each split; every case in the reported split still needs a scorecard. The gate reports `evidenceReady` separately from `promotionAllowed`; it never makes promotion decisions. The Phase 5 numeric acceptance targets, confidence intervals, baseline quality comparison, action-safety review, and cost-per-correct-completion comparison still require frozen policy and reviewed evaluation evidence. Synthetic tests exercise the gate only; they are not evaluation cases and do not count toward any sample threshold.

Run local tests with `node --test docs/meri/capability-routing-evaluation/v1/adjudication-gate.test.mjs`. Validate a reviewed record with `node docs/meri/capability-routing-evaluation/v1/adjudication-gate.mjs <record.json> development <family-freeze.json> <trusted-family-freeze-sha256>`. The trusted SHA-256 must come from the independently protected freeze record, not from the manifest being checked. The `family-freeze.json` object has exactly the `familyFreeze` fields described above; its canonical digest is SHA-256 of JSON encoding `["meri-promoted-family-freeze.v1", version, frozenAt, reference, sortedFamilyIds]`. There is no actual freeze record yet, so no current evaluation can pass this gate.

## Dormant route-decision metrics preflight

`route-decision-receipts.schema.json` and `route-decision-metrics.mjs` add a separate, offline structural preflight for the routing dimension. They do not change the seed, active router, offered tools, or promotion gate. Because the v1 adjudication validator loads the full case record, this preflight accepts **only an explicitly opened, protected `locked_holdout` review**; it must not be used during development or calibration. The caller supplies the v1 independently adjudicated record; a reviewed catalog manifest `{version, toolIds}` plus its independently protected SHA-256; the existing family-freeze manifest plus its independently protected SHA-256; and a receipt set matching the schema. The catalog digest is SHA-256 of JSON encoding `["meri-route-decision-catalog.v1", version, sortedToolIds]`. An expected digest calculated from the submitted receipt is **not** an independent freeze.

The caller must also supply `trustedCandidateManifest` from the protected evaluation record, with exactly `version`, `sha256`, `frozenAt`, `reference`, `evaluationBatchId`, and `catalogSha256`. That protected manifest must describe the exact candidate model, prompt, routing policy, candidate-generation and threshold versions; this module only verifies the externally supplied digest/binding, not the manifest contents. The receipt set and **every** decision repeat its candidate version/digest and batch ID, preventing one evaluated set from silently combining variants. Every captured decision timestamp must be later than the protected split, family, and candidate freeze times. This catches obvious pre-freeze receipts but cannot prove clock integrity, immutable storage, a genuinely precommitted batch, or completeness of attempted runs.

Each decision references an exact, separately protected run receipt by reference and content digest and binds case ID, split, dataset, catalog, family freeze, split membership, candidate and batch. Decision receipt references and required-tool oracle references must each be unique across holdout cases; one protected object cannot be reused to substantiate two cases, even if a caller supplies different digests. `accepted` means the proposal and selected route/ordered sequence are identical and selected tools were in the recorded candidate exposure. `fallback` carries an explicit reason, no candidate proposal or exposure, and receives no candidate-correctness or retained-tool credit. A route label alone cannot pass when an adjudicated ordered sequence is required; an executable route with no sequence oracle blocks workflow scoring. The v1 adjudication record does not pair alternative route labels with alternative sequences, so any case with more than one acceptable label and a nonempty sequence oracle fails closed pending a paired-oracle schema. With one executable tool label, every acceptable sequence must include that tool; `multi_intent` instead requires its explicitly adjudicated sequence. Repeated tool IDs in an ordered sequence are allowed consistently with the v1 adjudication contract. The preflight rejects missing/duplicate/cross-split receipts and self-reported routing success that contradicts the bound decision. It computes acceptable-workflow selection overall and by promoted family, accepted-decision precision, and fallback rate from decisions rather than trusting the old `scores.routing` label.

Required-capability recall is only calculated when every holdout case has a separate versioned, independently reviewed required-tool oracle. These labels must exactly match the intersection of tools common to every adjudicated acceptable sequence; this is a structural consistency check, not proof that the adjudicated sequences themselves are complete. A common-tool intersection is insufficient when the alternatives have different tool **sets**: for example `[bill, source_data]` or `[bill, memory]` cannot be scored as full recall from `bill` alone. Such disjunctive cases keep their routing/workflow metrics but leave required-capability recall `null` with an explicit blocker until a reviewed clause/coverage oracle exists. Alternatives with the same tool set in different orders do not trigger that blocker. Missing oracles or a zero required-tool denominator also leave recall `null`, never 100% by default. The result distinguishes `structuralReady` from `metricInputsComplete` (also structural only) and **always** returns `promotionAllowed:false`. The synthetic unit fixtures are contract tests only; they are not evaluation data and their computed rates are not evidence of Meri quality.

This module validates references and hashes structurally but cannot fetch or authenticate protected receipt/oracle contents, prove reviewer independence, prove the freeze predates candidate runs beyond timestamp ordering, or establish that the recorded candidate-exposed tools equal the actual final provider schema. Its result therefore always states `evidenceAuthenticated:false`, including when `structuralReady` and `metricInputsComplete` are true. The current 24 seed cases remain unassigned and zero are independently adjudicated. Real Phase 5 acceptance still needs protected exact receipts, an independently frozen representative >=300-case corpus with >=50 cases for every promoted family, authoritative execution/factual references, paired baseline runs, confidence intervals, safety review, and reviewed cost-per-correct-completion/p95 results. Do not expose locked-holdout receipts to development/calibration analysis or interpret this preflight as routing permission.
