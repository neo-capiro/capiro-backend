Do not point the frontend read base at the PR #48 full API merely because its ordinary GET handlers exist. That process runs `serve` with the `capiro_app` writer credential. Its tenant middleware can create/rebind users, repair membership, and update `lastSeenAt`. It does not implement the isolated read-only contract. The `111f` entrypoint avoids that middleware, requires an existing active member of pinned `capiro-internal`, verifies the Clerk session and local authority before and after the read, and uses a PostgreSQL transaction whose first statement is `SET TRANSACTION READ ONLY`. It requires a separately approved effective SELECT-only database identity and `default_transaction_read_only=on`. It intentionally has no `/health` route.

The frontend gateway requires `CAPIRO_PREVIEW_READ_ONLY=true`, that exact source marker, and an HTTPS `CAPIRO_PREVIEW_READ_API_BASE_URL` ending in `/api`, different from its ordinary backend origins. Its source allows the first-chat preview origin as a configuration value, but that value must stay unset until the **actual** isolated read runtime and target have been qualified. The gateway's narrow browser allowlist and bearer forwarding are additional checks; they do not turn the PR #48 writer process into a read-only service.

## Smallest shared-host listener proposal

The Core preview origin is `https://first-chat-preview.app-dev.capiro.ai` and the API base is that origin plus `/api`. At the last Core execution readback, the HTTPS listener had priority 1 for exact first-chat POST bootstrap/identity/context, priority 2 for exact POST membership, and an independently retained host-only fixed JSON 404 at priority 3. That guard protects this host from the host-agnostic production `/api/*` rule at priority 10. A GET rule after priority 3 would never run. The later listener inventory found priority 4 vacant; priorities 5 through 10 were occupied, including 9. Re-read every rule before rendering a change set.

Candidate, subject to exact synthesis, live listener review, and a separately qualified `111f` target:

1. Update only the guard stack's existing retained rule from priority 3 to **priority 4**. Verify that the same host-only fixed JSON 404 rule remains ahead of production priority 10; preserve its export and retain policies. Stop if priority 4 is occupied or the rule/action/export differs. Do not delete or recreate the guard.
2. Give a separately owned isolated read target a **priority 3** rule for exactly this host, HTTP method `GET`, and three anchored path regex evaluations: `^/api/me$`, `^/api/clients$`, `^/api/clients/[0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. Do not forward `/api/*`, `/api/clients/*`, POST, HEAD, or OPTIONS. The three path alternatives plus one host and one method evaluation exhaust the ALB's five-evaluation limit. AWS applies path matching after URI normalization and excludes query strings; test both listener behavior and the receiver's original-URL denial.
3. Keep the frontend read opt-in disabled while the isolated target is empty or unhealthy. A briefly empty target group can return 503 for those three GETs, but the priority-4 guard must continue to reject every other preview-host path before production priority 10. Do not bind the frontend read base until the isolated image, effective DB role, identity/session material, and live target have all passed their gates.

The rule uses CloudFormation `PathPatternConfig.RegexValues`, with `HostHeaderConfig.Values` for the exact host and `HttpRequestMethodConfig.Values=['GET']`. [AWS listener-condition documentation](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/rule-condition-types.html) permits regex path conditions and at most three evaluations per condition/five per rule; [CloudFormation's path configuration](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-elasticloadbalancingv2-listenerrule-pathpatternconfig.html) has `RegexValues`. This is a proposed source contract, not a synthesized template or an approved listener mutation. The separate Meri listener proposal still names priorities 3/4 and must be reconciled against the same live listener before any Meri change set.
