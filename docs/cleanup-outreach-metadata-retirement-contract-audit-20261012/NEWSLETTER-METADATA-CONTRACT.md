# Intentional legacy newsletter record distinction

This is a read-only contract proposal against backend `fe50dc1c2de1660a036e338cf81acdcf0f2fb26a`, tree `00ca67ae1f2cacc1ae0b51fff25cb33d58954f67`, and frontend PR16 `b680b65e14134be736942b29d715e49c2c6a8b19`, tree `67aabd83e9f129c1fdb25fbe254f41edd99394e7`. The backend legacy newsletter owner remains byte-exact to original C, W and reviewed restoration `a247f7a02a9b94d95e9ee5a516b396202aea994b`. No implementation, frontend dispatch, live API read, customer operation or incident is claimed.

The frontend `outreachRecord` response validator has no `metadata` property and calls `.strip()`. It discards the entire supplied metadata object. Four inert probes run the exact `id`, `client` and `outreachRecord` declarations with the installed, pinned frontend Zod4.6.5 and confirm this; no operation/transport module is imported. The result demonstrates a source boundary when such a response is supplied, not that a real backend response or customer record was lost.

`NewsletterOutreachService.open` creates an existing `OutreachRecord` with `type: 'outbound_campaign'`, `metadata.direction: 'to-clients'`, empty context pool, `metadata.newsletterStageId: stage.id` and `metadata.newsletterRevision: stage.revision`. The owner has no separate `newsletter` record type or wire-kind field. Its current schema persists generic JSON metadata. Therefore an additional kind, DTO version, store or UUID association is unnecessary for recognizing this existing producer's record.

## Bounded response fields and authority

| Existing field | Canonical meaning and proposed receiving boundary |
| --- | --- |
| `type` | Keep the existing `outbound_campaign` value. Rich-record routing considers this value together with the reserved stage hint; generic campaign types and unknown types retain their existing handling. |
| `metadata.newsletterStageId` | Optional response-only identifier of the existing immutable `ws_newsletter_stage` row. Preserve a bounded UUID accepted by the canonical stage owner: 36 characters, RFC variant and versions1–5, case-insensitive. It is never a saved Workspace document-version ID, tenant/client/actor grant, approval, sender grant or instruction to execute. |
| `metadata.newsletterRevision` | Optional positive safe integer snapshot provenance supplied by the same producer. Load authoritative `stage.revision` from the dedicated owner before acting; this metadata stamp cannot authorize a revision, content change, reprepare or resend. |
| Other metadata | Keep the receiving schema's bounded treatment of unknown fields. Do not add blanket passthrough or promote arbitrary JSON to authority. Ordinary records with absent/null metadata remain ordinary; malformed reserved fields require contract/error handling rather than silent migration to a different workflow. |

The smallest prospective receiving change is to the existing response schema and its inferred type, admitting these reserved fields with existing shared operation/session boundaries. It does not add these fields to create/update requests, a new public package version or an alternate DTO. The current backend generic create/update DTO accepts arbitrary metadata objects; without reading the protected service body, this audit cannot assert how all such input is normalized. Consequently field presence is only a routing candidate, even when it looks valid.

The frontend owner should resolve a rich record by its existing record ID through the dedicated newsletter owner. `record` calls the published `getOutreachRecord` interface, validates the stage hint by loading the actual stage, and rechecks record-client access. `stage` validates the UUID, tenant and Clerk owner and every source client. The delivery source-access helper additionally joins the current user and active tenant membership, then checks source-client walls/grants again. These current canonical checks remain necessary after parsing, on retry, after actor/tenant/client change and after grant revocation. Their source checks are not native RLS or concurrency acceptance.

The rich stage identity comes from Workspace's existing revision-CAS staging owner and unique `(documentId, revision, ownerId)` stage snapshot. Its returned route uses `newsletterStage=<stage UUID>`. An existing record hint must not automatically POST `open` to create/reassociate a record. Existing explicit stage/open/prepare/send/test intent semantics stay with their owners; parsing and routing cannot confer approval or generate/send content. The dedicated rich GET packet is its own current shape (`id`, `stage`, prepared versions and related data), not a generic `outreachRecord` response or a V3 session result.

## Separate saved-version contract

Q saved staging binds an exact `WsDocVersion`, snapshot hash, request identity, authorized existing OutreachV3 session and expected state version to its durable command receipt. Its read/export/client revocation, replay and conflict controls remain intact. A rich `WsNewsletterStage` UUID and a saved `WsDocVersion` UUID can both be syntactically valid UUIDs; syntax supplies no relationship. Neither may be copied, inferred, aliased or bridged into the other's endpoint or session. No schema, command, persistence or ownership change follows from this response-field proposal.

## Required inert review before dispatch

Preserve an ordinary record without a marker, the exact legacy producer marker/revision, unrelated metadata stripping and existing operation request strictness. Test malformed/null/empty/reserved fields, wrong record type, unknown stage, a document-version UUID used as a stage hint, forged same-tenant and cross-tenant/actor/client hints, grant/membership revocation, stale metadata revision and expired/uncertain workflow results. Refusing/intercepted canonical collaborators must prove that none of those fixtures performs POST open, prepare, send, reinvite, upload or generation merely by decoding/routing.

GET review may activate a saved reviewer grant/invite, and account-status GET may perform provider reads/receipt effects. Keep these effectful boundaries intercepted. Existing group creation refusals and sender/source restrictions are preserved; this contract supplies no group bypass repair. Frontend assets, packed public newsletter exports, editor/visual/native acceptance and protected unpublished EngagementService reporting remain with their existing owners. The frontend owner can consume this proposed existing-field contract after root reconciliation; dispatch/implementation acceptance remains pending.
