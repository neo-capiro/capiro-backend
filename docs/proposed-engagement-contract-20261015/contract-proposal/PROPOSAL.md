### Exact proposed manual lifecycle and cardinality

Plan lifecycle is `draft | active | archived`; freshness is separate `unknown | current | stale`. These are proposed manual engineering semantics, not a claim that the current backend or design defines a persisted enum. The retained design proves [Active](https://github.com/neo-capiro/capiro-frontend/blob/2758775ddf0e3b17898370be61540498344a9f57/docs/desktop-detail-content-20261014/figma/engagement-desktop.context.txt#L393), [Stale](https://github.com/neo-capiro/capiro-frontend/blob/2758775ddf0e3b17898370be61540498344a9f57/docs/desktop-detail-content-20261014/figma/engagement-desktop.context.txt#L480), [No plan](https://github.com/neo-capiro/capiro-frontend/blob/2758775ddf0e3b17898370be61540498344a9f57/docs/desktop-detail-content-20261014/figma/engagement-desktop.context.txt#L509) and [without an active plan](https://github.com/neo-capiro/capiro-frontend/blob/2758775ddf0e3b17898370be61540498344a9f57/docs/desktop-detail-content-20261014/figma/engagement-desktop.context.txt#L582) display cases; it does not prove transition rules.

| Explicit command                                        | Allowed transition          | Aggregate/result                                                    |
| ------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------- |
| Create                                                  | absent -> draft             | New plan V1; requestId/payload reconciliation; freshness unknown    |
| Activate                                                | draft -> active             | V -> V+1; no sibling-plan change                                    |
| Deactivate                                              | active -> draft             | V -> V+1; history/children retained                                 |
| Archive                                                 | draft or active -> archived | V -> V+1; soft archive only                                         |
| Restore                                                 | archived -> draft           | V -> V+1; never silently reactivate                                 |
| Edit plan or create/edit/reorder/archive/restore a wave | draft or active parent      | V -> V+1 for a real aggregate change; stable child identity/history |
| Record review                                           | draft or active parent      | V -> V+1 plus exact new-version review receipt; section 6           |

All non-create commands first recheck current authorization and expectedPlanVersion. A stale expected version conflicts even if the requested values happen to match. An authorized no-op with a matching version does not increment the version or renew review. A deliberate new review is a new review event, not an ordinary no-op. Distinguish `version_conflict`, `request_id_conflict` and authorized `invalid_lifecycle_transition`; never disclose versions to an unauthorized caller. An already-achieved lifecycle command may return a same-version no-op after those checks; a transition absent from the table conflicts. No command deletes history, changes immutable clientId, alters another plan, or sends/schedules/changes a task, meeting, campaign or outreach.

Authorized archived-plan reads/history and explicit restore remain available. Ordinary edits, wave mutation, activation and review require restoration first. Recommendations reject archived plan inputs after authorization. Plan archive does not rewrite child state; restoration preserves explicit child archives. Wave archive/restore concerns retained child visibility; **wave execution statuses and allowed execution transitions remain undefined** and must not be borrowed from task or campaign statuses.

Client summaries return explicit plan IDs and separate total/active/archived counts with lifecycle/freshness reasons. They never select an arbitrary winning plan or collapse mixed active-current and active-stale plans to one status. `totalPlans=0` and `activePlans=0` are distinct facts, both valid only after a complete authorized read; pagination failure, partial/denied reads and dependency failures remain explicit read states. Archived plans may be excluded from the ordinary active list only with an explicit archive filter/count and separate authorized history access. The retained label “No active plan” is safer than treating draft/archived plans as nonexistent.

### Office-reference lifecycle and concurrency decision

Existing target mutations may rescope a target to another client, rekey a manual target to Directory, archive it, or merge and delete the manual target. Initial plan validation alone is insufficient. [Current target owner](https://github.com/neo-capiro/capiro-backend/blob/cd3c51e940f14e1b2a1040b0ffa445e85d68b332/apps/api/src/engagement/report-targets.ts#L218).

Conservative candidate: bind existing targetId plus officeKey-at-binding and clientId, revalidate on every read, mutation and recommendation, and mark a missing/archived/rescoped/rekeyed/merged reference unavailable without revealing its new client or metadata. Do not silently follow names, attach a different target, cascade a plan deletion or rewrite its client. Permit explicit versioned removal/rebinding; block new bindings or operations that rely on an unavailable reference. Whether to follow an owner-issued merge/rekey receipt later is a separate reviewed extension.

Before persistence can bind these references, coordinate one existing target-owner fence: expose/reuse the current report-target tenant transaction lock through its owner, rather than copying the SQL or importing account ownership. Every plan operation that validates or changes target references takes that fence first, then its client/actor/grant and aggregate locks. Existing target writers already take the fence; the future integration must prove lock order and revocation/rescope/rekey/merge races with them. No frozen target route is changed now, and no FK/cascade/migration decision is allocated by this proposal. Office association persistence remains gated on that owner coordination.

## 6. Stale-plan meaning and DC-window inputs

**Recommended stale meaning for review:** a review cue on an existing authorized plan whose explicitly recorded review basis is no longer valid. It is not an archive, permission change, lifecycle transition or instruction to schedule/send anything. Keep lifecycle and freshness separate.

The following exact **manual review candidate remains PROPOSED for parent acceptance**. Use the same current authorized plan-editor membership/role/wall checks; no new reviewer or owner privilege is introduced. The editor deliberately supplies an explicit future `reviewDueAt` instant. There is no default TTL, age threshold or inference from a report/client timestamp. A review command checks expectedPlanVersion=V, increments the aggregate to V+1, and records `reviewedPlanVersion=V+1`, server `reviewedAt`, actor identity and the explicit deadline atomically. A replacement review appends history and supersedes the prior basis; it does not erase that receipt.

| Read/command event                                                                                      | Proposed freshness result                                                               |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Complete authorized read, no accepted review basis                                                      | unknown                                                                                 |
| Accepted review receipt at V+1, matching current version, checkedAt < reviewDueAt                       | current                                                                                 |
| Any later real aggregate change, including activate/deactivate/archive/restore or any child-wave change | stale if prior review exists; unknown if none; old review/deadline retained as history  |
| checkedAt >= reviewDueAt, even without intervening edits                                                | stale; no automatic lifecycle change                                                    |
| Authorized exact-version ordinary no-op                                                                 | Keep basis/deadline; time expiry still applies                                          |
| Deliberate new review with a future deadline and expected current version                               | New V+1 receipt becomes current; prior review remains historical                        |
| Failed, partial or denied read                                                                          | Explicit read failure/completeness state, never an asserted freshness or No-plan result |

Archiving/restoring cannot revive a previous current review. For an archived plan, return lifecycle=archived separately and retain the historical freshness reason (stale after the archive if a review existed, otherwise unknown); it is excluded from active-plan counts. Restore returns draft with stale/unknown basis until an explicit new review. This conservative exact-version candidate means reviewing a draft and then activating makes the basis stale; the editor may activate and then review. It avoids silently exempting lifecycle changes from aggregate versioning.

Parent review must accept the manual review protocol itself, including edit invalidation and explicit reviewer-supplied deadline, before it becomes public behavior. Until accepted and implemented, the UI continues to report the missing authority truthfully. No algorithm derives review age, availability or rank. External Objective/profile/target changes are not automatically mapped to freshness: that dependency policy requires a defined basis/revision list. Office-reference safety is independently revalidated under section 4 even when review metadata has not changed.
