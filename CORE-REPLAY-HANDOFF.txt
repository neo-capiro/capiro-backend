THE CONFIRMED DEFECT (closed here)
The delivery reconciliation read the NEWEST `maxRecordsPerSource` alerts of the watch
(`orderBy firstObservedAt desc, take maxRecordsPerSource`). That window slides forward, so an alert committed
with more than a page of newer siblings committed after it — or simply pushed out of the window by later
activity — was never offered again: after a crash or an UNKNOWN answer its handoff was permanently lost while
the run still reported a healthy page. Nothing else could recover it, because the diff produces no new draft for
an already-baselined record.

THE FIX (smallest safe pattern; no new table, no new platform, no scheduler)
ONE bounded OLDEST-FIRST keyset page over the watch's OWN canonical, immutable alert rows, with a durable cursor
in the existing versioned source-state checkpoint. Repeats are safe because Meri's identity dedup makes a
re-offered event the same single event.

1. CURSOR PERSISTENCE (the existing owner, extended additively)
   * Location: `business_development_watch_source_states.baseline_state` -> `.scan.delivery`, i.e. INSIDE the
     existing versioned scan checkpoint that `resolveScanCheckpoint` already fail-closes on.
     Shape (`BizDevWatchDeliveryCheckpoint`, version 1): `{ cursorAtMs, cursorId, pagesDone }`.
   * The alert row is NEVER mutated: `businessDevelopmentAlert` stays the immutable canonical source record, and
     no per-alert delivery marker/column was invented (none was needed — see "no missing field" below).
   * Validation: `assertDeliveryCheckpoint` mirrors the existing exposure sub-walk: malformed, newer-version, a
     half-paired keyset, or a bad instant/id/pagesDone THROWS, so the source goes `partial` and NOTHING advances.
     A malformed cursor is never reinterpreted as "start from the beginning" (whole-history replay) nor as
     "advance past everything" (the loss this exists to prevent).
   * Keyset: `(firstObservedAt, id)` ASCENDING, a stable total order even when many alerts share one instant.
     The page predicate is `OR(firstObservedAt > cursorAtMs, firstObservedAt = cursorAtMs AND id > cursorId)`.
   * Start/end: an absent cursor starts at the BEGINNING of the watch's own alert history (the only start that
     cannot strand an alert committed before the cursor existed); the cursor is monotone and is carried across a
     completed traversal cycle AND across a source-scope/identity change (both would otherwise replay history).
   * Legacy/immediate scope: a baseline with no `delivery` field is simply an empty cursor (existing LEGACY
     baselines keep working, exactly like the scan checkpoint itself).

2. ACK SEMANTICS (what may advance the cursor)
   * DEFINITE terminal states (Meri's own answer): DISPATCHED, DEDUPED, ACCEPTED, QUEUED, SKIPPED, REFUSED,
     CONFLICT. A definite answer advances — including a definite NO-EFFECT (SKIPPED = "no approved routine for
     this pair"), which is a terminal disposition, not a delivery.
   * Anything else is UNRESOLVED: UNKNOWN, a non-200 transport/credential/route failure, a thrown or swallowed
     exception, or an unintelligible body. None of these may advance.
   * Only the CONTIGUOUS OLDEST-FIRST prefix of definite answers advances (`acknowledgedDeliveryPrefix`).
     Scattered newer answers are deliberately NOT stepped over: an unresolved older alert holds the cursor
     exactly there, and the next evaluation re-offers the same page. A bounded page can therefore never
     silently advance past an UNKNOWN.
   * Aggregate-only delivery owners stay supported with the CONSERVATIVE WHOLE-PAGE rule: the page is
     acknowledged only when the owner accounts for every offered alert (`offered === page.length`) and reports
     no UNKNOWN. A partial or inconsistent aggregate (e.g. offered 1 of 2) acknowledges nothing.
   * Counts are derived per alert from the owner's dispositions when it reports them, so every offered alert is
     accounted exactly once; a silent/thrown owner is counted UNKNOWN for the whole page — never success.

3. LEASE / CAS ACROSS THE EXTERNAL CALL (no network inside a transaction)
   * Claim: unchanged raw lease claim (`lease_token`/`lease_until` CAS, only an unclaimed/expired row flips).
   * Transaction A (the existing per-source transaction): diff/scan/alerts/deliveries/activity/baseline/scan
     checkpoint commit together, and the healthy finalize now DELIBERATELY RETAINS the lease (it no longer
     clears `lease_token`). Every early-exit path (pending/deferred/review/read-error/error) still releases it
     exactly as before, so no path leaves a lease stranded.
   * Outside any DB transaction: ONE bounded oldest-first read, then ONE call to the delivery owner for exactly
     that page.
   * Transaction B (the existing source-state owner, separate, lease-CAS): persists the advanced cursor inside
     the committed baseline's scan metadata AND releases the lease, `WHERE tenant_id, id, lease_token = <our
     claim>`. A zero-count update means the lease was lost/expired during the bounded call or a newer evaluator
     owns the row — then NOTHING is written, so a stale worker can neither clobber a newer cursor nor resurrect
     a stale baseline. It is always attempted (also when there is no advance, and when the sink threw), so the
     lease is not left to expire on the happy path; a failed release needs no recovery path (the lease expires).
   * A failed recovery READ changes nothing durable and is never a family failure.

4. EXACT PRODUCTION CALLER (unchanged wiring, one factory swap)
   `apps/api/scripts/run-bizdev-watch.ts`:
     `const sourceEvents = origin && secret ? createSourceEventDispositionSink({ origin, secret }) : null;`
   with `origin = process.env.MERI_CONTROL_ORIGIN`, `secret = process.env.INTERNAL_SERVICE_SECRET`, passed as the
   runner's 5th argument. No origin/secret -> NO sink -> no recovery read and NO egress at all (unchanged
   behaviour, still not activated). The new `createSourceEventDispositionSink` is the real producer owner
   (real codec, real disposition parsing, one binding read per (tenant, family, watch) pair, 2 bounded attempts,
   3s timeout, 64KiB response bound); `createSourceEventSink` remains as the aggregate-only view.

5. PRESERVED (not changed by this work)
   watch diff baseline fields and page/cycle semantics, the scan traversal keyset and fence, suppression and the
   configured stale/catch-up/overlap/backpressure behaviour, owner/membership/client checks (a revoked or absent
   owner still returns pending and, because tx A released the lease on that path, the recovery step does not run
   at all — the existing owner-revocation spec still asserts the baseline is untouched), the finite
   network/deadline rules, the alert/delivery/activity ledger, and the existing runner as the sole retry owner.

NO MISSING DB FIELD (no schema need; alternatives attempted)
No new Prisma model, column or table is required and none was requested: the existing
`business_development_watch_source_states.baseline_state` JSON already carries the versioned checkpoint, and the
cursor rides inside it with fail-closed validation. `bizdev-watch-checkpoint.ts`'s keyset-walk checkpoint was
NOT repurposed for source projections (that traversal is untouched); the delivery cursor is a separate sub-object
of the same persisted checkpoint, and an absent one is a valid empty cursor. The immutable alert JSON was NOT
mutated and no per-alert source-payload field was invented. Alternatives rejected: a sliding newest-N window
plus a side cursor (still loses older rows); a per-alert delivery marker on the alert row (unsigned/immutable
canonical source fact, and unnecessary); a second outbox/scheduler (explicitly out of scope); a schema change
(unnecessary once the existing checkpoint owner was extended).
